# Phase 248: Fail-closed operator mount research

**Scope:** ADM-02, the public `threadline_operator_surface/2` mount contract. This note records codebase findings and the already-approved behavior; it does not reopen the decision.

## Recommendation

Make mount authorization explicit at macro expansion: a supported mount compiles only when it supplies a usable one-argument `:authorize_fn` or the exact `:adopter_acknowledges_unauthenticated: true` opt-out. `pipe_through` remains the host's middleware boundary for authentication, sessions, CSRF and other host policy, but by itself never satisfies Threadline's authorization contract. Any other value for the acknowledgement, including `false` or `nil`, does not opt out. A missing or literal-`nil` authorizer without the acknowledgement must raise a `CompileError` at the mount call with a fix-it naming the callback or exact opt-out. Reject a statically recognizable wrong-arity callback at compile time; where a callback expression cannot be statically inspected, the existing runtime invocation must continue to fail closed on exceptions/invalid results.

This is a narrow correction to the supported public macro. Keep `Threadline.OperatorSurface.Router`, `threadline_operator_surface/2`, existing route paths/helpers, callback keys, `authorize_fn`'s accepted return shapes (`:ok`, `true`, `{:ok, scope}`), host-owned auth and tenant policy, and query-scope threading. A callback denial/error remains a deny. Do not accept `export_authorize_fn`, `actor_fn`, `scope_query_fn`, capability-specific authorizers, or unrelated mount options as proof of general surface authorization. The host pipeline still runs and may provide information consumed by `authorize_fn`; Threadline cannot infer its security meaning from a pipeline name.

The current macro computes `has_auth_fn?` using `Keyword.has_key?(opts, :authorize_fn)` and `has_ack?` using `Keyword.get(opts, :adopter_acknowledges_unauthenticated, false)` [VERIFIED: `lib/threadline/operator_surface/router.ex:43-47` — source: `has_auth_fn? = Keyword.has_key?(opts, :authorize_fn)`; `has_ack? = Keyword.get(opts, :adopter_acknowledges_unauthenticated, false)`]. Thus `authorize_fn: nil` currently counts as supplied, and any truthy acknowledgement value can count as acknowledgement. The generated guard currently allows `_has_pipe?` as a third path [VERIFIED: `lib/threadline/operator_surface/router.ex:157-163` — source: `if not (_has_pipe? or unquote(has_auth_fn?) or unquote(has_ack?)) do`]. Replace that predicate with validation of a non-nil, one-arity authorizer OR an acknowledgement whose value is exactly `true`; retain pipeline application independently.

`Auth.on_mount/4` currently defaults a missing callback to `fn _socket -> true end` [VERIFIED: `lib/threadline/operator_surface/auth.ex:79-80` — source: `authorize_fn = Keyword.get(opts, :authorize_fn, fn _socket -> true end)`]. Its callback invocation is inside a rescue path that halts and redirects on exceptions, and unrecognized returns are denied [VERIFIED: `lib/threadline/operator_surface/auth.ex:97-157`]. Keep those denial semantics and scope assignment behavior. The compile-time guard is the required boundary: with an explicit unauthenticated acknowledgement, the existing allow-by-default path is intentional. `ExportAuthPlug` and `ThemeAuthPlug` independently invoke the same mount authorizer (or export override) for sibling HTTP routes, so the macro contract must cover the whole emitted surface, not just LiveViews (`lib/threadline/operator_surface/router.ex:88-137`, `lib/threadline/operator_surface/export_auth_plug.ex:13-33`, `lib/threadline/operator_surface/theme_auth_plug.ex:31-59`).

## Compatibility and security footguns

- Existing adopters that relied on a pipeline alone will get a compile error on dependency upgrade. This is the intentional behavior correction already approved in `.planning/MILESTONE-ARC.md:29-31`; give them a migration message to add `authorize_fn: &MyApp.Audit.authorize_operator/1` while retaining their pipeline. Do not disguise the break by treating names such as `:browser` or `:admin_auth` as trusted proof.
- `Keyword.has_key?/2` is insufficient: a present `authorize_fn: nil` is not an authorizer. A wrong-arity function capture is also not usable; reject statically visible arity mismatch and keep dynamic invocation errors/invalid results denied. Do not fall back to the allow-all default for either condition.
- The exact opt-out is `:adopter_acknowledges_unauthenticated` with literal `true`; an arbitrary truthy value or a feature-specific authorizer does not qualify. This is intentionally an explicit public/unauthenticated mount and should be conspicuous in the compile diagnostic and guide.
- There is a current prose/source conflict: `guides/operator-surface.md:166` says the acknowledgement raises in test and loudly warns in production, while the macro has no such branch and `router_test.exs:76-89` expects the acknowledged mount to compile. Follow the approved D-1 contract for this change (acknowledgement is the explicit compile-time opt-out); correct the inaccurate test/prod claim unless a separate decision reauthorizes that behavior. Do not make test mounts unusable by adding an unrequested environment-dependent rejection.
- LiveView `on_mount` does not protect the generated HTTP export routes or the POST theme route. Keep the host pipeline and ensure the callback decision reaches those routes through `ExportAuthPlug` / `ThemeAuthPlug`; keep `export_authorize_fn` as an optional narrower override. Do not let a new mount guard accidentally change exports, theme sessions, CSRF, callback inputs, or `{:ok, scope}` query scoping.
- The `1.x` option/module/route surface can remain stable while an old insecure mount stops compiling. That is a deliberate source-compatibility impact, not a reason to add a new API. The actual package version follows the milestone's release decision and shipped diff; this note does not assign one.
