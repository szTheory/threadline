# Threadline Admin milestone: product scope

**Synthesis status:** This is a retained research input. Its initial whole-foundation-first ordering and provisional versions are superseded by the [adversarially revised milestone proposal](milestone-proposal.md): begin the requested UI milestone now, with direct safety/proof gates and broader foundation work tracked separately.

**Research date:** 2026-11-10
**Recommendation:** deliver one complete, brand-led redesign of the existing Threadline Admin and its connected example/docs surfaces. Use one whole support investigation as the first implementation slice, then finish every existing Admin job and route in bounded batches before closing the milestone.
**Confidence:** High for product boundaries and route/story proof; medium for exact milestone placement and the locked PhoenixStorybook 1.2 behavior, which must be reconfirmed at implementation time.

## Product decisions

| Decision | Recommendation | Tradeoff and footgun |
|---|---|---|
| Product identity and copy | Use “Threadline Admin” in user-facing UI/docs; migrate to the approved spool identity, dark-default/full-light palette, themes, type, operation colors and calm/exact vocabulary. | Updating visible copy and brand contracts takes a coordinated pass. A global rename would break stable module, config, telemetry, schema, route and query names. Keep a compatibility map and preserve those names. |
| Host branding and sign-in | Use Threadline’s shipped identity in its example. Keep authorization, sign-in, mount path and tenant policy host-owned. | The book describes a host logo override, but the product has no such setting. Do not create white-label/login APIs or promise them in docs. |
| Storybook’s role | Keep PhoenixStorybook in example dev/test. Extend the existing foundations, primitives, forms, states, overlays, data display, groups and patterns with only useful area/screen/journey links. | Static/child stories are fast for component and composition review, but cannot prove production URL lifecycle, access, persistence or exports. Preserve mounted-route and domain tests for those facts. |
| Coverage model | Extend the existing journey inventory and fixture ownership. Map every current route/job to a screen state and executable proof or an explicit unsupported/not-applicable disposition. | An exhaustive duplicate registry and full state × theme × role × viewport matrix would become a maintenance product. Inventory omissions and distinct risk classes, not every possible combination. |
| Demonstration data | Keep the existing deterministic fictional multi-tenant help desk as the sole demo domain. Make the ordinary investigation believable and internally true; keep hostile, oversized, duplicate-label and boundary data as separately named stress cases. | Plausible names alone do not make accurate data. Correct the known weekday/epoch and duplicate-reset instructions if those walkthrough fixtures remain in use. Never imply real adopters or capture beyond installed-table/context/retention limits. |

## Requirements for the complete milestone

1. **R1 — Reconciled implementation base.** Start from clean current main after the Safe-by-default prerequisite. Diff the preserved 31-file candidate and explicitly port, replace or defer each relevant change. Import the approved `brand/` source from the original checkout deliberately; do not silently inherit old worktree package pins or branding.
2. **R2 — Brand integrated across owned surfaces.** Replace the old brandbook implementation authority in the operator UI, README/ExDoc assets, package allowlist and brand-specific tests. Map approved roles to UI semantic tokens while keeping layout/spacing tokens UI-owned. Preserve dark/light/system behavior, use the correct spool variants, serve licensed fonts offline, and package only assets/fonts actually used. Test the eight named contrast roles in both themes and inspect rendered content, controls and focus against composited backgrounds.
3. **R3 — Language without API churn.** Show plain user-facing terms such as record, change, transaction, action, actor, audited table, history and Redacted. Preserve precise distinctions: action ≠ change; transaction ≠ request; actor may be a job/system/anonymous identity; Redacted ≠ excluded/left out ≠ null/absent ≠ unavailable. Keep public module/function/config/telemetry/schema/route identifiers stable. Never claim “tamper-proof”, compliance, complete capture or available history when the current configuration cannot establish it.
4. **R4 — First whole-task slice early, then finish the redesign.** First redesign and prove the existing support investigation: Home/search → Timeline filters → transaction with exact old/new values and actor → record history → copy the full record ID accessibly → return with search context. This is a sequencing gate, not the milestone’s final deliverable. Continue to every other supported screen/job before close.
5. **R5 — Existing route/job coverage preserved end to end.** Cover Home, Timeline, actor and transaction detail, row history, Evidence, Coverage, Redaction and Retention policy, Exports/status/download, plus theme handling. Preserve existing path/query/action contracts, host authorization and scope, downloads, confirmation/cancel, reconnect and return behavior. Add no routes or backend capabilities merely to make a story look complete.
6. **R6 — One connected catalog.** Keep current story paths where practical. Link components → useful compositions → named screen states → existing real journeys. Extend `operator-journey-inventory.json` only for missing story/fixture/component links or genuinely uncovered failure classes; do not add a second registry, generic catalog engine, Fablebook dependency or paid critic.
7. **R7 — Truthful, usable states.** Preserve the route’s supported normal, empty/no-match, pending, completed, failed/unavailable, denied, stale/reconnect, redacted/excluded, missing actor/history, deleted-record and destructive-cancel meanings. Present an honest next step only when the product supports one. Keep exact values/timestamps/time zones and full copyable IDs; never let color replace operation text.
8. **R8 — Accessibility and responsive design across the complete UI.** Check both themes, keyboard/focus, touch, reduced motion, narrow/reflow behavior and actual 200% desktop zoom on representative ordinary and high-risk journeys. Measure the preview container and actual focus target. Use selected risk-based combinations rather than multiplying all states by all environments.
9. **R9 — Small, current proof.** Reuse named verification entrypoints and existing route/domain suites. Pair each bounded visual batch with matched route/story, data/clock, theme, viewport/zoom and source identity; inspect the served render. Static Storybook assertions cannot substitute for route/auth/capture truth. Tests and automated review establish observable behavior and bounded design judgments, not adopter fit or comprehension.

## Phase sequence (names only; IDs/count deferred)

1. **Reconcile and map.** Confirm current base and protected dirty diff; map existing routes, jobs, states, components and owning proofs; settle the compatibility map; identify demo facts that need correction. Do not rebuild the whole catalog yet.
2. **Brand and language foundation.** Import the approved source assets; establish role/token/font/logo contracts; replace legacy brand references and parity tests while retaining runtime theme and structural UI contracts. This phase makes subsequent screen work consistent.
3. **Support investigation vertical slice.** Implement the new shell and shared components through the complete Timeline → transaction → record-history task. Use ordinary fictional help-desk data. Validate actual route behavior, exact values, keyboard/focus, copy and return context.
4. **Complete remaining jobs in bounded batches.** Apply proven shared patterns to actor/correlation and Evidence; then Coverage/Redaction; then Exports/Retention and their permission, pending/failure and destructive states. The final order can shift to follow shared-component dependencies, but all current routes/jobs must receive a disposition and the new design before close.
5. **Close integration and release evidence.** Reconcile catalog links, docs, package assets, Storybook boundary and all existing host journeys. Run the required project gates; resolve or explicitly disposition findings. Close only after the full scope—not just the initial slice—is complete.

**Dependencies:** Safe-by-default mount behavior precedes live Admin journeys. Brand/token and compatibility contracts precede page batches. The initial whole-task slice precedes broad screen rollout. Mounted routes remain the owner of auth, URL/query, download, persistence and destructive behavior; domain tests remain the owner of capture/redaction truth.

## Stakeholder and adversarial review

- **Support operator:** lead with what changed, who and when; make an ordinary ticket investigation finish quickly; never bury the answer below IDs or diagnostic metadata.
- **Developer/architect:** keep code/API semantics and adoption docs stable; reuse Phoenix/LiveView/Ecto boundaries and existing assets. Avoid a new framework, duplicate registry, heavy dependency or discovery query solely to hide a filter.
- **Security reviewer/SRE:** authorization and tenant scope do not widen; false-empty, redaction leakage, unavailable data and missing capture remain distinct. No compliance or “complete history” claims without evidence.
- **Accessibility/design:** preserve semantic operation words, eight contrast-role contracts, both themes, keyboard access, focused controls, zoom/reflow and clear error recovery. Check rendered/composited results, not just token arithmetic.
- **Adversarial stop conditions:** (a) a complete catalog can still hide an awkward ordinary screen, so inspect the whole-task slice before batching; (b) a production-shared renderer can still omit LiveView routing and authorization, so keep real journeys mounted; (c) synthetic coherence can still misstate product guarantees, so tie every state to actual supported behavior; (d) exhaustive matrices and source-digest machinery can outlive their value, so retain only checks that catch a distinct failure class. Do not add human UAT as a default gate or restore the retired critic.

## Deferred from this milestone

New login/authentication provider; host white-label logo/config API; new public routes, API/schema/telemetry names or capture semantics; all-schema auditing defaults; new backend capabilities to satisfy mock stories; a second demo vertical; Fablebook or generic workbench adoption; exhaustive screenshot/state matrices; paid critics or auto-applied AI edits; compliance packs/legal-hold/immutable-archive claims; avatar artwork, mascot, logo animation or sound; unrelated product/infra work.

## Consequential gap for milestone synthesis

The scope itself has a clear winner: migrate the approved brand and complete the existing Admin jobs while preserving product contracts. The open decision is **when it ranks against the current v1.49–v1.51 queue after v1.48**. Recommendation: finish v1.48 first, then use the milestone guide’s fresh evidence-based ranking at close; do not assign phase or release numbers in this product-scope artifact. If current product-code changes alter the public compatibility promise, treat that as a separate scope/semver decision rather than folding it into this UI migration.
