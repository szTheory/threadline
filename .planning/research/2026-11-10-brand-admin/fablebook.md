# Fablebook principles for Threadline's PhoenixStorybook

## Finding: ideas are portable; Fablebook is not yet a working reference

Fablebook's README says the workbench is unreleased, and its only route returns a plain-text placeholder (`fablebook:README.md:3`; `fablebook:lib/fablebook/router.ex:24-40`; `fablebook:lib/fablebook/placeholder.ex:11-15`). Its seed says no requirements are validated yet; the tier ladder, state coverage matrix, LLM context bundle, and journey checks remain unchecked v1.0 commitments (`fablebook:FABLEBOOK-SEED.md:29-48`; `fablebook:FABLEBOOK-SEED.md:126-141`). Treat these as design proposals, not proven Fablebook behavior. The repo does have working packaging safeguards: mounting is dev-only by convention, and a contract test proves a reachable prod mount fails compilation (`fablebook:lib/fablebook/router.ex:5-18`; `fablebook:test/contract/prod_guard_test.exs:13-35`).

Threadline already has the best implementation evidence here. PhoenixStorybook is confined to the example app's dev/test dependencies; the library package has a contract that forbids a PhoenixStorybook dependency or route (`examples/threadline_phoenix/mix.exs:80`; `test/threadline/operator_surface/storybook_boundary_test.exs:27-47`). The example README explicitly calls it a maintainer review tool, not a production route or public component API (`examples/threadline_phoenix/README.md:80-93`). Keep that boundary; do not add Fablebook or another production dependency.

## Recommended hierarchy and coverage

Keep today's eight component-oriented Storybook entries and their folders. Connect them to higher levels as the UI needs them, preserving each story's stable path and explicit provenance:

| Level | Threadline subject | Review question |
| --- | --- | --- |
| Primitive | button, ref, badge, field, pager | Is this control correct and legible? |
| Pattern | filter toolbar, data panel with pager, permission/error state | Do these controls complete their small job together? |
| Area | Timeline results, transaction detail and row history, coverage or redaction panel | Does this operator area hold up with realistic audit data? |
| Screen | Full Threadline Admin screen in its normal shell | Can the operator finish the stated job? |
| Journey | Ordered screens/actions for one operator job | Do the real transitions reach the expected outcome? |

This borrows Fablebook's four questions (`fablebook:FABLEBOOK-SEED.md:43-44`) without replacing the existing Storybook categories (`examples/threadline_phoenix/storybook/index.exs:8-15`). Add `areas/` and a small set of screen stories only when they compose real production components; do not turn the gallery into a second application. Keep full interactions in the existing ConnCase and Playwright lanes.

Do not create a second journey/coverage registry. Cached `origin/main` already has `e2e/support/operator-journey-inventory.json`, which links jobs and failure classes to stable Playwright test identities and records voting/nonvoting boundaries (`main@d35b9422:examples/threadline_phoenix/e2e/support/operator-journey-inventory.json:4-38`). Extend or reference that inventory with Storybook paths, owning components and fixture IDs as needed. Fablebook's per-story state classification and visible gap/waiver idea can help spot missing applicable cases (`fablebook:FABLEBOOK-SEED.md:45-49`; `fablebook:GLOSSARY.md:183-196`); map gaps to the existing inventory and explicitly mark covered, planned, not applicable with reason, or unsupported/debt. Do not create the full Cartesian product for every primitive.

Anchor whole screens and journeys to the approved product jobs: support staff find a change by table/person-or-job/date, open the record's history, and copy its ID; reviewers check capture coverage, redaction, retention, and export (`brand/brand.json:31-38`). PhoenixStorybook stories inspected here are static `:page` examples: they document component states but do not prove that an operator can complete a job. The retained candidate has real mounted-route proofs, and cached `origin/main` carries those flows forward: the journey inventory covers investigation, actor/correlation pivots, evidence history, scoped coverage, redaction, exports, retention denial, reconnect, keyboard, responsive, reduced-motion, and desktop zoom (`main@d35b9422:examples/threadline_phoenix/e2e/support/operator-journey-inventory.json:5-38`). The Timeline investigation test exercises keyboard operation and URL recovery (`main@d35b9422:examples/threadline_phoenix/e2e/tests/operator-timeline-investigation-flow.spec.ts:771-809`); the transaction-evidence test follows real writes through Timeline into exact change details (`main@d35b9422:examples/threadline_phoenix/e2e/tests/operator-transaction-evidence.spec.ts:38-128`). Reuse these proofs before proposing new ones; add only behavior the inventory does not establish.

The old critic-oriented page/path matrix and refutation layers belong to the retained candidate and were removed from cached `origin/main`. A smaller dev/test stress harness and reusable fixture helpers remain (`main@d35b9422:lib/threadline/operator_surface/live/stress_live.ex:14-40`; `main@d35b9422:lib/threadline/operator_surface/stress_fixtures.ex:1-32`). Preserve useful current fixtures; do not recreate the retired critic matrix or MechanicalChecker. Static specimens and live route tests establish different facts. The Storybook tests remain useful for source coverage/provenance, while the Storybook Playwright smoke checks route rendering and horizontal overflow at 320/375/768 px, not journey behavior (`examples/threadline_phoenix/test/threadline_phoenix_web/storybook_stories_test.exs:156-215`; `examples/threadline_phoenix/test/threadline_phoenix_web/storybook_stories_test.exs:244-255`; `examples/threadline_phoenix/e2e/tests/operator-storybook.spec.ts:5-16`; `examples/threadline_phoenix/e2e/tests/operator-storybook.spec.ts:59-81`). The separate main-branch journey tests supply the route behavior evidence above.

## Fixtures and rapid AI iteration

Reuse the example's deterministic fiction instead of inventing unrelated sample data. `DEMO-MANIFEST.md` centralizes fixed UUID/time anchors, Acme/Globex/offboarded organizations, hero ticket incidents, and recipes for happy, empty, dense, scoped, denied, redacted, retention, and actor-kind states (`examples/threadline_phoenix/DEMO-MANIFEST.md:7-17`; `examples/threadline_phoenix/DEMO-MANIFEST.md:19-45`; `examples/threadline_phoenix/DEMO-MANIFEST.md:58-105`). It also contains one known chronology defect: the prose calls May 20 “last Tuesday,” although the date is Wednesday; reconcile the epoch, date, and label before using it as a story fixture. Keep Storybook fast and DB-free by projecting named synthetic records from that domain into the current allowlisted `Fixtures` helper; use the seeded DB only for real route/journey tests. Make fake-but-plausible values, timestamps, IDs, before/after values, redaction, and human/job/system actors consistent across stories. Do not feed real customer rows, credentials, or secrets to AI.

For AI iteration, use Fablebook's proposed small, reproducible context as a principle, not its unimplemented bundle system or the retained worktree's retired critic. Give the agent one job, story/route, fixture/state, owning components, expected result, approved brand role and current executable proof. Capture only the changed Storybook story and affected route at the required theme/viewport; record source revision, fixture/clock, browser and capture identity. Ask one focused critique, verify every claimed DOM/source detail, make a bounded change, then run the mapped proof and inspect the new render. Current main contains browser screenshot regression tests and the journey inventory; those are distinct visual and behavioral evidence. Do not add a paid critic, restore MechanicalChecker or the retired critic/refutation tooling, auto-apply source changes, or let an AI judgment override the signed-off canon.

## Coherence and pitfalls

- The signed-off Threadline v1.0 brand is a fixed constraint: dark default, complete light theme, system theme support, exact audit values/IDs/timestamps, calm factual copy, and operation words Insert/Update/Delete/Redacted written out (`brand/BRAND.md:5-29`; `brand/brand.json:41-66`; `brand/brand.json:138-207`). Do not import Fablebook's proposed neutral, unbranded workbench chrome into Threadline Admin.
- Preserve Threadline's capture / semantics / exploration separation and canonical nouns (`AGENTS.md:9-27`). In particular, Fablebook's “Twin” term is not portable: Threadline already has Organizations/tenancy, and Fablebook itself says “Twin” should not mean tenant (`fablebook:GLOSSARY.md:242-244`). Call them fictional demo organizations/sample data. Keep `AuditAction` distinct from a user's UI action or journey step.
- Do not count a static component specimen as proof of permission boundaries, production data fidelity, or a complete user flow. Keep dev/test routing and the maintainer-only boundary covered as they are today (`examples/threadline_phoenix/lib/threadline_phoenix_web/router.ex:1-23`; `examples/threadline_phoenix/test/threadline_phoenix_web/storybook_route_test.exs:37-55`).
- Avoid a universal state matrix, generated combinations, and duplicate fixture catalogs. Reuse `StressFixtures` via explicit allowlists; use `DEMO-MANIFEST` as the shared narrative source; keep story samples synthetic and deterministic.

## Unaddressed angles

1. Choose which two or three approved jobs get first-class screen/journey coverage; the brand and demo manifest define candidates, not their implementation priority.
2. Extend the existing inventory with story/fixture relationships where useful and choose the existing test that owns drift detection.
3. Verify PhoenixStorybook's supported way to present any proposed multi-step/screen sequence before relying on the gallery for it; this inspection found static story pages only.
4. Compare the selected job/story map against `operator-journey-inventory.json` and its owning route tests before claiming any flow gap. The inventory shows broad coverage already; this research did not run those tests or prove their current receipts.
