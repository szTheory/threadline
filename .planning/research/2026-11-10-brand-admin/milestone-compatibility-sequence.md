# Milestone Compatibility and Sequence

**Synthesis status:** This is a retained research input. Its initial whole-foundation-first ordering and provisional versions are superseded by the [adversarially revised milestone proposal](milestone-proposal.md): begin the requested UI milestone now, with direct safety/proof gates and broader foundation work tracked separately.

**Research date:** 2026-11-10
**Recommendation:** complete the currently ranked security foundation as v1.48, then deliver the brand-led Admin milestone as v1.49. Plan the shipped user-facing Admin experience for package 1.3.0; do not infer a patch bump merely because API names stay stable.

## Evidence and decision

- Cached `origin/main` is `d35b9422`; `.planning/STATE.md` says v1.47 is complete, package 1.1.0, with no active milestone. `.planning/MILESTONE-ARC.md` ranks v1.48 Safe by default next, targeting 1.2.0. Phase 247.1 closed REL-02 and left REL-01 deferred until the first natural release; it did not ship a package change.
- The live baseline reported for this review has required CI run 40856193944 green, but it is not an all-clear: [issue #61](https://github.com/szTheory/threadline/issues/61) reports Phoenix HTML 4.3.0 attribute injection, Ecto 3.14.2 unbounded caching, and Bandit 1.13.1 denial-of-service/request-smuggling advisories; [issue #90](https://github.com/szTheory/threadline/issues/90) reports the first Flake Detection iteration on main as broken. Before milestone acceptance, assign each a bounded fix-or-accepted-risk disposition and reopen trigger. This is triage, not a requirement to implement unrelated dependency or CI work inside the UI milestone.
- The operator mount is a direct security dependency. In `lib/threadline/operator_surface/router.ex`, the compile guard accepts any `pipe_through`; in `lib/threadline/operator_surface/auth.ex`, the absent `authorize_fn` defaults to `fn _socket -> true end`. This contradicts `guides/operator-surface.md`'s fail-closed promise. The approved v1.48 fix—compile error unless `authorize_fn` or explicit unauthenticated acknowledgement is present—must land before implementation or acceptance of new Admin screens.
- The other v1.48 items (transaction-ID reuse after restore, CSV/header and SQL hardening, PgBouncer lock behavior, support-floor change) are not technical prerequisites for a visual migration. They remain ranked, known foundation work. Do not absorb them into the UI requirements or describe them as resolved by UI proof. Keeping v1.48 first is a risk-priority recommendation based on the current approved arc, not a code dependency claim.

Recommendation: retain v1.48 first. Moving UI ahead changes the accepted risk order; the authorization to research and scope UI does not itself disposition the other known risks.

## UI milestone prerequisites and bounded scope

1. **Reconcile the preserved candidate.** The retained branch is `0f9347f2`, 203 commits behind and 17 ahead of cached main. Preserve its 31 dirty product/docs/test files, but reconcile against `d35b9422` before porting. Main overlaps the paused edits in `guides/operator-surface.md`, `style_contract_test.exs`, and the accessibility/motion browser tests. The current workspace also has unrelated planning and instruction edits; do not sweep them into the product migration.
2. **Make the approved brand the source of truth.** Import the original checkout’s `brand/` assets deliberately. Replace old brandbook authority and `test/threadline/brandbook_token_parity_test.exs` contracts in one coordinated migration across README/ExDoc logos, favicon, logo component, package allowlist, fonts, docs and tests. Map the eight stable contrast IDs in both themes to UI roles; test actual values rather than spacing-token parity or stale brandbook prose. Package only referenced assets, required webfont subsets and their OFL licenses, not the full source bundle.
3. **Keep host behavior and public compatibility stable.** “Threadline Admin” is the user-facing name; preserve `Threadline.OperatorSurface`, `threadline_operator_surface/2`, option/config keys, route helpers, URL/query semantics and telemetry event names/metadata. Keep host-owned auth, path, sessions and tenancy. Do not add a logo-override API merely because the brand book permits one conceptually; the product has no such setting. Do not add sign-in/SSO, new routes, all-schema defaults or a new navigation capability as incidental brand work.
4. **Preserve the drop-in runtime.** The public mount stays host-owned and optional-Phoenix. Keep dark as default, complete light and system themes, session-backed native `POST <mount>/theme` with CSRF, and the existing font/script opt-outs. Scope CSS to the Threadline preview/root; keep rendering offline without a new asset service or dependency. If Familjen Grotesk is served for headings, bundle the needed subset and license, and retain a usable system fallback when `operator_surface_embed_fonts: false`. Do not change copy-helper CSP behavior or require inline script for the theme picker.
5. **Start with one supported job.** Use the existing support investigation: filter for ticket #4521’s unexpected change → inspect the transaction’s exact values and actor context → open record history → copy the full record ID → return with filters intact. Confirm the host fixture/schema supports the story; label projected Storybook data as synthetic. Keep timestamps zoned, shorten IDs in the middle without changing their copied value, and distinguish absent history, unavailable reads, denied access, fields left out and values actually Redacted. Correct the existing demo chronology/reset documentation while fixture data is in scope.
6. **Prove each seam where it runs.** PhoenixStorybook child stories can inspect component/composition rendering but do not prove `handle_params/3`, host authorization, downloads, persistence or reconnect. Keep those on mounted host routes and existing browser/ConnCase contracts. Reuse the existing journey inventory; do not create a second catalog registry, restore the retired critic, or claim screenshots/synthetic fixtures establish comprehension.

The export presentation may be refreshed with the UI, but its download/CSV semantics must stay unchanged; if implementation changes export behavior or increases its use, sequence that work after the v1.48 CSV/header hardening. The same rule applies to any route that would expose a known v1.48 risk more broadly.

## Adversarial checks

- **Security/adopter:** a more polished Admin must not make the mount appear self-authenticating. Require the host’s explicit authorization contract first; keep exports separately authorized and coverage/policy/evidence capability gates intact.
- **Semantics/operator:** preserve the distinction between `AuditAction`, `AuditTransaction` and `AuditChange`, and between actor and user. UI words can become “action”, “transaction”, “change”, “actor”, “record”, “history”, “audited table” and “Redacted” without renaming public modules or persisted fields.
- **SRE/maintainer:** do not add a dependency for a local catalog or font pipeline. Keep licensed assets small, packaged-artifact assertions truthful, offline fallback working, route state bookmarkable, and verification bounded to matched route/data/theme/viewport/zoom plus behavior/accessibility proof.
- **Release/semver:** milestone IDs and Hex versions are separate. Recommend v1.49 / 1.3.0 for the planned shipped Admin experience; determine the actual conventional release type from the final product diff. If implementation collapses to docs or dev-only Storybook with no shipped package behavior, do not force a package release.
