# Verification and Developer Experience: Brand/Admin Work

**Baseline inspected:** `d35b9422fb2a83897902c2276cb94ecf5129a5e3` (`origin/main`, v1.47 / package 1.1.0); retained UI worktree is older and dirty. This report is a proposal for scoping, not evidence that the UI or brand migration is implemented.

## Recommendation

Keep one proof system: PhoenixStorybook for fixed component/state rendering; the example host's mounted `/audit` routes plus Playwright for URL, authorization, clipboard, navigation and actual task behavior; ExUnit/ConnCase for database, redaction, tenancy and fixture truths. Extend the existing journey inventory/receipt and seeded help-desk scenario. Do not add a second fixture registry, Storybook app, visual-critic CI job, or new CI lane.

First prove one ordinary task through shared production components: support filters a ticket change, opens its transaction and exact diff, opens row history, copies the complete ID, then returns with the query intact. Keep no-match, redaction/left-out, denied/unavailable, clipboard failure and stress cases separately named. Every material inventory row gets a proof owner and disposition: covered, planned, not applicable with reason, or unsupported/debt. Select cross-cutting combinations by risk; do not build every state × role × route × theme × viewport combination.

## Phase proof budget and closure

1. Reuse the current desktop/mobile required browser matrix and existing representative Storybook smoke. Add the first whole-task journey and only distinct uncovered brand/accessibility cases to the current specs and inventory. Both projects already run the whole selected suite; the receipt already enforces discovered-and-executed inventory coverage.
2. Use one deterministic fixture and a captured clock for the ordinary slice. Review both themes for changed components; apply viewport/actual-zoom checks to the assembled journey or affected responsive controls. Use one matched visual before/after pair for the bounded batch, not screenshot snapshots for every story and state.
3. A short agent visual/copy pass may report bounded observable issues against the brand and task contract. Do not put an LLM score in CI or claim adopter understanding. Automated completion follows the project's zero-human-verification default; comprehension claims need actual user research and are outside this proof budget.
4. Close only against the exact candidate with passing required checks, current source/asset/fixture identity, and no unclassified acceptance rows. Record remaining visual limitations and unsupported behavior as explicit debt with owner/reopen trigger. A green browser receipt proves inventory execution, not that every design is good.

## Minimal CI/CD delta

**New workflow jobs: zero.** Put recurring brand/fixture contracts in the existing example test command (`mix verify.example`); put route, real focus/clipboard, responsive, theme and selected accessibility cases in the existing Playwright specs and inventory, which already feed the required browser receipt. Leave `ci-required`, job IDs, project partition and release lanes unchanged unless a later measurement identifies a missing recurring failure class.

This avoids rerunning the same two Playwright projects, adding a browser install/dependency, or placing visual opinions on the critical path. Keep the throwaway comparison/capture local to the bounded batch and archive only its small attributable evidence. The latest exact-main receipt shows the current test job at 448s versus desktop/mobile browser legs at 354s/341s; it is one run, useful for selecting where to inspect if this scope adds cost, but not a before/after saving. Reuse `.planning/research/2026-11-10-brand-admin/milestone-live-baseline.json`; do not dispatch CI just to claim an optimization.

## Open boundary

The current baseline also has separate dependency-advisory and deterministic first-iteration test-failure follow-ups (issues 61 and 90); preserve and triage those independently rather than treating the historical required-CI pass as proof that scheduled checks are clear.
