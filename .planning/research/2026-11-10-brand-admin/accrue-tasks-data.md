## Conditional transfer to Threadline

1. **Start with one real investigation job.** Use the smallest whole flow supported by Threadline’s present routes and data: find a changed record, open its history or transaction, understand the operation, before/after values, actor and time, then return with the search context intact. A help-desk ticket can be the sample only if the existing host/schema can represent its relationships and changes. The domain model says a change is not an action, a transaction is not a request, and a user is not always the actor; keep those facts visible in the example. (`prompts/audit-lib-domain-model-reference.md:91-94,104-151,827-830`; see also `.planning/research/2026-11-10-brand-admin/README.md`)
2. **Honor Threadline’s vocabulary while preserving compatibility.** User-facing copy should follow the signed-off terms: history, record, change, transaction, action, actor, audited table, and Redacted. Explain what people need before an ID. Keep public module/function/field/route names distinct from those labels; do not rename or invent routes, login, white-label, tenant, or authorization behavior as part of visual work. The host app owns where Admin runs and who can open it. (`brand/BRAND.md:455-495,574-580`; `AGENTS.md:127-134`; `prompts/audit-lib-domain-model-reference.md:87-94`)
3. **Treat filters and summaries as job aids, subject to product evidence.** Inspect Threadline’s actual filters and permissions first. Hide a category only when it has no useful choice in that screen’s real scope; keep an active URL constraint visible and removable if that behavior is supported. Prefer one accurate result summary beside recovery/reset, without claiming a loaded count is a total. Preserve pagination, failure/retry, accessible status, and current URL semantics. Accrue’s owner-type/org scope is billing-specific and must not be copied.
4. **Make ordinary data tell one coherent fictional story.** Use a stable, readable record and actor, a plausible operation, consistent timestamps and old/new values, and only identifiers/relations the actual schema and renderer support. Keep routing UUIDs or evidence-bound fixture keys stable; use valid formats and safe reserved email domains where relevant. Label projected/static stories as synthetic. Put long Unicode, oversized values, duplicate labels, malformed or boundary cases in explicitly named edge states rather than the default. Plausibility is not evidence of live capture or user fit. (`accrue:.planning/phases/256.1-comprehensive-jtbd-led-admin-inventory-and-phoenix-storybook/256.1-LEARNINGS.md:55-61,103-111`; `brand/BRAND.md:501-505`)
5. **Keep empty and failure states truthful.** For Threadline, no matches, no captured history, an unavailable read, access denial, a redacted value, and a field that was never recorded have different meanings. Give each a next step only where the existing behavior supports one; never turn an unavailable read into “no changes.” (`brand/BRAND.md:449-458,485-495`; `prompts/audit-lib-domain-model-reference.md:369-392`)
6. **Separate automated checks from claims about users.** Tests can protect filter semantics, reset/return behavior, status copy, ID handling, and distinct state rendering. Use same-route/same-data visual comparisons and bounded agent review for layout and task-flow quality, consistent with Threadline’s zero-human-verification default. Do not claim observed comprehension or adopter fit from screenshots, illustrations, synthetic fixtures, tests, or agent judgment. Accrue’s open operator review is not a Threadline phase gate; real user evidence is needed only when making an observed comprehension/adopter-fit claim. (`brand/BRAND.md:501-505`; `prompts/threadline-elixir-oss-dna.md:37-41`; `AGENTS.md:84-87,127-134`)

## Decision

Transfer the **method**—whole-task-first, coherent default data, meaningful controls, distinct empty/error states, and bounded evidence. Do not transfer Accrue’s billing entities, ownership scope, exact filter rules, component layout, or unresolved catalog choices. Threadline’s signed-off brand and verified product behavior decide the final hierarchy and language.
