# Threadline v1.22 Research: Policy / Evidence Plane

**Date:** 2026-05-25
**Milestone:** v1.22 — Policy / Evidence Plane
**Confidence:** HIGH on repo-fit, MEDIUM on exact operator surface shape

## Thesis

The right next milestone is a narrow evidence-plane slice: append-only evidence
records for Threadline-owned governance surfaces, plus read-only operator and
Mix-task/API access to those records. The work should improve procurement and
audit-of-audit posture without turning Threadline into a compliance platform,
policy engine, RBAC system, or tenant model.

This follows directly from the shipped v1.21 support-safe `/audit` baseline.
The strongest open question is no longer whether operators can use the surface
truthfully; it is whether Threadline can prove what policy and governance
posture existed when operators used it.

## Milestone summary

- **Version:** v1.22
- **Name:** Policy / Evidence Plane
- **Arc status:** Activated default candidate from `.planning/MILESTONE-ARC.md`
- **Goal:** Add durable policy/evidence records and read-only proof surfaces for
  Threadline-owned governance concerns without widening the library boundary.
- **Why now:** Enterprise scrutiny now falls on evidence quality and audit-of-audit
  posture more than on support-lane truth.

## Target features

- Append-only evidence records for Threadline-owned governance subjects such as
  redaction posture, trigger coverage posture, retention runs, export posture,
  and support-lane proof posture where Threadline already owns concrete facts.
- Public library APIs and Mix-task parity for creating and reading evidence
  snapshots without requiring Phoenix.
- Read-only `/audit` evidence views that present the same evidence facts on the
  shipped operator surface without creating a new UI family.
- Explicit documentation of what the evidence proves, what remains host-owned,
  and which stronger claims Threadline still does not make.

## Key context

## Recommended requirement shape

1. Start with evidence primitives and append-only persistence.
2. Add API and Mix-task parity before new mounted views.
3. Reuse the existing `/audit` family for any UI.
4. Lock negative claims in docs and support matrix:
   no legal hold, no immutable-storage guarantees, no generic compliance packs,
   no Threadline-owned RBAC or tenancy DSL.
