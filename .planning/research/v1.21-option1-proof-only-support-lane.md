# Threadline v1.21 Option 1 Memo: Proof-Only Support/Operator Lane

**Date:** 2026-05-24
**Confidence:** MEDIUM-HIGH

## 1. Thesis

Option 1 is viable only if it is framed narrowly: prove that the existing in-tree `/audit` surface can host a support-safe, read-only, multitenant operator experience through one host-owned `authorize_fn` plus one host-owned `scope_query_fn`, while keeping exports denied by default.

That is already close to the current repo shape. It is also the idiomatic Elixir/Phoenix shape for a library: the host owns Plug pipelines, auth, tenancy semantics, and Ecto query narrowing; Threadline owns the mount macro, the LiveView/controller plumbing, and the query handoff seam. What should not be claimed in v1.21 is a first-class "support lane" product abstraction with its own role DSL, tenancy model, or separate policy subsystem.

The main blocker to making a broad claim today is that the row-history/as-of subview is not scope-aware yet. Timeline, transaction, actor, and export flows already carry `scope_query_fn`; row history does not.

## 2. Pros

- Fits the repo's existing architecture. `authorize_fn`, `scope_query_fn`, and `export_authorize_fn` already form the public contract across LiveView and HTTP export surfaces.
- Matches least-surprise Phoenix composition. The host keeps `/audit` behind its own browser/auth pipeline and passes normal function captures; the library does not invent a framework inside the framework.
- Good multitenant posture when scoped correctly. The example app and tests already prove support users can see only their org's transaction data and receive `403` for exports.
- Low API surface expansion. This can ship mostly as tightened proof, docs, and tests rather than a new subsystem.
- Preserves optional-dependency discipline. Capture-only adopters are unaffected; the work stays inside the existing `phoenix-surface` lane.

## 3. Cons / Risks

- The current proof is partial, not end-to-end. `Threadline.OperatorSurface.Live.RowHistoryComponent` calls `Threadline.history/3` and `Threadline.as_of/4` directly with no scope seam, so a support-scoped transaction page can still expose unscoped row history unless fixed or explicitly excluded.
- Opaque scope maps are flexible but easy to misuse. If adopters forget a surface clause in `scope_query_fn`, they can get silent over-breadth.
- "Support lane" can overpromise. The repo currently proves a host-owned scoped operator surface inside the Phoenix lane, not a separately versioned or independently hardened support product mode.
- Saved views and actor semantics are admin-shaped today. Support scopes can inherit fallback actor refs, but the ergonomics and ownership story are still tuned more for operators/admins than constrained support personas.
- A separate support tree would increase surprise. The docs already push one shared `/audit` mount; introducing `/audit/support` as a primary story would complicate router and docs without clear payoff.

## 4. Architectural Implications

- Keep one canonical `/audit` mount. The host should differentiate admin vs support through its pipeline and one shared `%{assigns: assigns}` authorizer, not through a second library-owned surface.
- Keep auth host-owned and query scoping host-owned. This is the right library boundary for Plug/Ecto/Phoenix.
- Treat `scope_query_fn` as the single narrowing seam across every read path. If Option 1 is chosen, row-history/as-of must either:
  - be brought onto the same seam, or
  - be removed/hidden for support-scoped sessions in v1.21.
- Keep exports deny-by-default for support. Current docs and code already support this cleanly through `exports: false` or `export_authorize_fn`.
- Do not add a Threadline roles DSL, tenant behaviour, or policy schema. That would be a different milestone.

## 5. DX / UX Implications

- Preferred developer story: one router macro call, one shared `authorize_fn`, one `scope_query_fn`, optional `export_authorize_fn` only for stricter export posture.
- Preferred support UX: same `/audit` surface, fewer affordances. Read-only browsing is fine; export buttons should disappear and export URLs should 403.
- Documentation should be explicit that the returned scope is opaque host data, and that authors must scope every supported surface clause intentionally.
- Tests should read like contract tests, not implementation tests: support user sees only in-scope timeline/transaction/actor data, does not see export affordances, export endpoints 403, and row-history behavior is either scoped or unavailable.

## 6. Recommended Phase Shape If Chosen

1. **Close the scoping gap first**
   - Make row-history/as-of honor the same host-owned scope seam, or explicitly disable that subview for support-scoped sessions.
   - Add regression tests proving no cross-tenant leakage through that path.

2. **Narrow the claim in docs**
   - Position v1.21 as "proof-only support-read-only posture inside the Phoenix surface lane."
   - Say clearly what is covered: shared `/audit`, host-owned auth, host-owned query scoping, exports denied by default.
   - Say clearly what is deferred: role DSL, policy engine, separate support surface, support-specific saved-view semantics, broader lifecycle guarantees.

3. **Strengthen repo proof**
   - Add one canonical example in the example app using the shared `/audit` route with admin + support behavior.
   - Add high-signal tests spanning timeline, transaction, actor, row-history decision, and export denial.

4. **Defer everything else**
   - Do not build first-class support abstractions.
   - Do not split packages or add new behaviours.
   - Do not broaden the support matrix beyond the existing Phoenix lane.

## Bottom Line

Choose Option 1 only as a constrained hardening-and-proof milestone. That is aligned with the current repo and with idiomatic Elixir library design. Do not choose it if the goal is to introduce a new first-class support product lane; the current architecture is not trying to own that, and should not start in v1.21.
