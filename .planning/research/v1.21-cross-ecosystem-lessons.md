# Threadline v1.21 Cross-Ecosystem Lessons

**Date:** 2026-05-24  
**Focus:** scoped support/operator adoption for Threadline as an Elixir library with optional Phoenix UI  
**Confidence:** HIGH on Elixir/Phoenix patterns, MEDIUM-HIGH on cross-ecosystem transfer

## Bottom line

The strongest ecosystem pattern is consistent: successful admin/operator surfaces keep auth and tenancy host-owned, thread an explicit actor/scope into every read path, treat exports as a separate capability, and make the UI a thin convenience layer over the same query contracts the API/CLI use.

That points Threadline toward a **proof-only v1.21**: prove the existing `/audit` surface is support-safe for Phoenix SaaS adopters, close the remaining scope gaps, and avoid inventing a Threadline-owned auth, role, or tenancy subsystem.

## 1. Strongest lessons to copy

### Elixir / Phoenix first

- **Phoenix LiveDashboard:** mount with a router macro, but require host auth in front of it. That matches Threadline's best boundary: library-owned route macro, host-owned `pipe_through`, no built-in auth assumptions. LiveDashboard also keeps destructive actions opt-in instead of default-on.  
  Sources: LiveDashboard production auth guidance and router options (`:on_mount`, `:allow_destructive_actions`) [hexdocs.pm](https://hexdocs.pm/phoenix_live_dashboard/Phoenix.LiveDashboard.html), [hexdocs.pm](https://hexdocs.pm/phoenix_live_dashboard/Phoenix.LiveDashboard.Router.html)

- **Oban Web:** separate "who is this?" from "what can they do?" via `resolve_user/1` and `resolve_access/1`, then emit audit/telemetry for operator actions. Threadline already has the transport split (`authorize_fn` vs `export_authorize_fn`); the lesson is to keep read-only vs action permissions explicit and observable.  
  Sources: Oban Web access control and resolver docs [hexdocs.pm](https://hexdocs.pm/oban_web/limiting_access.html), [hexdocs.pm](https://hexdocs.pm/oban/2.8.0/web_customizing.html), [hexdocs.pm](https://hexdocs.pm/oban/2.4.1/web-changelog.html)

- **AshAdmin:** explicitly says there is no built-in security beyond app policies, and its tenant UX improves once you provide a real tenant selector instead of a raw text field. That is the right humility for Threadline too: the host owns security, but the library can offer better scoped UX once the host supplies good scope data.  
  Sources: AshAdmin security and tenant selection docs [hexdocs.pm](https://hexdocs.pm/ash_admin/getting-started-with-ash-admin.html)

- **Backpex:** URL-as-state filters plus strong param validation/clamping are the right operator UX baseline. Threadline's timeline already leans this way; v1.21 should keep support scoping on the same query spine rather than introducing a second filter dialect.  
  Sources: Backpex filters, visibility hooks, and pagination validation [hexdocs.pm](https://hexdocs.pm/backpex/what-is-a-filter.html), [hexdocs.pm](https://hexdocs.pm/backpex/visibility-and-authorization.html), [hexdocs.pm](https://hexdocs.pm/backpex/pagination.html)

- **Ash multitenancy:** tenant context must be explicit, and optional global access must be mirrored in authorization or it becomes a leak. That maps directly to Threadline's `scope_query_fn`: every read path must either honor scope or be unavailable to support-scoped users.  
  Sources: Ash multitenancy and scope docs [hexdocs.pm](https://hexdocs.pm/ash/multitenancy.html), [hexdocs.pm](https://hexdocs.pm/ash/3.5.13/Ash.Scope.html)

### Cross-ecosystem prior art worth borrowing

- **ActiveAdmin / Avo / Django admin:** do not assume the app's auth provider, but do provide central places to scope collections and check per-action permissions. Threadline should keep one shared authorizer and one shared query-scope seam, not page-specific ad hoc checks.  
  Sources: ActiveAdmin authorization adapter and `scope_collection` [activeadmin.info](https://activeadmin.info/13-authorization-adapter.html), Avo authentication/authorization [docs.avohq.io](https://docs.avohq.io/4.0/authentication.html), [docs.avohq.io](https://docs.avohq.io/3.0/authorization.html), Django admin permissions/queryset hooks [docs.djangoproject.com](https://docs.djangoproject.com/en/dev/ref/contrib/admin/)

- **GitLab / GitHub audit exports:** "export the current view" is the right default mental model, but mature products publish hard caps, retention windows, and API/streaming escape hatches. Threadline's export story should stay "same query, separate capability gate, honest limits."  
  Sources: GitLab current-view CSV export and caps [docs.gitlab.com](https://docs.gitlab.com/administration/compliance/audit_event_reports/), GitHub filtered audit export plus API/streaming alternatives [docs.github.com](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/exporting-audit-log-activity-for-your-enterprise)

- **GitLab audit instrumentation guidance:** not every event belongs in the audit log; events should be attributable to a user/admin persona, and thread-local/block-local queues do not work for async or multi-process flows. That is directly relevant to Threadline's library posture.  
  Sources: GitLab audit development guide [docs.gitlab.com](https://docs.gitlab.com/development/audit_event_guide/)

## 2. Strongest footguns to avoid

- **Process-local or thread-local audit/auth context.** ExAudit's PID-local `track/1` is convenient, but it is exactly the shape that breaks once work crosses async boundaries. GitLab's own docs also call out that local-thread queueing does not support async or multi-process actions. Threadline should keep actor/scope explicit in function inputs, session assigns, and persisted job state.  
  Sources: ExAudit custom tracking [hexdocs.pm](https://hexdocs.pm/ex_audit/readme.html), GitLab audit guide [docs.gitlab.com](https://docs.gitlab.com/development/audit_event_guide/)

- **UI visibility without query scoping.** Backpex `can?/1`, ActiveAdmin `authorized?`, and Django per-model permissions are helpful, but none of them replace collection scoping. For Threadline, hiding export buttons or links is insufficient unless `scope_query_fn` and HTTP export auth enforce the same boundary.

- **Allowing a global/tenantless path without mirrored auth rules.** Ash's `global? true` warning is the cleanest articulation of this. If Threadline lets some screens ignore support scope while others honor it, the support lane is not real.

- **Assuming current user / auth provider / role model.** Avo and AshAdmin both make the host provide this. Threadline should not add a first-party support-role DSL or tenant behavior in v1.21.

- **Over-broad audit surface.** GitLab explicitly warns that events without a clear admin/operator value or clear author are poor audit events. Threadline should avoid turning v1.21 into a generic support workflow or product telemetry expansion.

- **Unbounded exports and silent truncation.** Mature products publish limits. Threadline should document support-export denial by default, admin export posture, caps, and when to move to async/API flows.

- **Separate support tree as a first-class product mode.** The successful pattern is one surface with narrower capabilities and narrower queries. A second Threadline-owned `/audit/support` abstraction would add product surface without solving the core boundary problem.

## 3. Idiomatic Elixir / Phoenix guidance for Threadline

- Keep **auth and tenancy host-owned**: Plug pipelines, `current_user`, org lookup, and tenant semantics belong to the adopter.
- Keep **library seams function-shaped**: `authorize_fn`, `scope_query_fn`, and `export_authorize_fn` are more idiomatic than a Threadline policy DSL.
- Keep **scope explicit and transport-neutral**: the same scope must flow through LiveView, controller, CLI, and async export paths.
- Keep **UI optional and compile-gated**: continue the current `Code.ensure_loaded?` posture so capture-only adopters pay nothing.
- Keep **HTTP export auth separate from LiveView mount auth**: LiveView `on_mount` is not enough; the current `ExportAuthPlug` pattern is correct and should remain authoritative.
- Keep **one query spine**: support scoping should narrow the same underlying query contracts rather than forking a support-only API.
- Prefer **read-only by default, destructive/actions opt-in**: support posture should default to browse-only, export denied unless the host deliberately opts in.
- Emit **telemetry for auth and operator actions** with stable shapes so adopters can monitor boundary decisions.

## 4. How these lessons should push the v1.21 recommendation

v1.21 should stay narrow and evidence-heavy:

1. **Make scoped support a proven lane, not a new subsystem.**
   - Keep one canonical `/audit` surface.
   - Keep one shared `%{assigns: assigns}` authorizer.
   - Keep `scope_query_fn` as the only query-narrowing seam.

2. **Close or remove every unscoped read path before making bigger claims.**
   - The repo's current gap is row-history / as-of proof, not auth macro shape.
   - If that path cannot be scoped cleanly in v1.21, hide or disable it for support-scoped sessions.

3. **Treat exports as a separate privilege.**
   - Support defaults: `exports: false`.
   - Admin override: explicit `export_authorize_fn` or deliberate host policy.
   - Docs should state limits and posture as plainly as GitLab/GitHub do.

4. **Invest in example-app proof and tests, not new UI families.**
   - One Phoenix SaaS example with admin and support personas.
   - Contract tests proving scoped timeline, transaction, actor, row-history decision, and export denial.
   - Staging-honest docs showing exactly what the host must own.

5. **Do not build in v1.21:**
   - Threadline-owned RBAC or tenancy DSL
   - separate support product tree
   - policy engine / admin framework abstraction
   - broad compliance or SIEM expansion

## Threadline-specific conclusion

Threadline's current architecture is already closer to the good Elixir/Phoenix examples than to the bad ones. The main remaining risk is not "missing a framework"; it is **overclaiming support safety before every read/export path is scoped the same way**.

So the v1.21 recommendation should be:

- **Yes** to a scoped support/operator milestone.
- **No** to new auth/tenant abstractions.
- **Yes** to hardening the existing seams with end-to-end proof.
- **No** to broader product surface until that proof is honest.
