# v1.38 Research Summary: Operator UI Page-by-Page IA & Design-System Polish

**Date:** 2026-06-26
**Scope:** Mounted `/audit` operator surface, Phoenix example maintainer tooling, internal design-system guardrails.

## Findings

- The v1.37 operator UI already has the right substrate: private Phoenix function components, `/audit/__stress`, ugly-data fixtures, a design-system ledger, Playwright screenshots, accessibility specs, motion checks, and source contract tests.
- The current `/audit` nav is present, not missing. Desktop/tablet render a sticky left rail; mobile uses a native `details` disclosure labeled `Audit navigation`. The user pain is discoverability, visual hierarchy, and page-level CTA competition.
- PhoenixStorybook is valuable for maintainer component documentation, but it should live in `examples/threadline_phoenix` only. Root `threadline` must keep Phoenix and LiveView optional and avoid adding Storybook to the host-facing dependency graph.
- The strongest page order is Shell/Home/Timeline first, then Coverage, then detail/governance/export surfaces. This matches first-time orientation, primary investigation JTBD, and the highest-risk repeated-readiness/metadata-dump pages.
- Mature UI guidance converges on the same bar: one primary task per page, strong state hierarchy, useful error/empty copy, native controls where possible, APG fidelity for custom controls, and restrained transform/opacity motion.

## Decision Briefs

### PhoenixStorybook vs `/audit/__stress`

**Decision:** Add PhoenixStorybook only to the Phoenix example/dev-maintainer lane; keep `/audit/__stress` as the canonical operator-flow stress harness.

**Why:** PhoenixStorybook provides story navigation, component docs, attrs/variations, and visual-test endpoints. Threadline's stress route already carries operator-specific route/auth/page-state coverage that Storybook would duplicate poorly. Root Storybook would also conflict with optional Phoenix deps and host-app friendliness.

**Rejected:** Add Storybook to root `mix.exs`; replace `/audit/__stress`; publish public component docs now.

**Tests/docs:** Storybook route must be dev/test-only; root `mix compile --no-optional-deps` must keep passing; docs must distinguish Storybook from stress route.

### Page-by-page cleanup order

**Decision:** Shell/Home/Timeline anchor the milestone.

**Why:** Shell and Home determine whether users understand where they are; Timeline is the primary investigation workflow. Improving these first creates patterns that Coverage and governance surfaces can adopt rather than inventing their own local fixes.

**Rejected:** Start with Coverage only; run another broad audit without an implementation order.

### Motion and interaction posture

**Decision:** Keep motion purposeful, token-backed, and restricted to transform/opacity/focus feedback.

**Why:** The operator context rewards clarity under pressure. Motion should communicate state change, continuity, or tactile feedback; it should not decorate, delay, or hide information.

**Tests/docs:** Style contracts should forbid `transition: all`, preserve reduced-motion behavior, and verify press/focus/overlay behavior in browser tests.
