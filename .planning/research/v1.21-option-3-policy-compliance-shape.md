# Threadline v1.21 Option 3 Research: Broader Operator Policy / Compliance Work

**Project:** Threadline
**Milestone context:** v1.21 candidate evaluation
**Option:** 3
**Researched:** 2026-05-24
**Overall confidence:** HIGH on repo-fit assessment, MEDIUM on external market pull beyond current adopters

## Scope

This memo evaluates a broader operator policy/compliance milestone beyond the
already-shipped support-lane proof seams. The question is not whether
compliance-adjacent work is valuable in the abstract. It is whether that work
is the right next wedge for Threadline now, given:

- the current arc in [.planning/MILESTONE-ARC.md](/Users/jon/projects/threadline/.planning/MILESTONE-ARC.md:1)
- the host-owned auth/scope boundary in [guides/operator-surface.md](/Users/jon/projects/threadline/guides/operator-surface.md:1)
- support-matrix honesty in [guides/upgrade-path.md](/Users/jon/projects/threadline/guides/upgrade-path.md:1)
- packaging constraints around the in-tree optional surface
- prior shipped milestones through v1.20 in [.planning/PROJECT.md](/Users/jon/projects/threadline/.planning/PROJECT.md:1)

## 1. Thesis

Option 3 is strategically valid only if it stays narrow: durable policy and
evidence records that strengthen Threadline's audit-of-audit posture without
turning Threadline into a policy engine, RBAC framework, tenancy system, or
compliance platform.

Teams would want this because enterprise buyers, internal security reviewers,
and regulated operators do not just ask "can you capture changes?" They also
ask "what policy was in effect?", "who changed the policy?", "what evidence can
we hand to auditors?", and "can support staff prove they stayed inside the
intended read boundary?" That pressure is real.

But as the next milestone for Threadline, broad policy/compliance work is
weaker than the scoped support/operator proof lane. The repo's own strategic
arc already says the highest-leverage remaining gap is a first-party proven
tenant-safe `/audit` lane, with policy/evidence work following after that.
Choosing Option 3 now risks solving procurement questions before fully proving
the strongest day-2 operator workflow.

Net: Option 3 fits Threadline later and narrowly. It is a poor fit now if
framed broadly.

## 2. Pros

- It sharpens enterprise credibility. v1.20 already added governance state,
  retention history, async exports, and truthful adapter seams. A narrow
  evidence-plane follow-up would make those capabilities easier to defend in
  procurement and internal review.
- It compounds existing work instead of inventing a new product family. Policy
  drift viewing, retention history, export jobs, and actor-owned surface state
  already exist. Extending them into snapshotting and attestation is more
  idiomatic than adding a new operator role model.
- It aligns with library-first Elixir patterns when implemented as plain Ecto
  schemas, append-only records, Mix-task parity, and host-composed callbacks.
  That is consistent with how Threadline already handles exports, retention,
  and scoping.
- It preserves least surprise if it answers concrete operator questions:
  "what policy is deployed?", "what changed?", "when?", "by whom?", "what was
  exported under which rules?" Those questions are adjacent to Threadline's
  core audit value.
- It can improve support-matrix honesty if positioned as evidence for the
  currently proven lanes rather than as a claim to support arbitrary
  compliance frameworks or vendor integrations.
- It creates a cleaner base for later sink-hook or evidence-export work without
  committing to SIEM positioning.

## 3. Cons / Risks

- The biggest risk is platform overreach. The moment Option 3 becomes "policy
  management", "operator permissions", "compliance packs", "legal hold", or
  "immutable archive guarantees", Threadline stops feeling like an audit
  library and starts feeling like an underpowered governance platform.
- It pulls against the host-owned auth/scope boundary if implemented
  incautiously. Threadline currently carries opaque scope and delegates
  narrowing through `scope_query_fn`; it explicitly does not define a role DSL
  or tenancy semantics. Broader compliance work tempts exactly that mistake.
- It can become support-matrix dishonesty in a new form. Today the project is
  careful to claim only named, proven lanes. A broad compliance milestone could
  imply generic enterprise readiness that the repo does not yet prove across
  host topologies, policy models, and storage setups.
- It competes with the stronger next wedge. The repo's own post-v1.20 judgment
  says the remaining practical adopter gap is support-safe scoped operator
  access. Skipping that proof means building evidence around a lane that still
  relies heavily on callback literacy and adopter discipline.
- It adds maintenance surface in the most durable part of the library. Policy
  snapshot formats, evidence schemas, machine-readable reports, and attestation
  literals become public contracts quickly. Those are harder to retract than a
  UI affordance.
- It can distort packaging pressure. Compliance-facing UI/reporting tends to
  want faster iteration, more docs, and more policy-specific screens. That is
  exactly the kind of pressure that could prematurely force a `threadline_web`
  extraction conversation the repo deliberately deferred.
- It risks violating least surprise for Phoenix adopters if page-level access,
  action-level authorization, and export policy start diverging through
  Threadline-owned rules instead of host rules. Phoenix and LiveView expect
  authn/authz to remain app-specific and enforced at Plug + mount + event
  boundaries, not hidden inside a library-owned policy layer.

## 4. Architectural Implications

If chosen, the architecture should stay boring and idiomatic:

- Use append-only Ecto-backed evidence records, not mutable "policy state"
  objects with embedded decision logic.
- Keep policy meaning host-owned. Threadline may snapshot configured policy,
  deployed policy, actor, timestamp, runtime metadata, and attestation result.
  It should not interpret business roles, organization scopes, or approval
  semantics.
- Reuse the existing split:
  - Plug/router boundary for HTTP requests
  - LiveView `on_mount` for mounted surface auth
  - query transformation via `scope_query_fn`
  - Ecto schemas and context modules for persisted evidence
- Favor explicit context modules such as `Threadline.PolicyEvidence`,
  `Threadline.RetentionEvidence`, or `Threadline.ExportEvidence` over one
  giant "compliance" namespace. That matches existing Elixir/Phoenix code shape
  better and reduces conceptual sprawl.
- Prefer Mix-task and API parity for every evidence viewer. Threadline is still
  a library-first project. Anything visible in `/audit/policy/*` should have a
  no-Phoenix equivalent if practical.
- Do not introduce a Threadline-owned authorization matrix for screens. If some
  policy pages are admin-only, keep that as host-controlled `authorize_fn` /
  `export_authorize_fn` behavior or an explicit documented recipe, not a
  library-managed permission system.
- Keep snapshot generation server-side and deterministic. In Ecto terms, this
  wants normal changesets, stable schemas, and reproducible presenter modules,
  not ad hoc serialized blobs.

What should not happen:

- no embedded policy DSL
- no built-in approver workflow
- no vendor-specific compliance report suite
- no claim of immutability stronger than the host storage/runtime can prove
- no cross-tenant semantics baked into Threadline core

## 5. DX / UX Implications

For adopters, narrow evidence-plane work can be good DX if it feels like
"more proof from the same seams" rather than "new subsystem to learn."

Good DX shape:

- one or two new Ecto schemas and public APIs with obvious names
- one or two operator pages adjacent to existing policy/retention/export pages
- stable JSON output from Mix tasks for CI or auditor handoff
- explicit docs that say what is proven, what is inferred, and what remains
  host-owned
- first verification steps that look like current Threadline workflow:
  run a Mix task, compare with `/audit`, inspect attestation rows

Bad DX shape:

- multiple new callback types for policy adjudication
- library-owned role names like `:compliance_admin`
- separate route trees or UI families only for compliance personas
- hidden coupling between auth scope and evidence capture semantics
- broad checklists that imply support for environments the repo does not prove

UX-wise, the least surprising path is incremental:

- extend existing policy drift and retention/export surfaces
- add read-only attestation/snapshot views
- keep support users out of export/evidence download by default unless the host
  opts in deliberately

That matches the current `/audit` posture better than inventing a new "policy
console."

## 6. Recommended Phase Shape If Chosen

If Threadline deliberately chooses Option 3 now despite the arc, the milestone
should be constrained to a policy/evidence plane, not broad compliance.

### Recommended milestone thesis

Make Threadline better at proving what policy and governance posture existed at
the time of operator actions, exports, and retention runs, without introducing
Threadline-owned authorization or compliance workflow logic.

### Suggested phases

1. **Evidence primitives and schemas**
   - Add append-only evidence tables for policy snapshots / attestations.
   - Record actor, capture time, subject (`redaction`, `retention`, `export`,
     maybe `support_scope_check`), summary status, and machine-readable detail.
   - Keep changeset validation strict and schema format stable.

2. **Policy snapshot + attestation APIs**
   - Add public API/context modules that produce and read evidence records.
   - Start with existing Threadline-owned concerns only:
     redaction drift, retention configuration/runtime, export delivery posture.
   - Do not branch into host business-policy interpretation.

3. **Operator and Mix-task evidence views**
   - Add read-only `/audit/policy/*` or adjacent pages plus Mix-task parity.
   - JSON output should be stable enough for CI artifacts or audit packets.
   - Preserve capture-only usefulness where feasible.

4. **Support-lane evidence, but only as proof**
   - If support scope appears here at all, it should be attestation-oriented:
     document and expose that scoped support is host-owned, what Threadline
     enforces, and what it does not.
   - Do not replace the missing first-party support-lane milestone with prose.

5. **Doc-contract and support-matrix lock**
   - Explicitly update docs to say this is evidence-plane work, not a generic
     compliance feature set.
   - Lock negative claims too: no Threadline RBAC, no legal-hold guarantee, no
     generic SIEM support, no immutable-storage promise.

### Phase ordering rationale

- Schema and API first, because evidence formats become the long-lived contract.
- Views second, because UI should present established facts, not invent them.
- Support-lane tie-in late and narrow, because the main support-safe proof still
  deserves its own milestone if the project wants honesty.
- Doc-contract last, but before release, so the public claim surface matches the
  actual proof.

## Recommendation

Do not choose Option 3 as a broad v1.21 milestone. The repo's current arc is
correct: prove the scoped support/operator lane first, then consider a narrow
v1.22-style policy/evidence plane.

Choose Option 3 now only if the scope is explicitly reduced to:

- durable evidence snapshots for Threadline-owned governance features
- read-only proof surfaces and Mix-task parity
- stronger audit-of-audit posture

Reject it if it expands toward:

- Threadline-owned roles or tenancy semantics
- compliance workflow orchestration
- legal hold / immutable archive guarantees
- vendor-report packaging
- a new operator product family
