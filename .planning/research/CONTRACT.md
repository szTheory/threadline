# Domain Research: The 1.x Contract

**Domain:** stability policy for a trigger-backed, SQL-native Elixir audit library
**Researched:** 2026-10-02
**Overall confidence:** MEDIUM-HIGH (precedent for named projects verified via official docs/changelogs; some specifics flagged LOW where search summaries were ambiguous)

## Executive Summary

Threadline's contract is wider than its Elixir functions because capture is generated SQL living in the adopter's own database and migration history, not code the library ships and controls end to end. Hex/semver answers "did the Elixir API change," but it says nothing about whether a 1.1.0 can safely `CREATE OR REPLACE` a trigger function in an adopter's production database, rename a GUC, or add a JSONB key to `data_after`. The research below treats the problem as **two separate promises that must both hold for 1.x**: (1) the ordinary Elixir/Hex semver promise over `lib/`, and (2) a **ONE-WAY, additive-only promise over everything written into the adopter's PostgreSQL instance** — table columns, indexes, function/trigger names, GUC names, and the generated migration shape.

The strongest precedent for the second promise comes from the three projects that share Threadline's trigger-in-adopter-database shape: **Carbonite** (Elixir, versioned migrations via `Carbonite.Migrations.up(N)`, one function call per schema version, explicit SemVer policy document), **Logidze** (Rails, idempotent `CREATE OR REPLACE FUNCTION` regeneration via `--update`, safe to rerun any time because the trigger body is pure and stateless), and **pgaudit** (C extension, hard major-version lockstep with PostgreSQL itself, no in-place schema to version because it has none). Threadline already independently arrived at a Carbonite/Logidze-shaped answer without naming it: `mix threadline.gen.triggers` is idempotent `CREATE OR REPLACE FUNCTION`, 0.11.0 proved a real cross-minor schema-shape change (primary-key resolution) shipped through "regenerate your triggers, then migrate," and `guides/upgrade-path.md` already carries a per-minor action table. What v1.45 needs to add is not new tooling — it is a **named, enforced policy** that says which of these moves are allowed inside a 1.x minor versus only at a major, plus a test for each clause instead of prose alone.

Rails `audited`'s `rails generate audited:upgrade` and Ash's "6 months of critical fixes on the previous major" are the cleanest precedents for the 0.x-after-1.0 support story: Threadline should commit to a fixed backport window on 0.12.x (its final 0.x line) measured in months, not "until we feel like it," and should keep the existing `rails generate audited:upgrade`-equivalent (`mix threadline.gen.triggers` + the upgrade guide) as the one and only upgrade mechanism rather than inventing a second one. Elixir's own three-step deprecation (soft → warning → removal no earlier than a major) and Django's `RemovedInDjangoNN` naming are the cleanest precedent for Elixir-API deprecations; Threadline already uses this shape informally (the v1.44/v1.45 overlapping-entry-point consolidation) and should formalize it as a `@moduledoc` convention plus a changelog-anchor test. For the operator surface, Oban Web and Phoenix LiveDashboard's router-macro pattern is the exact right shape and Threadline's `guides/integration-contracts.md` already states it in prose ("the router macro and mount options are stable... HTML/CSS/routes inside are not") — it needs one new static contract test, not a rewrite.

The single highest-risk area is the **JSONB shapes of `data_after` and `changed_fields`**: these are driven by `pg_catalog`/`row_to_json` output, which already changes behavior silently across PostgreSQL versions (e.g., numeric formatting, timestamp precision) in ways Threadline does not control and cannot promise against. This must be documented as a **narrower promise** (column exists, is this Elixir type, keys are the audited table's own column names) rather than a byte-stable JSON promise, and flagged ONE-WAY in the opposite direction: once documented, narrowing it further is a breaking change.

## Key Findings

**Stability policy:** adopt a two-tier STABILITY.md: ordinary Elixir/Hex semver for `lib/` plus a **separate, explicitly-named "Database Contract"** for everything SQL that ships into the adopter's own instance, with ONE-WAY column-addition-only promises enforced by a schema-snapshot test.

**Architecture:** the real contract boundary is not the Elixir module tree, it's **what Threadline writes into someone else's `pg_catalog`** — tables, indexes, functions, triggers, GUCs — versus what stays entirely inside `lib/threadline.beam` and can move freely.

**Critical pitfall:** treating `data_after`/`changed_fields` JSONB *content* as a byte-stable promise. PostgreSQL's own `row_to_json`/`to_jsonb` formatting (numeric precision, timestamp text, NaN/Infinity handling) is itself not stable across PG major versions, so Threadline cannot out-promise its own storage engine. The 1.0 promise must be scoped to *column existence + Elixir-side type + key-naming rule*, not exact serialized bytes.

**Recommendation for Threadline's STABILITY policy** — a single `guides/stability.md` page with two sections and a short `@moduledoc` convention, not a sprawling document:

1. **Elixir API tier** (ordinary Hex semver): every public, non-`@moduledoc false` module/function with a `@spec`+`@doc` is covered. Follow Elixir's own three-step model, compressed to two named states because Threadline does not have Elixir's 6-month minor cadence:
   - `@deprecated "use X/Y instead"` attribute + a CHANGELOG `### Deprecated` entry the same release it is deprecated (this *is* the enforceable marker — Elixir's compiler already turns this into a warning for free, no custom tooling needed).
   - Removal only at the next **major** (2.0), never in a 1.x minor, mirroring Elixir/Ash/Django's "majors only" rule. This is the direct fix for the `history/3`/`row_history/4` et al. overlap: deprecate the redundant entry points now, remove them at 2.0, not at 1.1 or 1.2.
   - Anything under a module tagged `@moduledoc false` or inside `lib/mix/tasks/` private helpers is **not covered**, mirroring Ecto's `Mix.Ecto` carve-out.
   - A convention line added to every public module's `@moduledoc`: `> **Stability:** public, SemVer-covered since 1.0.` or `> **Stability:** experimental — no compatibility guarantee until promoted.` (Elixir/Ecto precedent: explicit experimental labeling, no guarantee until stabilized.) Used sparingly — Threadline should enter 1.0 with **zero** experimental-labeled public modules if possible; anything not ready should stay `@moduledoc false` instead, per the v1.45 "hide internal helpers" scope line.

2. **Database Contract tier** (separate from Elixir semver, ONE-WAY by construction — see §2–3): column/index/function/GUC *names* are additive-only for the life of 1.x; a 1.x minor may add a column, index, finding code, or telemetry event, and may never remove or rename one. Removing or renaming anything in this tier is a major-version event requiring the Carbonite/Logidze-style versioned-migration mechanism Threadline already has in `mix threadline.gen.triggers` + the upgrade guide, generalized under a numbered scheme if/when 2.0 needs it (not needed for 1.0 itself).

**ONE-WAY flag:** Both tiers are stated above as *commitments made at 1.0.0* — once published, narrowing either promise (e.g., deciding a column is no longer guaranteed, or deciding deprecation windows can be shorter) is itself a breaking change to the policy and must ship as a major-version change to `guides/stability.md` with its own CHANGELOG entry.

**How 1.x schema changes ship today:** through `mix threadline.gen.triggers` (idempotent `CREATE OR REPLACE FUNCTION`) plus `mix threadline.gen.row_history_index`, both Mix-task generators that a host runs and then migrates — this **is** the "additive migration generated by a mix task" mechanism the question asks whether exists. It exists and shipped a real cross-minor change in 0.11.0 (primary-key resolution). `guides/upgrade-path.md` and `guides/upgrading-to-0.11.md` are the guide; there is no single `mix threadline.upgrade` meta-task, and the v1.44 research explicitly **decided against** building `mix threadline.gen.backfill` because the upgrade guide's hand-rolled SQL was judged right-sized (`PROJECT.md`, "Decided not to build" list). Recommendation: keep this pattern for 1.x — it already matches Carbonite's per-version migration call and Logidze's idempotent regenerate-on-demand model. Do not build a generic schema-migration DSL for 1.0; that is new scope the milestone guide rules out.

**Carbonite vs. Logidze on schema evolution across majors:**
- **Carbonite** versions its schema explicitly: each release that changes schema ships a documented integer version, and the host calls `Carbonite.Migrations.up(N)` in a normal Ecto migration — an explicit, numbered, additive-by-construction mechanism. [Carbonite docs](https://hexdocs.pm/carbonite/Carbonite.Migrations.html) — HIGH confidence (official docs).
- **Logidze** treats its trigger function as idempotent and stateless with respect to schema changes: `rails generate logidze:install --update` simply regenerates the `CREATE OR REPLACE FUNCTION` body, and later versions moved column-filtering logic *into* the trigger function itself specifically so that host schema changes (adding/removing tracked columns) don't require regenerating anything. [Logidze README](https://github.com/palkan/logidze) — MEDIUM-HIGH.

Threadline's `gen.triggers` is closer to Logidze's model (regenerate, `CREATE OR REPLACE`, safe to rerun) than Carbonite's numbered-migration model, and that's the right fit given Threadline's per-table trigger-function generation. The gap versus Logidze: Threadline's regeneration is not yet promised to be a true no-op across every 1.x minor in all cases (0.11.0 required a real regeneration for a real behavior change) — that's acceptable *between* majors with a documented action, but 1.x must promise it won't ask for *silent* behavior changes without a changelog + guide entry, which is exactly today's `guides/upgrade-path.md` pattern formalized as policy.

### 3. Generated code as API

What 1.x promises about regenerated triggers:
- **Compatibility with 0.11/0.12-generated triggers:** 0.11.0 proved the precedent — "0.10.x triggers keep working" (`PROJECT.md`, v1.42 summary) even after 0.11.0 shipped new capture logic, because old triggers simply didn't get the new behavior until regenerated. The 1.x promise should be the same shape stated forward: **a trigger generated by any 1.x minor keeps functioning (keeps capturing correctly for the capabilities it was generated with) under every later 1.x minor without forced regeneration**, and a 1.x minor **may** ask for an *opt-in* regeneration to gain new capability (e.g. a new finding code becoming detectable), but never a *mandatory* regeneration to keep existing capture correct. A mandatory regeneration (like 0.11.0's) is a 2.0-only event under this policy, formalizing what the project has already done once at a de facto major-equivalent moment.
- **"Regenerate triggers" in a minor:** today, yes — 0.11.0 is a minor release, and it required regeneration (`guides/upgrade-path.md:118`). This is the clearest honesty gap at 1.0: either (a) commit that post-1.0, a *mandatory* trigger regeneration is reserved for 2.0 (recommended — matches how Elixir/Ecto reserve breaking removals for majors), or (b) explicitly carve out trigger regeneration as a *named exception* class allowed in a minor only for a security fix or a correctness bug (analogous to Elixir's "exceptions are allowed only for security issues" language already present almost verbatim in `guides/upgrade-path.md:180`). **Recommendation: adopt (b)** — Threadline already states this exact exception shape for surface-only deprecations; extend the same three-way exception list (security issue / upstream hard incompatibility / undocumented internals) explicitly to cover "mandatory trigger regeneration," since a correctness bug in generated SQL (like 0.11.0's) is exactly a security/correctness exception, not routine evolution.
- **Enforcement:** Phase 224's `gen.triggers` rerun property (a DB-backed property proving the regenerate-chain rolls back to a clean `pg_proc`) already proves *idempotency*. It does not yet prove *backward function* — that a trigger generated under 0.12 still captures correctly when the host upgrades the `threadline` dependency to a later 1.x without regenerating. **Needed:** an integration test that generates triggers at a pinned historical commit/version (or a frozen SQL fixture captured from 0.12.0), installs them, then upgrades library code only (no `mix threadline.gen.triggers` rerun) and proves capture keeps working under the newer code.

### 5. The operator surface (parked, but the contract still needs declaring now)

Precedent is unambiguous across all three comparable Elixir dashboards:

- **Oban Web** (`Oban.Web.Router`) — the router macro (`oban_dashboard/2`) and its option keys are the stable surface; the mounted dashboard's internal routes/markup are implementation detail that can change between releases without being a breaking-change event. [Oban.Web.Router docs](https://hexdocs.pm/oban_web/Oban.Web.Router.html) — HIGH.
- **Phoenix LiveDashboard** (`Phoenix.LiveDashboard.Router`) — same shape: `live_dashboard/2` macro + documented options are the contract; internal pages are not individually versioned. [LiveDashboard router docs](https://hexdocs.pm/phoenix_live_dashboard/Phoenix.LiveDashboard.Router.html) — HIGH.
- **ErrorTracker** (`ErrorTracker.Web.Router`) — `error_tracker_dashboard/1` macro + `on_mount` option is the stable seam; the LiveView screens inside are not. [ErrorTracker web router](https://hexdocs.pm/error_tracker/ErrorTracker.Web.Router.html) — MEDIUM-HIGH.

Threadline's own `guides/integration-contracts.md` already states this exact split in prose for `threadline_operator_surface/2` (§ "Operator-surface composition via `authorize_fn` and `export_authorize_fn`", § "Secure-by-default mount boundary", § "Shared authorization vocabulary"). **Recommendation for 1.0:** declare explicitly, in the stability guide, that:
- `threadline_operator_surface/2`'s macro name, required/optional option keys (`repo`, `authorize_fn`, `scope_query_fn`, `evidence_authorize_fn`, `export_authorize_fn`), the `authorize_fn` result vocabulary (`:ok` / `true` / `{:ok, scope}` / anything-else-denies / raise-denies), and the documented mounted route *paths* (since hosts may put CSP/proxy rules in front of them, per `guides/upgrade-path.md`'s 0.10.0 bullet about `/theme` and `/rows/:table/:record_id`) are **stable, SemVer-covered**.
- Everything rendered inside the mount — HTML structure, CSS classes, LiveView internal module names, component boundaries — is **not API**, same as Oban Web/LiveDashboard/ErrorTracker, and explicitly **not** covered even though it currently lives in-tree. This matches the standing posture that operator-UI design work is parked until after 1.0.0 (`PROJECT.md`, `MILESTONE-ARC.md`), so it costs nothing today and prevents a future UI-polish milestone from accidentally being read as a breaking-change-free zone when it touches a documented route.

Enforcement: `test/threadline/public_surface_contract_test.exs` already has module-visibility and doc-reference scaffolding (`@module_owner_tags`, `@reference_owner_tags`) that is the natural home for a new assertion pinning the macro's option-key list and the documented route list; `test/threadline/operator_surface/surface_header_csp_test.exs` already touches CSP/route surface and is the natural sibling for a route-literal pin.

### 6. 0.x support story after 1.0, and the 0.11/0.12 → 1.0 upgrade path

Precedent: Ash commits to **a minimum of 6 months of critical bug fixes and security upgrades** on the prior major after a new major ships ([Ash upgrade guide](https://hexdocs.pm/ash/upgrading-to-3-0.html)) — the cleanest, most citable number found. Rails `audited`'s compatibility-matrix-plus-generator model (`rails generate audited:upgrade`) is the cleanest precedent for *how* the upgrade itself should be mechanized: one named command, safe to rerun, documented in the gem's own README rather than a separate wiki.

**Recommendation:**
- **0.12.x security-fix window:** commit to security and correctness-critical backports on `0.12.x` for a fixed window stated in months (recommend 6 months post-1.0.0, matching Ash's stated number and giving slow-moving adopters a real runway) rather than an open-ended "as long as someone asks" promise, which is unenforceable and already a known support-engineer pain point in audit-library contexts.
- **0.11/0.12 → 1.0 upgrade path:** this is **not expected to require a new trigger regeneration** if 1.0 ships no schema-shape change beyond what 0.12.0 already has (confirm this holds once the v1.45 "history/3 limit default" and entry-point-consolidation decisions land — if either touches generated SQL, the upgrade-path guide must say so explicitly, same as the 0.11.0 precedent). The upgrade guide entry for `0.12.x → 1.0.0` should follow the exact table shape already established in `guides/upgrade-path.md`'s "At a glance, per minor" table (`Bump | Breaking? | Migration required | Config touch | Reassurance`), extended with one new row, keeping the existing per-minor doc-contract test pattern (`test/threadline/upgrade_path_doc_contract_test.exs`) rather than inventing a new doc format for the 1.0 boundary.
- **Deprecated-entry-point removal timing:** any Elixir-API consolidation decided in v1.45 (e.g. deprecating `row_history/4` in favor of a single entry point) ships as `@deprecated` + CHANGELOG `### Deprecated` in 1.0.0 itself, with actual removal reserved for 2.0 — giving the full 1.x line as the overlap window, which is more generous than Elixir's own 3-minor minimum and appropriate for a library whose adopters upgrade less frequently than the language itself.
