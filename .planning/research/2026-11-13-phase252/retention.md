## Existing Retention job: preview, confirmation, and reconnect safety

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Ephemeral server-side dry-run preview followed by the existing typed confirmation | Reuses `Retention.purge/1`'s exact read-only count predicates for changes and optional empty transactions; no new public API, route, config, schema, lock, dependency, or retention history semantics; preserves existing global scope and persisted run lifecycle | Counts are an estimate at preview time and may differ when the asynchronous run starts; global exact counts add database read work; preview failures must not fall through to confirmation | `retention_history_live.ex`, its LiveView tests, current journey/source fixtures, and one route-state browser case -- Risk: stale estimates, global-count disclosure, full-count query load | Rec if a clearly labeled point-in-time estimate is sufficient |
| Persist preview metadata and bind the request to a recorded cutoff | Leaves a durable preview-to-run reference and records which policy boundary the operator reviewed | Requires retention-run schema/migration and Pruner changes; row contents can still change between preview and worker execution, so a cutoff alone cannot guarantee the shown counts; expands upgrade and operational failure surfaces | LiveView, `Retention`, `Pruner`, `RetentionRun`, migration and compatibility tests -- Risk: migration/lock semantics and false confidence in preview/result equality | Rec only if future operators require durable preview lineage |

**Rationale:** The Phase 252 requirement has one real missing capability: `lib/threadline/operator_surface/live/retention_history_live.ex` goes directly to a global type-to-confirm modal and explicitly says the history records no preview count or cutoff. The backend already implements a non-mutating `dry_run: true` count in `lib/threadline/retention.ex`; `test/threadline/retention_test.exs` and `test/threadline/retention/cutoff_property_test.exs` own that predicate and no-delete boundary. Keep the preview transient, show separate estimated AuditChange and optional AuditTransaction counts with the preview time and existing global-schema scope, call it an estimate that can change, and refuse confirmation if preview/auth/read fails. Preserve the existing event-time authorization, server-side constant-time typed confirmation, audited operator request, and actual persisted queued/running/completed/failed outcomes in `RetentionRun` (one aggregate `deleted_count`, with no stored cutoff or per-type split); preview is not a run and should not be presented as an Export-style queued/accepted/completed status. The LiveView tests already cover cancel, forged confirmation, auth revocation, active-run rejection, audit failure and persisted runs. Shared `script.ex` and reconnect CSS already disable mutations while disconnected and wait for a fresh persisted revision; export route-state tests exercise that guard, but retention's browser owner only proves confirmation focus/cancel. Add the retention-specific offline-submit/reconnect no-replay case to `examples/threadline_phoenix/e2e/tests/operator-route-states.spec.ts`. Preserve `route.retention` and `job.operator-retention-operations`; update `examples/threadline_phoenix/e2e/support/operator-journey-inventory.json`, `test/fixtures/operator_surface/route-inventory.json`, and changed anchors in `test/fixtures/operator_surface/source-surface-checklist.json`; `test/threadline/operator_surface/rendered_output_contract_test.exs` has no direct RetentionHistoryLive assertion, so retain the mounted LiveView test as the behavior owner. The screen already uses production `UI.Page`, `UI.Data`, `UI.Display`, and `UI.Overlay`; catalog additions should project this state through those components and link to the mounted route proof, since PhoenixStorybook rendering cannot prove authorization, persistence, or reconnect. The bounded first tracer is an ExUnit preview-with-zero-writes / failed-preview / cancel / confirm-and-persist sequence, plus that one real-route offline/reconnect case. Keep the dry-run and permission/persisted-outcome contracts recurring; keep matched before/after captures local to the changed scene, using the same seeded ordinary RetentionRuns lifecycle, `/audit/policy/retention`, open confirmation, browser/served assets, clock, theme, and viewport (desktop dark and narrow light are a useful pair); preserve existing screenshots and do not treat a static story as that proof. This is source-only research: no app, database, test, or browser was run. The recommendation follows the repo's capture/semantics/operations boundary and Ecto's separation of query/persistence/orchestration, plus Phoenix LiveView's guidance to reauthorize mutation events and its remount-on-reconnect behavior ([LiveView security model](https://phoenix-live-view.hexdocs.pm/security-model.html), [LiveView 1.1 lifecycle](https://phoenix-live-view.hexdocs.pm/1.1.33/Phoenix.LiveView.html)); the preview must remain an estimate because the asynchronous worker runs against later database state.
