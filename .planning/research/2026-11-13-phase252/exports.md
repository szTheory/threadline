## Existing export flow

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Keep the current scoped immediate downloads and unscoped actor-owned queue | Already preserves committed Timeline filters and host `scope_query_fn` for CSV/JSON/NDJSON; separate `export_authorize_fn` protects HTTP exports; queued jobs have truthful pending/running/completed/failed/expired/unavailable labels, owner checks, recovery links and completion-only download | Scoped users cannot queue a background job, by design; queue acceptance is a transient “Export queued” flash while the stored job remains `pending` | Reuse `TimelineLive`/`Filters`, `ExportStatusLive`/`Components`, `ExportController`, `Presentation`; no new dependency/API/schema — Risk: visual changes could blur immediate downloads and queued jobs | Rec if retaining the shipped route, scope and actor-ownership contracts |
| Persist scope with background jobs and apply it in the worker and download authorization | Long-running exports could retain a tenant-scoped query and status lifecycle | Requires a safe serializable scope contract, scope revalidation/revocation semantics, schema/worker/controller changes and new security proofs; opaque host scope may contain data that must not be persisted | Export-job schema, queue adapters, worker, auth callback, download controller, migrations and compatibility tests — Risk: stale or overbroad authorization and durable host-specific data | Rec only if scoped exports must be asynchronous and a host-owned scope persistence/recheck contract is accepted |

**Rationale:** Current source already meets the export behavior in Phase 252: `TimelineLive.Filters.export_actions/1` carries the committed query and exposes immediate formats, while queue handlers refuse either operator or export scope instead of serializing it; `ExportController.dispatch/3` validates filters and calls `ExportReads` with `surface: :export` plus the host scope transform. `ExportAuthPlug` and `Auth.assign_exports_enabled/2` apply export-specific authorization; the completed download also checks current request authorization, actor ownership, `status == "completed"`, file availability and expiry. This follows Phoenix LiveView's [security guidance](https://phoenix-live-view.hexdocs.pm/security-model.html) to authorize mounted views and mutations, and uses Plug's [file and chunked response APIs](https://plug.hexdocs.pm/Plug.Conn.html) for controller-owned delivery. Root owners cover scoped query results, fail-closed missing scope transforms, queue failure, forbidden scope-to-background escalation, actor/status/expiry download boundaries; the example browser owners cover accepted queue → completed download → committed-search return, seeded lifecycle states, denial and reconnect replay protection. Reuse `route.exports`, `seam.exports.changes-csv/json/ndjson`, `seam.exports.download-job_id`, `job.operator-export-status`, `job.operator-export-response`, `scenario.acme-4521-investigation`, and `scenario.state-export-failed` / `fixture.state-export-failed.1`; keep the actual route and persistence proofs in `test/threadline/operator_surface/{live/export_status_live_test.exs,live/timeline_live_test.exs,controllers/export_controller_test.exs,export_auth_plug_test.exs}` and `examples/threadline_phoenix/e2e/tests/{operator-route-states.spec.ts,operator-earned-flows.spec.ts}`. A useful before/after baseline is the ordinary #4521 filtered source query plus the real queued/completed/download return, paired with the named failed-job stress state; static Storybook can show the production job component states but cannot replace those routes. The reference app does not combine organization-scoped access with export permission (support is denied exports), so mounted host proof for that exact role combination is absent; root scoped HTTP tests do prove filtering. Confidence is high on current source boundaries, but this is read-only research, not a fresh runtime receipt. No new route, public API, configuration key, query name, schema status, dependency, registry, or Storybook framework is indicated; keep queue acceptance as the existing confirmation rather than inventing a persisted “accepted” status. Only reopen the architect-level scope question if Phase 252 is intended to promise asynchronous tenant-scoped jobs.
