## Preview target seam

The Retention preview must resolve the worker's live target, not assume the LiveView mount target is the worker target. `Threadline.OperatorSurface.Auth.on_mount/4` assigns the mount option `:repo` to `threadline_repo` ([auth.ex](../../../lib/threadline/operator_surface/auth.ex#L79)); `RetentionHistoryLive.resolve_repo/1` prefers that socket value and otherwise falls back to the first app repo ([retention_history_live.ex](../../../lib/threadline/operator_surface/live/retention_history_live.ex#L558)). In contrast, `Threadline.Application.retention_child/0` starts the singleton pruner with the first configured repo and passes only `repo`, interval, and sleep options ([application.ex](../../../lib/threadline/application.ex#L56)); `Pruner.init/1` captures that repo, `StorageSchema.get(opts)` and `sleep_ms` in worker state ([pruner.ex](../../../lib/threadline/retention/pruner.ex#L56)). Thus a mount-level repo override can point at Repo A while `Pruner.trigger/0` schedules the worker against Repo B. The same split exists for schema if application storage-schema config changes after the worker starts: the LiveView calls `StorageSchema.get()` at use time, while the worker keeps its initialized schema. The current confirmation also writes the `AuditAction` using the socket repo/schema before triggering the worker ([retention_history_live.ex](../../../lib/threadline/operator_surface/live/retention_history_live.ex#L509)), so target mismatch can split the audit request, preview, visible run history, and deletion across stores.

**Recommendation:** coordinate through the existing, undocumented `Threadline.Retention.Pruner` module instead of reading GenServer internals with `:sys.get_state/2`. Add `@doc false` internal `target_snapshot/0` and `trigger_if_target/1` calls. The pruner handles the snapshot request and returns only `%{pid: self(), repo: ..., storage_schema: ..., sleep_ms: ...}` from its initialized state. `trigger_if_target/1` calls that exact PID directly; its GenServer handler compares the PID and those three target fields with its live state, and only then calls the existing `accept_or_coalesce/1`. A dead/stale PID or any mismatch returns an error without resolving the registered name again. Keep `trigger/0` and its existing behavior unchanged for every current caller. `@doc false` functions are technically BEAM-exported, but this `@moduledoc false` module has no supported public target-inspection contract; the documented API and config remain unchanged.

In `RetentionHistoryLive`, resolve a snapshot per preview, require its repo/schema to match the effective mounted target, and pass the snapshot repo/schema/sleep to `Retention.purge/1` with `dry_run: true`; the existing domain call continues to resolve the current retention policy. After counting, resolve the current snapshot again by name and compare all four fields, including PID, before assigning visible preview counts. Save the original snapshot server-side with the successful preview. On confirmation, reauthorize first, require both that the worker snapshot still matches and that the socket repo/current storage schema still match it, then clear/refuse a stale preview before auditing. Write the audit request to the snapshot repo/schema, then call `trigger_if_target/1` on the original PID so a restart cannot route the accepted request to a replacement worker. This is a smaller, explicit internal protocol than coupling LiveView behavior to the pruner's state layout, and it closes the name-lookup restart race. It adds no domain operation, route, config, serialized scope, or persisted preview. A process exit after the audit write but before guarded acceptance can still leave an audited request without a run, as the current audit-before-trigger ordering already permits; the guarded call will never retarget that request to a replacement worker.

**Test consequence:** add focused protocol and LiveView cases. A stale snapshot from a restarted pruner must make `trigger_if_target/1` return a target-changed error and create no run. In `retention_history_live_test.exs`, a mount repo/schema mismatch must show no preview; restarting the worker after preview but before submit must clear/refuse the stale preview and produce no `AuditAction` or `RetentionRun`. A matching repo/schema preview must use the snapshot values, show counts only if the same PID still serves that target afterward, and preserve the existing no-write assertions. Keep `retention_test.exs` as the owner of backend cutoff/count semantics; use the existing test database without starting another PostgreSQL service.
