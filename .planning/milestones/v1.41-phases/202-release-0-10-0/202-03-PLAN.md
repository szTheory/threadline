<objective>
Give the 0.10.0 release a changelog an adopter can actually read, and make the split that
keeps it readable structural rather than remembered.

Purpose: release-please emits roughly three hundred bullets since the last release, forty of
which trip the archive contract's planning-vocabulary regexes. Merging the release PR as-is
would ship internal planning language to hex.pm and turn the suite red on the release commit.
History is immutable, so policing commit messages is not available — the prevention has to be
structural. D-11 splits ownership by file; D-12 through D-14 write the entry itself; D-15 and
D-16 re-scope the upgrade guide so it tells the truth about the storage-schema default under
D-01 and still names the four adopter actions that remain.

Output: a bot-owned generated changelog, a human-owned shipped changelog with a real 0.10.0
entry, a contract test that fails if the shape regresses, and a corrected upgrade path.
</objective>

## Plan decision: history stays put

`CHANGELOG.md` already contains released entries whose bodies were bot-generated. Those are
not moved. History is immutable and the links in them are what adopters have followed for two
years. `CHANGELOG-GENERATED.md` is seeded empty-but-headed and begins accumulating at 0.10.0;
its header says so. This is the minimum change that makes the ownership split real going
forward without rewriting published history.

    Point release-please's `changelog-path` at a new `CHANGELOG-GENERATED.md` and make

    **What this buys:** the generated commit list stops being the shipped changelog, so the
    forty subjects carrying planning vocabulary never reach hex.pm and never turn the archive

    on commit-message discipline over history that cannot be rewritten.

    read would swap meaning between versions if the split were undone after publishing.

    **Alternative considered and rejected:** keeping one file and filtering generated subjects.
    Rejected because it requires the bot and the contract to agree on a vocabulary forever, and
    because history is immutable so a single bad subject reappears on every regeneration.
  </decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| release-please (write access to tracked files) → shipped documentation | an automation writes prose that reaches adopters |

| changelog claims → adopter upgrade decisions | a wrong "no action required" line causes a silent production break |
