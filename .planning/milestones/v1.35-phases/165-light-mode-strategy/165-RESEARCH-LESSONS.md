# Phase 165 — Research Lane B: Cross-Ecosystem Dark/Light Lessons

**Researched:** 2026-06-12

## 1. Case Studies — Default Posture and Architecture

### GitHub (Primer)

- **Default:** Light. Theme picker lives in Settings → Appearance. [CITED: docs.github.com]
- **Selection mechanism:** Two modes — a single fixed theme, OR "sync with system" where the user picks *separate day and night themes* and the OS `prefers-color-scheme` decides which applies. Also ships high-contrast and colorblind variants. [CITED: docs.github.com — Managing your theme settings](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-user-account-settings/managing-your-theme-settings)
- **Token architecture:** Three-layer hierarchy — **base** scale tokens (e.g. `color-scale-pink-5`, "should never be used directly in code or design"), **functional** tokens (`fgColor-muted`, `borderColor-default` — the workhorses), and **component/pattern** tokens. Functional tokens automatically resolve to different values per color mode; the *names* never change. Nine themes ship from one token system. [CITED: primer.style — Color usage](https://primer.style/product/getting-started/foundations/color-usage/), [Primer UI color system](https://primer.style/foundations/color/overview/)
- **Key structural trick:** the light and dark neutral scales are *inverted relative to each other* (light starts at white, dark starts at near-black), so most functional tokens work in both modes **without per-mode overrides**. [CITED: primer.style]
- **Praise/complaints:** The token abstraction is widely cited as the reason GitHub could ship nine themes (incl. accessibility themes) without per-page rework; GitHub built dedicated color tooling to keep theme creation tractable. [CITED: github.blog — Accelerating GitHub theme creation](https://github.blog/news-insights/product-news/accelerating-github-theme-creation-with-color-tooling/), [Primer color system inclusivity](https://github.blog/engineering/user-experience/unlocking-inclusive-design-how-primers-color-system-is-making-github-com-more-inclusive/)

### Grafana — the cautionary dark-default tale

- **Default:** Dark, since the project's early days. Light theme exists; theme is settable at **four levels** (server → org → team → user), lowest level wins. "System" option added later. [CITED: grafana.com — Organization preferences](https://grafana.com/docs/grafana/latest/administration/organization-preferences/)
- **What went wrong:**
  - Organizations optimize dashboards for dark; the light theme "does not look very good" — one org literally **patched Grafana's source to remove the light option from the dropdown** because their content was unviewable in light. [CITED: community.grafana.com thread #19241](https://community.grafana.com/t/hiding-removing-the-light-ui-theme-from-user-interface/19241)
  - "System" theme + plugins not built for both modes ⇒ dark-on-dark unreadable elements (Grafana OnCall). Third-party surfaces don't automatically follow the host's theme contract. [CITED: github.com/grafana/oncall#3188](https://github.com/grafana/oncall/issues/3188)
  - Long tail of theme-persistence bugs (selection saved but not applied, theme stuck on light). [CITED: grafana#76224](https://github.com/grafana/grafana/issues/76224), [community thread](https://community.grafana.com/t/grafana-ui-theme-stuck-on-light/40541)
- **Lesson:** A second mode you don't *design and test* becomes a liability users ask you to remove. User-authored content (dashboards ≈ Threadline's audit data visualizations) gets tuned to the default mode and breaks in the other.

### Linear

- **Default:** Dark-leaning power-user app; both modes plus system preference offered in Settings, applied instantly. [CITED: linear.app/docs — Preferences](https://linear.app/docs/account-preferences)
- **Architecture:** The 2023+ redesign moved theming from ~98 hand-set variables per theme to **LCH-based generation from three inputs: base color, accent color, contrast**. Light and dark are generated by the *same* system; a `contrast` variable auto-generates high-contrast variants. They explicitly darken text/icons in light mode and lighten them in dark mode — same role, different tuned values. [CITED: linear.app — How we redesigned the Linear UI, part II](https://linear.app/now/how-we-redesigned-the-linear-ui)
- **Lesson:** Perceptually-uniform generation (LCH) beats hand-picking 100 hexes twice. Even at Linear's polish level, light is *derived from the same semantic system*, never a palette inversion.

### Datadog

- **Default:** Light; dark mode introduced later as a first-class feature (avatar menu + `Ctrl+Opt+D` shortcut + "System" option). [CITED: datadoghq.com — Introducing dark mode](https://www.datadoghq.com/blog/introducing-datadog-darkmode/)
- **Notable mechanism:** **Shared dashboards carry a default mode chosen by the author, and viewers can override** — per-artifact theme defaults for embedded/public surfaces. [CITED: docs.datadoghq.com — Shared dashboards](https://docs.datadoghq.com/dashboards/sharing/shared_dashboards/)
- **Chart discipline:** Datadog maintains explicit guidance for picking widget colors that survive both modes, and retuned sidebar contrast "in both light and dark mode" for low-vision/photosensitive users. [CITED: docs.datadoghq.com — Widget colors](https://docs.datadoghq.com/dashboards/guide/widget_colors/), [navigation redesign](https://www.datadoghq.com/blog/datadog-navigation-redesign/)
- **Lesson:** Data-viz color ramps are a separate theming problem from chrome; treat them as their own token lane.

### Stripe Dashboard

- **Default:** Light. **No native web-dashboard dark mode for years** — demand visible as browser extensions and userstyles (StripeDark, userstyles.world, Firefox add-ons), plus an open thread on Stripe Insiders. Dark shipped first on iOS as a proof of concept while the dashboard's theming architecture was rebuilt. [CITED: github.com/BlinkStrike/StripeDark](https://github.com/BlinkStrike/StripeDark), [insiders.stripe.dev thread](https://insiders.stripe.dev/t/dashboard-dark-mode/2473), [mattstromawn.com — Stripe Dashboard](https://mattstromawn.com/projects/stripe-dashboard/)
- **The canonical color lesson:** Stripe's brand hues couldn't meet 4.5:1 on white; naive darkening produced "dark and muddy" colors. They moved to the perceptually-uniform **CIELAB** space and built tooling to normalize lightness curves across hues — colors stay vibrant *and* guarantee contrast on white and on the lightest tinted background of every hue. They later auto-generate color tokens from the WCAG contrast algorithm. [CITED: stripe.com/blog — Designing accessible color systems](https://stripe.com/blog/accessible-color-systems)
- **Lesson (two-sided):** (a) Hue retuning per background is mandatory and is a *perceptual* problem, not an RGB arithmetic problem. (b) Deferring the second mode for years creates an ecosystem of hacky third-party recolors of your product — the worst possible brand presentation.

### VS Code

- **Default:** Dark ("Dark Modern"). Thousands of community themes.
- **Architecture at scale:** Two distinct layers — **workbench colors** (UI chrome: hundreds of named color slots like `statusBar.background`, with derivation fallbacks when a theme omits a key) and **token colors** (syntax: TextMate scopes + **semantic tokens** from language servers, where semantic rules override textual ones). Themes are *data* (JSON), not code; `"include"` lets themes extend a base. [CITED: code.visualstudio.com — Color Theme guide](https://code.visualstudio.com/api/extension-guides/color-theme), [Semantic Highlight Guide](https://code.visualstudio.com/api/language-extensions/semantic-highlight-guide)
- **Lesson:** Exhaustive named slots + sensible fallback derivation is what makes third-party theming safe — a theme that defines 30 of 500 keys still renders coherently. The cost is a large, permanent API surface; every new UI element must be assigned a slot. For a library UI like Threadline, the transferable subset is: *theme = data resolved through named roles, with fallbacks, never inline values*.

### Rails admin tools (avo, rails_admin)

- **Avo:** Light-only to date. Dark mode requested in 2022 ([#1191](https://github.com/avo-hq/avo/issues/1191)), deferred for years, closed into a combined "Theming + dark mode + Tailwind v4" tracking issue ([#631](https://github.com/avo-hq/avo/issues/631)) that is **still open**, gated on Tailwind v4, planned around CSS variables (colors: primary/secondary/background/text/heading/link/border), and likely a **paid-tier** feature "considering the high level of complexity." Even shipped pieces leak: CodeMirror/`pre`/`code` blocks ignored dark mode ([#4423](https://github.com/avo-hq/avo/issues/4423), closed). A revealing comment from #1191: *"It would be considerably easier to have the same primary/secondary colors on both light and dark variants"* — the exact instinct the rest of this document argues against. [VERIFIED: gh issue view, avo-hq/avo]
- **rails_admin:** No theme system; "theming" = overriding Bootstrap SCSS variables (`$primary`, `$info`, `$danger`) in `app/assets/stylesheets/rails_admin/custom/variables.scss`, or community theme gems. No dark mode, no mode switching. [CITED: tosbourn.com — Changing Rails Admin colours](https://tosbourn.com/changing-rails-admin-colours/), [rollincode/rails_admin_theme](https://github.com/rollincode/rails_admin_theme)
- **Lesson:** Mountable admin libraries in the Rails ecosystem either never solved this (rails_admin) or have spent 3+ years trying to retrofit it (Avo). The deciding factor is whether the surface was built on a semantic CSS-variable seam from day one. **Threadline's `--tl-*` single-scope seam already is that seam** — Threadline is architecturally ahead of both, missing only the second value lane.

### Default-posture summary table

| Product | Default | Selection mechanism | Token architecture |
|---|---|---|---|
| GitHub | Light | Single theme OR system-sync with separate day/night themes | 3-layer semantic tokens (Primer), inverted neutral scales |
| Grafana | **Dark** | Server/org/team/user cascade + system | Theme objects; user content tuned to dark in practice |
| Linear | **Dark**-leaning | Light/dark/system in settings, instant | LCH-generated from base+accent+contrast |

The dark-default precedents (Grafana, Linear, VS Code) all *still ship light mode*. No successful devtool stayed single-mode at scale; the ones that delayed (Stripe web, Avo) accumulated user workarounds and multi-year retrofit projects.

## 2. Semantic-Token Discipline — "Designed, Not Recolored"

**Why role tokens beat palette swaps:**

- Components reference *roles* (`bg`, `surface`, `text`, `accent`, `border`), never hues. The mode swap changes token **values**, never token **names** — so component code, tests, and screenshots reference one stable vocabulary (Primer's model; GitLab and Material do the same). [CITED: primer.style](https://primer.style/product/getting-started/foundations/color-usage/)
- Naive inversion/palette-swap "will break layout consistency, reduce overall hierarchy, and severely decrease readability" — the unanimous practitioner position. Material explicitly treats dark as "designed as its own system with dedicated tokens, surfaces, and semantic colors," and the same applies in reverse when dark is primary. [CITED: Material dark theme codelab](https://codelabs.developers.google.com/codelabs/design-material-darktheme), [uxcel — 12 principles of dark mode](https://uxcel.com/blog/12-principles-of-dark-mode-design-627), [atmos.style — dark mode best practices](https://atmos.style/blog/dark-mode-ui-best-practices)
- **Accent/signal hues must darken for white backgrounds.** This is physics, not taste: at equal mathematical lightness, different hues are perceived as different lightness; bright accents tuned for dark backgrounds collapse below 3:1 on white. Stripe's CIELAB work is the canonical proof; Linear's LCH generation operationalizes it. [CITED: stripe.com/blog](https://stripe.com/blog/accessible-color-systems), [linear.app/now](https://linear.app/now/how-we-redesigned-the-linear-ui)

**Validation of Threadline's brandbook light lane** [VERIFIED: computed WCAG 2.x relative-luminance ratios from `brandbook/tokens.json` values]:

| Token | Dark value on white | Light value on white | Verdict |
|---|---|---|---|
| accent | `#4F8CFF` → **3.22:1** (fails 4.5:1 text) | `#1557C0` → **6.65:1** (passes AA, near AAA) | Hue darkening was **necessary and correctly executed** — matches Stripe/Linear practice exactly |
| signal | `#4EDFD1` → **1.64:1** (catastrophic on white) | `#0F8F85` → **3.97:1** | Correct direction; passes 3:1 (UI components / large text) but **fails 4.5:1 for body text** — light-mode signal must be restricted to non-text/large-text roles, or a deeper text variant (~`#0B6E66`) added |

The brandbook's light lane follows industry practice. Two additional findings from the same computation (these are *gaps*, not validations):

| Token | Ratio on white | Problem |
|---|---|---|
| `text-soft` `#73819C` | **3.93:1** | Fails AA for normal text — restrict to large text / decorative, or darken for light mode |
| `focus.color` `#7FA9FF` | **2.33:1** | Fails the 3:1 non-text minimum — the single dark-tuned focus ring **cannot be shared**; light mode needs its own ring (e.g. derived from `#1557C0`) |
| `border` `#C9D3E2` | 1.51:1 | Fine for hairline separators, but cannot serve as the sole boundary of a meaningful UI component (3:1 rule) — light mode leans on `border-strong`/fills for affordances |

Also note: `tokens.json` currently scopes `code.*` per mode (`dark-bg`/`light-bg`) but **`callout.*`, `shadow.*`, `focus.*`, `border.accent`, and `state.disabled` are single-lane, dark-tuned rgba values** — every one of these is a hardcoded-overlay footgun (topic 5) sitting in Threadline's own token file today.

## 3. Contrast & Accessibility Across Modes

- **WCAG applies independently per mode.** Offering dark mode does not exempt light (or vice versa): each theme must meet 4.5:1 normal text, 3:1 large text and UI components/focus indicators, on its own. [CITED: boia.org — Dark mode doesn't satisfy WCAG](https://www.boia.org/blog/offering-a-dark-mode-doesnt-satisfy-wcag-color-contrast-requirements), [webaim.org — Contrast and color](https://webaim.org/articles/contrast/), [makethingsaccessible.com — WCAG 2.2 AA contrast](https://www.makethingsaccessible.com/guides/contrast-requirements-for-wcag-2-2-level-aa/)
- **Common failures when a dark-first UI adds light:**
  - **Washed-out borders:** dark themes can run low-contrast borders because surface-vs-bg lightness steps carry hierarchy; on white, those hairlines vanish (Threadline's light `border` at 1.51:1 confirms — fine as texture, insufficient as affordance).
  - **Insufficient text contrast for "muted" tiers:** dark themes get away with soft text because of glow/halation; the same role naively mapped to light gray-on-white fails (Threadline `text-soft` at 3.93:1 confirms).
  - **Elevation systems that only work on one polarity:** dark themes signal elevation by *lightening surfaces* (and borders/glows) because shadows are invisible on dark; light themes signal it with *shadows*. A dark-first system often has no shadow language at all — Threadline's `shadow.*` alphas (0.18–0.40 black) were tuned to be perceptible against `#0B1020` and will read as heavy smudges against `#F7F9FC` unless retuned down. [CITED: Material dark theme codelab](https://codelabs.developers.google.com/codelabs/design-material-darktheme), [muz.li — dark mode tokens & hierarchy](https://muz.li/blog/dark-mode-design-systems-a-complete-guide-to-patterns-tokens-and-hierarchy/)
  - **Focus rings tuned per mode:** the indicator needs 3:1 against the background it sits on; a pale-blue ring perfect on near-black fails on white (Threadline: 8.13:1 on dark vs 2.33:1 on white — measured). [CITED: blog.greeden.me — dark mode & high contrast a11y guide](https://blog.greeden.me/en/2026/02/23/complete-accessibility-guide-for-dark-mode-and-high-contrast-color-design-contrast-validation-respecting-os-settings-icons-images-and-focus-visibility-wcag-2-1-aa/), [accessibility-test.org — WCAG 2.2 contrast](https://accessibility-test.org/blog/support/advanced-guides/color-contrast-in-wcag-2-2-testing-and-fixes-that-actually-work/)
  - **State colors:** Material's documented fix for error red (overlay 40% white onto `#B00020` → `#CF6679` for dark) is the template — every semantic state color gets a per-mode value, validated per mode. Threadline's light lane already does this for success/warning/error text (6.43/6.78/6.78:1 — all pass AA [VERIFIED: computed]).
- **Design-system remedy:** publish *approved per-mode color pairs including states* (hover/active/focus/disabled) so component authors never improvise. [CITED: blog.greeden.me]

## 4. Eye-Strain / Daytime-Readability Evidence (honest read)

**What's solid (peer-reviewed, replicated):**
- **Positive polarity (dark-on-light) wins for visual acuity and reading performance** in normal-vision users; the advantage *grows as text gets smaller*. Mechanism: bright backgrounds constrict the pupil → smaller aperture → sharper retinal image. Sources: Piepenbrock et al. (Ergonomics, 2013) and the studies NN/g synthesizes (Ergonomics, Applied Ergonomics, Human Factors). [CITED: nngroup.com — Dark mode vs light mode](https://www.nngroup.com/articles/dark-mode/)
- **Astigmatism (~30–50% of adults) amplifies the effect:** halation makes light-on-dark text bleed and fuzz; these users read black-on-white measurably better. [CITED: nngroup.com; H Locke — dark mode accessibility issues](https://medium.com/@h_locke/why-dark-mode-causes-more-accessibility-issues-than-it-solves-54cddf6466f5)
- **Who genuinely benefits from dark:** users with cloudy ocular media (e.g., cataracts), photosensitivity, and low-ambient-light contexts. [CITED: nngroup.com]

**What's weaker or commonly overstated — be honest:**
- "Eye strain" as such is mostly **self-report**; the hard evidence is about *performance* (speed, acuity, proofreading), not measured strain. Claims that dark mode "causes" strain are stronger than the literature.
- **Ambient light nuance cuts the unintuitive way:** in *bright daytime* conditions the polarity difference shrinks; one NN/g-cited study found light mode's advantage strongest *at night*. So the precise claim "dark mode strains eyes in daytime" is the least-supported framing — the well-supported framing is "**light mode reads better for most sighted users in most conditions, especially small/dense text**." [CITED: nngroup.com]
- A long-term caveat exists in the other direction: one study found choroidal thinning (a myopia-associated marker) after sustained *light-mode* reading. Single study, not load-bearing. [CITED: nngroup.com]

**Net for Threadline:** the user's instinct is directionally right and the conclusion is industry consensus: **offer both, let the user choose**. An audit UI is dense, small-text, scan-heavy work — exactly the regime where positive polarity helps most — used by operators who may be in bright offices. NN/g's recommendation is precisely Threadline's plan: dark as identity, light as an option. [CITED: nngroup.com]

## What This Means for Threadline

Decisive, transferable rules for a dark-primary Elixir audit-platform admin UI:

1. **Dark stays the default and the brand.** Grafana, Linear, and VS Code prove a devtool can be dark-first and respected for it. But all three ship light mode — *no successful devtool stayed single-mode at scale*, and the two that deferred (Stripe web, Avo) bred third-party recolor hacks and multi-year retrofits. Ship light as a designed second lane in v1.36.

2. **Selection mechanism: system-sync default with a persisted manual override, plus a host-level pin.** This is the converged pattern (GitHub's day/night sync, Datadog's avatar menu + System, Linear's instant settings). For a *library* surface, add the Grafana/Datadog innovation: the host app can pin a mode (`theme: :dark | :light | :system` router opt — lane A's API shape), and that pin wins over OS sniffing. Never OS-sync without an override; never override without persistence.

3. **One token vocabulary, two value lanes.** Keep the existing `--tl-*` semantic names exactly as they are; light mode is a second *value* set, never new names and never component-level conditionals. This is Primer's three-layer discipline and the reason Threadline is already ahead of Avo/rails_admin: the seam exists, only the second lane is missing. Components, tests, and docs keep referencing one vocabulary.

4. **"Designed, not recolored" is non-negotiable, and the brandbook already complies for the headline hues.** Light-lane accent `#1557C0` (6.65:1 on white) and signal `#0F8F85` are correct, Stripe-grade hue retuning — validated by computation, not vibes. Do not "simplify" to shared accent values across modes (the Avo instinct); that path measurably fails WCAG (`#4F8CFF` on white = 3.22:1).

5. **Five token groups must be retuned or split before light ships** (all measured against `tokens.json` today):
   - **Focus ring** — `#7FA9FF` is 2.33:1 on white (fails 3:1). Per-mode ring required; derive light's from `#1557C0`.
   - **Shadows** — dark-tuned alphas; light needs its own lighter elevation scale, and dark's surface-lightness elevation language must not be ported to light unchanged.
   - **Callouts** — `callout.*` rgba overlays and text colors are dark-only; build the light lane (the per-mode `code.*` block is the in-file template to follow).
   - **`text-soft`** — 3.93:1 on white; restrict to large/decorative text in light or darken its light value.
   - **`signal` as text** — 3.97:1; in light mode, signal is a non-text/large-text color only, or add a deeper text variant.

6. **Both modes pass WCAG independently.** Light is not a courtesy recolor; it gets the same contract-test rigor as dark (style contract parity, computed contrast assertions). The Grafana lesson is exact: an undesigned, untested light theme becomes the thing your own users patch out of the product.

7. **Data-viz and state colors get their own per-mode lanes.** Diff tints, severity badges, coverage/timeline visualizations are the audit-platform equivalent of Grafana dashboards — the single most likely surface to silently break in light. Route them through tokens now; never inline.

8. **Kill the flash and the UA mismatch up front.** Inline pre-paint theme resolution (blocking snippet appropriate to a LiveView layout the library may not own) and `color-scheme` set per mode on the surface root. These are cheap at design time and reputation-expensive after launch.

9. **Imagery is a scoping decision, not an afterthought.** Dark-authored brand imagery and screenshots need dual variants, neutral plates, or an explicit "docs stay dark" boundary — decide in the recommendation doc, don't discover it in review.

10. **The eye-strain pitch, stated honestly:** light mode measurably improves reading performance for most sighted users — strongest for small, dense text (an audit UI's exact profile) and for the ~30–50% with astigmatism. The evidence for "daytime dark-mode eye strain" specifically is softer than the performance evidence, so frame light mode as *readability and accessibility choice*, not a medical claim. The conclusion is unchanged either way: dark identity, light option, user choice.
