## 🚧 v1.42 Capture Correctness for Real Table Shapes (In Progress)

**Milestone Goal:** Every audited table gets correct, collision-free capture, whatever its primary-key shape, Postgres schema, or name length, with no silent failure modes. First rung of the ladder to 1.0.0 (`.planning/MILESTONE-GUIDE.txt` §7). Ships as **0.11.0**.

**Granularity:** coarse config, but six phases. Each boundary is a hard contract hand-off (names, then the `create_trigger` signature, then the `table_pk` encoding, then the read-side match), and the security fix (209) must not wait behind the larger PK rewrite. Merging any adjacent pair would make one phase unverifiable until the other lands.

**Evidence:** `.planning/research/SUMMARY.md` (reconciled decisions 1-7) and the four maintainer-accepted scope decisions in `.planning/REQUIREMENTS.md`. Where they conflict, REQUIREMENTS.md wins: the row-history index ships in install, and the PK override is `primary_key:` config, not a CLI flag.

### Dependency spine

```
208 Identifier Foundation ──→ 209 Collision-Free Emission ──→ 210 PK-Agnostic Capture ──→ 211 Read-Side Agreement ──→ 212 Detection & Twins ──→ 213 Upgrade Guide & 0.11.0
  (REL-01 lands first,           (security fix)                  (CONF-01 write side)          (CONF-01 read side,
   before any releasable commit)                                                                 RowKey unit layer may
                                                                                                 start alongside 210)
```

- **Write and read PK fixes ship in one release.** Only 213 releases. A release between 210 and 211 would split history reads.
- **CONF-01 spans two phases.** It is mapped to 210, which introduces the config key and enforces it at migrate time. Its last clause ("history reads use the same declared columns") is proven by Phase 211 success criterion 3. The requirement is not marked complete until 211 passes.

### Cross-cutting invariants (hold in every phase)

- **Red first.** Each phase opens with failing tests that reproduce its defect, then turns them green.
- **Zero human verification.** Every success criterion below names the automated test or gate that proves it. `mix ci.all` stays green at each phase close.
- **No planning vocabulary in shipped artifacts.** No phase numbers or requirement IDs in product code, comments, releasable commit subjects, HexDocs or CHANGELOG.
- **No operator-UI design work.** READ-04 is a minimal guard only.
- **No per-row catalog lookup** in trigger bodies. The PK is resolved at migrate time.
- **Audit rows are evidence.** Historic `table_pk` rows are never rewritten by Threadline; the upgrade guide offers opt-in SQL only.

## Phase Details

### Phase 208: Identifier Foundation

**Goal**: Every identifier Threadline derives is valid, deterministic, unique per table and within PostgreSQL's 63-byte limit, and generator tasks agree on where migrations live
**Depends on**: Nothing (first phase). REL-01 must land before any releasable (`feat`/`fix`/`perf`/`deps`) commit in the milestone.
**Requirements**: NAME-01, NAME-05, CONF-02, REL-01
**Success Criteria** (what must be TRUE):

  1. A developer passing an oversized or invalid schema/table name to the trigger generator gets an error naming the derived identifier and its byte count, never "storage schema" (unit test on the naming module and on `mix threadline.gen.triggers`).
  2. StreamData properties in the default `mix test` (`async: true`, bounded runtime) prove every derived name is ≤ 63 bytes, matches the identifier regex, is deterministic, and is injective under generators biased toward `_`-split pairs, case pairs and 36-byte shared prefixes; a golden literal-name test freezes the format, including byte-identical trigger names wherever the legacy name fits.
  3. `mix threadline.gen.triggers` writes to, and detects reruns in, the repo's configured migrations path (the same resolution `mix threadline.install` uses), and honors `--migrations-path` (Mix task tests against a repo with a non-default `priv` path).
  4. `release-please-config.json` has `bump-minor-pre-major: true`, committed as a non-releasable `ci:`/`chore:` commit that precedes every releasable commit on the milestone branch (asserted by a config contract test plus a `git log` ordering check recorded in the phase verification).

### Phase 209: Collision-Free Emission

**Goal**: No audited table can run another table's capture function or redaction rules, and regenerating or dropping one table's capture never damages another's
**Depends on**: Phase 208
**Requirements**: NAME-02, NAME-03, NAME-04
**Success Criteria** (what must be TRUE):

  1. On real PostgreSQL, `public.billing_invoices` and `billing.invoices`, and a pair of long table names sharing their first 36 bytes, each get a distinct per-table capture function, and each table's writes apply only its own `mask`/`exclude` rules (real-PG integration test).
  2. Regenerating triggers over a 0.10.x install (fixture with frozen 0.10.x trigger SQL) leaves exactly one Threadline trigger per table, and trigger names that fit stay byte-identical (real-PG test counting `pg_trigger` rows per table).
  3. Dropping or rolling back one table's capture objects leaves every other table's trigger present and enabled; no generated SQL contains `CASCADE` on a capture function, and a function is dropped only when no trigger references it by `tgfoid` (real-PG test plus a generated-SQL assertion).
  4. Any PostgreSQL identifier-truncation NOTICE raised during the test suite fails the suite (suite-level guard with a positive control).

### Phase 210: PK-Agnostic Capture

**Goal**: A table's audit rows record its real primary key, whatever the key's name, type or column count, without adding per-row cost or breaking existing installs
**Depends on**: Phase 209 (both rewrite `create_trigger` and migration assembly). Phase 211 depends on the `table_pk` encoding locked here.
**Requirements**: CAP-01, CAP-02, CAP-03, CAP-04, CAP-05, CAP-06, CONF-01
**Success Criteria** (what must be TRUE):

  1. Writes to tables keyed by a non-`id` integer, uuid or text column, and to composite-PK tables (including a PK index with INCLUDE columns), store every key column in `table_pk` with no configuration (`trigger_pk_shapes_test.exs`, real PG across the CI PostgreSQL matrix).
  2. Migrating triggers for a table with no primary key and no override fails at migrate time, before any host write, with a message naming the table and the `primary_key:` option; a primary-key column listed in `mask` or `exclude` is refused before any capture with a message naming the column (real-PG migration tests).
  3. An adopter can declare `primary_key: [...]` for a PK-less table in `config :threadline, :trigger_capture, tables:`; empty lists, invalid names, duplicates and redaction overlap are rejected, the migration refuses unless a unique, non-partial, immediate index over NOT NULL columns matches, an override on a table that already has a PK is refused, and captured rows carry the declared columns (config validation unit tests plus real-PG migration tests).
  4. A trigger installed by 0.10.x SQL (no trigger arguments) keeps capturing exactly as before, and a write whose key cannot be resolved stores `{}` instead of failing the host transaction (real-PG test with frozen legacy trigger SQL).
  5. Per-row trigger overhead on the reference benchmark is within noise of the 0.10.x baseline, recorded as before/after numbers in the phase verification, and the trigger body contains no catalog lookup (benchmark run plus a generated-SQL assertion).

### Phase 211: Read-Side Agreement

**Goal**: What a developer reads through `history`, `row_history_query` and `as_of` matches exactly what the trigger stored, for every supported key shape, and row lookups are indexed
**Depends on**: Phase 210 (acceptance needs the final `table_pk` encoding; the `RowKey` unit layer and the integer-PK regression may start alongside 210)
**Requirements**: READ-01, READ-02, READ-03, READ-04, IDX-01
**Success Criteria** (what must be TRUE):

  1. `history/3`, `row_history_query/3` and `as_of/4` return captured rows for a default Ecto bigserial-keyed table, fixing the text-vs-integer mismatch (regression test that fails on the 0.10.x query code).
  2. A developer reads a composite-key row's history by passing a keyword list or map of its key columns; a missing, extra or mismatched key set raises an `ArgumentError` naming the expected columns (query unit tests plus real-PG integration).
  3. History for a `primary_key:`-override join table returns its rows using the same declared columns the trigger recorded, completing CONF-01 (real-PG round-trip test).
  4. One `history/3` call returns both a row captured by frozen 0.10.x trigger SQL and a row captured by the regenerated trigger for the same record, and operator-surface links for composite-key rows render no row link rather than a wrong one (mixed-row fixture test plus a LiveView render test).
  5. New installs create `audit_changes_row_history_idx` on `(table_schema, table_name, table_pk, captured_at DESC, id DESC)`, an upgrader copy-paste `CREATE INDEX CONCURRENTLY` migration exists, and an EXPLAIN-based test proves `history` and `as_of` use the index (install test plus EXPLAIN test).

### Phase 212: Detection and Adopter Twins

**Goal**: Adopters are told, by command and with the exact fix, when a table's capture is stale, drifted, shared, duplicated or disabled, and the adopter twins prove every table shape works end to end
**Depends on**: Phase 211
**Requirements**: HLTH-01, HLTH-02, HLTH-03, HLTH-04, HLTH-05, HLTH-06, TWIN-01
**Success Criteria** (what must be TRUE):

  1. `Threadline.Health.trigger_findings/1` returns structured findings (`code`, `severity`, `schema`, `table`, `message`, `details`) whose messages name the table and the exact fix command, and it works through PgBouncer transaction pooling and as a non-owner role (real-PG tests plus the PgBouncer topology lane).
  2. Seeded catalog states each produce exactly the right finding: a pre-0.11 trigger on an `id`-keyed table gives a `:legacy_trigger_no_pk_args` warning; recorded key columns differing from the live PK or override index give `:pk_drift`; one function referenced by two tables' triggers gives `:shared_capture_function`; two Threadline triggers on a table give `:duplicate_capture_trigger`; a disabled trigger gives `:capture_trigger_disabled` and no longer counts as covered (one real-PG fixture per code, each with a clean negative control).
  3. `mix threadline.verify_coverage` exits non-zero on any error finding for an expected table and only prints warnings; `mix threadline.health.coverage` shows findings in text and JSON (Mix task tests asserting exit status and both output formats).
  4. The example Phoenix app and the hex evaluator (rehearsal mode) contain audited tables with a non-`id` PK, a composite PK, a `primary_key:` join table, same-named tables in two schemas and a ≥ 60-byte name, with trigger migrations generated by `mix threadline.gen.triggers` itself, pinned by a contract test, and each shape's history round-trips (example-app suite and hex-evaluator lane in CI).

### Phase 213: Upgrade Guide and 0.11.0 Release

**Goal**: An adopter on 0.10.x can upgrade to 0.11.0 by following one guide, and 0.11.0 is published from a clean, green `main`
**Depends on**: Phase 212
**Requirements**: REL-02, REL-03
**Success Criteria** (what must be TRUE):

  1. The upgrade guide covers regenerating triggers, adding the row-history index concurrently, opt-in backfill SQL for INSERT/UPDATE rows captured as `{"id": null}`, which pre-0.11 rows cannot be recovered (DELETEs, redacted keys), and the CHANGELOG carries a security note for installs where two tables shared a capture function (doc-contract tests pin the regenerate and index steps).
  2. The documented backfill SQL and upgrade steps run cleanly against a fixture install seeded with 0.10.x rows, and `ecto.rollback --all` leaves no orphan capture functions and drops no foreign triggers (real-PG upgrade and rollback tests).
  3. The milestone lands on `main` as a squash with a clean conventional title, release-please proposes exactly `0.11.0` with phase-ID-free notes, `main` CI is green on the released SHA, and no open PRs or stray branches remain (release runbook checks recorded in verification; push, merge and publish wait for the maintainer's explicit go).
