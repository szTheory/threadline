# Phase 45: Bench Harness & Published Baselines - Research

**Researched:** 2026-04-26
**Domain:** Elixir Benchmarking (Benchee), Reproducible Performance Environments
**Confidence:** HIGH

## Summary

This phase delivers a robust, reproducible performance benchmarking suite and an associated set of published baseline numbers for Threadline v1.14. It introduces `benchee` within an isolated `bench/` Mix project to prevent test dependencies from leaking into the final Hex package. The harness measures three required scenarios (`cold_single_table`, `warm_loaded`, `concurrent_purge`) to provide realistic capacity planning expectations, rather than merely synthetic best-cases.

**Primary recommendation:** Build `bench/` as a sibling, self-contained Mix project (like `examples/threadline_phoenix/`) rather than adding `benchee` and test scripts to the root `mix.exs`. This completely eliminates the risk of tarball bloat and dependency leakage (PERF-P2).

## Architecture Patterns

### Recommended Project Structure
```
src/
├── mix.exs (root - NO bench deps)
├── bench/
│   ├── mix.exs (standalone sibling)
│   ├── README.md
│   ├── baselines/ (for EXPLAIN output)
│   ├── scripts/
│   │   ├── seed_audit_changes.exs
│   │   ├── setup.exs
│   │   └── teardown.exs
│   ├── audit_capture_bench.exs
│   ├── timeline_query_bench.exs
│   └── redaction_and_changed_from_bench.exs
└── guides/
    └── performance.md
```

### Pattern 1: Bench Harness as a Sibling App (PERF-P2)
**What:** The root library `mix.exs` explicitly excludes `bench/` from its package `:files` list and places no benchmarking libraries in `:deps`. The benchmark logic is a wholly independent Mix app referencing the parent via `path: ".."`.
**When to use:** Crucial for any library shipping to Hex to avoid pulling unneeded dev/test-only dependencies into consumer trees, or inflating tarball size.
**Example:**
```elixir
# In root mix.exs
defp verify_bench(_args) do
  # Shell out to the sibling app
  cmd = "bash -lc 'set -euo pipefail && cd bench && mix deps.get && mix run scripts/setup.exs && mix run audit_capture_bench.exs'"
  case Mix.shell().cmd(cmd, env: [{"MIX_ENV", "bench"}]) do
    0 -> :ok
    status -> Mix.raise("verify.bench failed (#{status})")
  end
end
```

### Pattern 2: Pinned Bench Environments and Randomness (PERF-P1)
**What:** Eliminating variability by pinning data volume, PRNG seeds, and documenting the hardware context via a `BENCHMARK-ENV` metadata block. 
**When to use:** Any published baseline to ensure it serves as a stable reference.
**Example:**
```elixir
:rand.seed(:exsss, {1, 2, 3})
# Run bench, then emit JSON metadata capturing environment
File.write!("results/metadata.json", Jason.encode!(%{
  commit_sha: System.cmd("git", ["rev-parse", "HEAD"]) |> elem(0) |> String.trim(),
  elixir_version: System.version(),
  preset: "warm_loaded",
  changed_from: true
}))
```

### Anti-Patterns to Avoid
- **Leaking `benchee` into root dependencies:** As defined in PERF-P2, having `{:benchee, only: :dev}` in the root `mix.exs` makes it load unnecessarily in adopters' CI environments due to dependency tree bleed.
- **`mix verify.bench` in `mix ci.all`:** This causes unpredictable PR durations and runs heavyweight setup scripts on every commit (PERF-P5).
- **Synthetic Empty Tables Only:** Benchmarking just `TRUNCATE TABLE` then insert leads to numbers ~10x higher than realistic loaded DB behavior (PERF-P3).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Benchmark iterations & std-dev | `:timer.tc` loops | `benchee` | Statistical rigor, warmup periods, memory tracking, multi-formatter support. |
| EXPLAIN parsing | Regex on raw strings | `FORMAT JSON` | `EXPLAIN (ANALYZE, FORMAT JSON)` returns structurally clean JSON to write straight to `baselines/`. |

## Common Pitfalls

### Pitfall 1: Non-Reproducible Numbers (PERF-P1)
**What goes wrong:** Publishing numbers without environmental contexts (hardware, DB version, loaded size).
**Prevention:** Guide **must** contain `BENCHMARK-ENV` block with schema preset and config. Ensure static `:rand.seed(:exsss, {1, 2, 3})` is used.

### Pitfall 2: Harness leaks into Tarball (PERF-P2)
**What goes wrong:** Hex tarballs end up bloating adopters' disk, or dependencies bleed down.
**Prevention:** `bench` isolated as its own app. Verify `:files` in root `mix.exs` uses a strict allowlist.

### Pitfall 3: Unrealistic Workload Base (PERF-P3)
**What goes wrong:** Adopters experience 10x slower ingestion than documentation claims.
**Prevention:** Test and publish the `warm_loaded` (indexes, 10M rows) and `concurrent_purge` variants. Quote the *lowest* figure as typical.

### Pitfall 4: Stale Output Divergence (PERF-P4)
**What goes wrong:** Triggers get heavier, but old output numbers persist in docs.
**Prevention:** Include a `git rev-parse HEAD` marker with output runs so consumers can tell how fresh the test run is.

### Pitfall 5: CI Wall-Time Drag (PERF-P5)
**What goes wrong:** CI grinds to a halt on simple PRs.
**Prevention:** Ensure the `test/threadline/ci_topology_contract_test.exs` validates that `ci.all` does *not* run benchmarks, and the bench job runs separately/on-demand.

## Code Examples

### Executing EXPLAIN JSON into baselines
```elixir
defmodule Bench.Explain do
  def capture(query, file_path) do
    # Use Ecto to bypass ORM abstraction and grab direct plan
    %{rows: [[json]]} = Ecto.Adapters.SQL.query!(Threadline.Test.Repo, "EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) " <> query, [])
    File.write!("bench/baselines/#{file_path}", Jason.encode!(json, pretty: true))
  end
end
```
