```markdown
# Threadline ↔ Sigra integration

<!-- SIGRA-03-INTEGRATION-GUIDE -->

This guide is the **integrator-owned** place for wiring [Threadline](https://hex.pm/packages/threadline) into a Phoenix host that uses [Sigra](https://hex.pm/packages/sigra) for authentication. After ten minutes of copy-pasting, your `audit_actions` rows will distinguish four request shapes — user session, admin impersonating a user, machine-to-machine API token, and unauthenticated — without `:sigra` becoming a Threadline runtime dep.

The wiring contract is **additive**: Threadline never overrides explicit integrator intent (`x-correlation-id` header always wins), and the adapter is safe to ship even when `:sigra` is not installed (it returns `nil` instead of raising).

## Install

Add `:sigra` to **your host application's** `mix.exs` — for hosts; never for the library:

```elixir
{:sigra, "~> 0.2", optional: true}
```

Threadline's library `mix.exs` does NOT depend on `:sigra` (not even `optional: true`). The `Threadline.Integrations.Sigra` adapter is in-tree but soft-deps Sigra via `Code.ensure_loaded?/1`. If your host removes `:sigra` later, Threadline keeps loading; the adapter just returns `nil` for the actor.

Run `mix deps.get` once `:sigra` is in your deps list. Then move to wire-up.

## Plug callback wire-up

In your Phoenix router's `:api` pipeline, run a small pre-plug **before** `Threadline.Plug` so Sigra-derived correlation IDs reach Threadline through the standard `x-correlation-id` header path. Then wire `Threadline.Plug` with `:actor_fn` pointing at the adapter:

```elixir
pipeline :api do
  plug :accepts, ["json"]
  plug MyApp.SigraContextPlug
  plug Threadline.Plug, actor_fn: &Threadline.Integrations.Sigra.actor_ref_from_conn/1
end
```

The single integrator-facing call is the line:

```elixir
plug Threadline.Plug, actor_fn: &Threadline.Integrations.Sigra.actor_ref_from_conn/1
```

`MyApp.SigraContextPlug` is a ~25-line plug that mirrors the standard `Plug.RequestId` check-before-set idiom. Drop this verbatim into `lib/my_app_web/sigra_context_plug.ex`:

```elixir
defmodule MyApp.SigraContextPlug do
  @moduledoc false

  @behaviour Plug
  import Plug.Conn

  @impl true
  def init(opts), do: opts

  @impl true
  def call(conn, _opts) do
    case get_req_header(conn, "x-correlation-id") do
      [_ | _] ->
        conn

      [] ->
        case Threadline.Integrations.Sigra.audit_context_overrides_from_conn(conn) do
          %{correlation_id: cid} when is_binary(cid) ->
            put_req_header(conn, "x-correlation-id", cid)

          _ ->
            conn
        end
    end
  end
end
```

The plug never overrides an existing `x-correlation-id` — explicit integrator intent always wins. This trust-boundary contract is intentional and documented under "Behaviors locked by SPEC" below.

> **Forward pointer:** A future `Threadline.Plug` `:context_overrides_fn` option will let hosts skip this pre-plug entirely. We are deliberately not committing to a timeline; raise an issue if the two-plug pipeline becomes a friction point.

A working end-to-end reference of this exact pipeline lives in `examples/threadline_phoenix/lib/threadline_phoenix_web/router.ex`.

## Behaviors locked by SPEC

The adapter implements six locked semantic decisions. Each is verifiable in your audit table and pinned by Threadline's regression suite:

1. **Impersonation maps to `:admin`.** When `current_scope.impersonating_from` is non-nil (admin acting as a user), `actor_ref_from_conn/1` returns `%ActorRef{type: :admin, id: <admin_user_id>}` — the audit row records who really pressed the button. The impersonated user's id rides in `correlation_id` (see "correlation_id formats" below).
2. **API token maps to `:service_account`.** When `current_scope.auth_method` is `:api_token` (or `:jwt`), `actor_ref_from_conn/1` returns `%ActorRef{type: :service_account, id: <scope.id>}`. Machine-to-machine writes are visibly distinct from interactive user writes in `WHERE actor_ref->>'type' = 'service_account'` queries.
3. **Active organization rides in `correlation_id`.** When `current_scope.active_organization_id` (or the equivalent `Sigra.Session.active_organization_id`) is non-nil, the adapter appends `:org:<org_id>` as a suffix on the correlation_id. No new field is added to `AuditContext` — the adapter respects Threadline's "additive only" v1.14 rule.
4. **Anonymous / Sigra-absent returns `nil`.** When `current_scope` is missing, `nil`, or has no `:user` and no token shape, `actor_ref_from_conn/1` returns raw `nil` — NOT `ActorRef.new(:anonymous, nil)`. This preserves the distinction between "no actor, by policy" and "actor not yet attached" in the audit table.
5. **`x-correlation-id` header always wins.** When the conn carries an `x-correlation-id` request header, `audit_context_overrides_from_conn/1` returns `%{}`. Threadline never overrides explicit integrator intent. This is the key trust-boundary contract: the integrator owns the header.
6. **Plug-only adapter — no telemetry subscription in v1.** The adapter is consumed exclusively through `Threadline.Plug`'s `:actor_fn` callback. Subscribing to `[:sigra, :audit, :log]` events is deferred to a future milestone (the dedup design between Plug-driven and telemetry-driven recording is not mature enough to ship).

## correlation_id formats

When the `x-correlation-id` header is absent, the adapter constructs one of four literal formats:

| Request shape | correlation_id format |
|---------------|----------------------|
| Impersonation (`scope.impersonating_from` non-nil) | `sigra-imp:<session_id>:user:<imp_user_id>` |
| Plain user session | `sigra-session:<session_id>` |
| API token (no session) | `sigra-token:<token_id>` |
| Anonymous / Sigra absent | no override (`%{}`) |

Each format optionally has a `:org:<org_id>` suffix when the scope or session carries an active organization.

The four prefixes — `sigra-imp:`, `sigra-session:`, `sigra-token:`, and the anonymous `%{}` outcome — are stable contracts. They are designed to be greppable in operator queries (`WHERE correlation_id LIKE 'sigra-imp:%'`).

## Soft-dep contract

The single gate for "is Sigra installed?" is:

```elixir
Code.ensure_loaded?(Sigra.Session)
```

When this returns `false`:

- `actor_ref_from_conn/1` returns `nil` (no raise, no error).
- `audit_context_overrides_from_conn/1` returns `%{}` (no raise, no error).
- `actor_fn/0` still returns the captured function reference; calling it just yields `nil`.

This is why Threadline's library `mix.exs` does not list `:sigra`. The adapter compiles and ships in every Threadline release; it activates only when your host adds `:sigra` to its own deps. Removing `:sigra` from your host later is safe — Threadline keeps loading, audit_actions rows just lose their actor attribution.

A test-environment shim at `test/support/sigra_test_doubles.ex` defines minimal `Sigra.Session`, `Sigra.Scope`, and `Sigra.APIToken` `defstruct`s under an `unless Code.ensure_loaded?(Sigra.Session)` guard, so Threadline's own test suite runs deterministically without `:sigra` in deps. The guard makes the shim mutually exclusive with a real Sigra install.
