<decisions>
## Implementation Decisions

### Down-path drop shape (CAPT-01)
- **D-01:** **Emit the drop from the first-run migration only, unconditionally.** In `down_body/2`
  (`lib/mix/tasks/threadline.gen.triggers.ex`), remove the `needs_per_table` filter from
  `function_downs`. Every first-run table's `down` emits
  `TriggerSQL.drop_function_if_unused(Naming.function_name(t))` after its trigger drop, whether or
  not that run created a per-table function. The rerun migration's `down` stays unchanged: no
  trigger drop and no function drop, plus its existing "capture stays on" comment.
  - **Why this works:** `Naming.function_name/1` depends only on schema and table, so the one
    possible per-table name is known when the first-run migration is generated. No forward
    scan is needed, and none is possible, because later reruns don't exist yet.
  - **Why no rerun-side drop:** `ecto.rollback` runs downs newest-first, so a rerun's `down`
    always finds the first-run trigger still live. The guarded drop would never succeed, and it
    would print a false `WARNING … kept … regenerate triggers` on every ordinary single-step
    rollback.
  - **Supersedes the roadmap's Phase 224 Research note** and `.planning/research/ARCHITECTURE.md`
    §C.3, which proposed two-sided emission with the first-run side wired through
    `TriggerMigration.covered_pairs/1`. That wiring can't be implemented: `covered_pairs/1` scans
    migrations that exist when a migration is generated, and later reruns don't exist yet. The
    Phase 224 success criteria are still met exactly: drops go only through
    `drop_function_if_unused/2`, no CASCADE, zero orphans after partial and full-chain rollback.
    The planner should make the roadmap's Research note match this in a planning-docs commit.
  - **Reversibility:** costly. Generated migrations are host-owned and committed, so every
    migration generated from this release on carries the new `down` shape permanently.
- **D-02:** **Reuse `drop_function_if_unused/2` unchanged.** No `quiet:` option, no new
  parameter, no change to its SQL or WARNING text. The only remaining WARNING is the true
  positive: a pre-0.10.2 table that shares the function name and still has an unregenerated trigger.
- **D-03:** **Don't target `Naming.legacy_function_name/1` in the first-run `down`.** Legacy names
  are only ever retired, never created. For legacy-eligible tables (in `public`, name of 36 bytes
  or fewer) the legacy name equals `function_name/1`, so D-01 already covers them.
- **D-04:** **Emit a short `#` comment in the generated first-run `down`, before the function
  drop**, in the style of `rerun_rollback_comment`. It tells an adopter why a plain table's `down`
  has a `DO $$` block with no matching `up`. Suggested wording: "This also removes the per-table
  capture function of <table> if a later rerun created one and no trigger still uses it." The
  planner may edit it for project voice: plain, specific, no hype.
- **D-05:** Update the "Rerunning" section of the `gen.triggers` moduledoc: a full rollback
  also removes any per-table function a later rerun added, even though that rerun's own `down`
  leaves its table alone.

### Chains generated by earlier releases
- **D-06:** **Documentation only, reusing the existing pinned cleanup SQL.** Chains generated by
  0.11.2 or earlier won't emit the new drop, so a full rollback can still leave the orphan.
  Remediation:
  - Extend `guides/upgrading-to-0.11.md` §"## Rolling back". Broaden its prose so it also covers
    "a first trigger migration generated before this fix, followed by a rerun that added
    redaction, exclusions or `store_changed_from`". Point that case at the **existing**
    `<!-- threadline:rollback-cleanup-sql:start/end -->` sweep. It already matches every
    `threadline\_capture\_changes\_%` function in the storage schema with no live trigger, drops
    without CASCADE, and never touches the global function.
  - Don't add a second snippet or marker pair.
  - Add a CHANGELOG `Fixed` entry that points to the section, written for adopters, with no
    planning vocabulary.
  - The existing proofs stay authoritative: `test/threadline/upgrade_rollback_test.exs` runs the
    snippet live against the catalog, and `test/threadline/upgrading_to_0_11_doc_contract_test.exs`
    pins its markers and heading. Update those tests' assertions only if the heading or pinned
    text changes. Prefer adding prose under the existing heading over renaming it.
  - Snippets call no library code. `Threadline.Capture.TriggerSQL` is `@moduledoc false`, so
    guides never tell adopters to call it.
- **D-07:** **No detection at generation time.** The generator won't scan old first-run
  migrations to warn about them. Matching the text of host-edited files is fragile, and the
  warning would only fire for adopters who rerun the generator.

### Tests (CAPT-02)
- **D-08:** **Deterministic regression test.** Extend `test/threadline/capture/trigger_rerun_test.exs`
  with a new `describe` block. Generate for real with `Mix.Tasks.Threadline.Gen.Triggers.run/1`
  into a tmp dir, using the existing `generate!/2`. Migration 1 uses the default/global function.
  Migration 2 is a rerun that forces a per-table function (`--store-changed-from`, an exclude or a
  mask). Add an `apply_down!/1` helper that mirrors `apply_up!/1`. Assert:
  - **Partial rollback** (migration 2's `down` only): the trigger is still there and **still uses
    the per-table function**. By design, capture stays on with the policy the rerun installed; it
    does **not** revert to the global function. The function is not orphaned and not dropped, and
    the rollback emits **no** `threadline: kept` WARNING.
  - **Full chain** (then migration 1's `down`): no trigger remains, and the orphan check returns
    zero rows.
  - **Fidelity:** SC1 is worded around `mix ecto.rollback --all`. The planner decides whether the
    regression's full-chain case also goes through `Ecto.Migrator` with an isolated migrations
    source, or whether text-extracted `execute` application (the existing, never-compile pattern)
    is enough. If `Ecto.Migrator` can be isolated cheaply without touching the suite's own
    `schema_migrations`, prefer it for the one regression test.
- **D-09:** **Structural orphan check, independent of `Naming`.** Query `pg_proc` joined to
  `pg_namespace`, filtered by `pronamespace` to the configured storage schema. Never rely on
  `search_path`: the local test DB may carry a stale `public.threadline_capture_changes()`. Match
  `threadline_capture_changes_%` (escaped underscores, the global name excluded) and assert every
  match has a live `pg_trigger` with `tgparentid = 0` and a matching `tgfoid`. A check against
  `Naming.function_name/1` may be added as a secondary assertion, but it can never be the only
  orphan check (that would be tautological).
- **D-10:** **Property test.** New file `test/threadline/capture/trigger_rerun_property_test.exs`,
  `DataCase`-based and `async: false`. It sits next to the rerun test, not in the pure
  `trigger_migration_property_test.exs`.
  - Generator: a new `test/support/trigger_run_generators.ex` in the style of `naming_generators.ex`.
    It produces 1–4 ordered runs for one table, each `:default` or per-table-forcing (options
    `store_changed_from`, `exclude` or `mask`). Use `frequency` to bias towards default→per_table,
    per_table→default (the `retire_ups` path) and per_table→per_table with different options.
  - Isolation: a unique table name on each iteration (`System.unique_integer([:positive, :monotonic])`),
    with `try/after` cleanup inside `check all`, because `on_exit` doesn't fire between iterations.
    Don't pull the collision-biased `pair_gen()` names into the DB property; long names add DDL
    cost and are already covered by the pure naming property.
  - Checks: after applying the whole sequence and then every `down` in reverse, the D-09 check
    finds zero rows. At the end of the sequence, every live trigger's `tgfoid` resolves.
  - `@max_runs 20` as a named module attribute. Don't add an env var yet; Phase 226 wires
    `THREADLINE_PROPERTY_SCALE` and can swap the attribute in one line.
- **D-11:** **Mutation controls, run by hand and recorded.** Locally revert only the `down_body/2`
  change, keeping the new tests. Show the regression and the property red, and cite the
  property's failing seed along with the exact `mix test --seed N <file>` command. Paste both
  failures into VERIFICATION.md, then restore the fix and show green. Don't build an automated
  mutation harness.
- **D-12:** Update the existing expected-output `down` assertions in
  `test/mix/tasks/threadline/gen_triggers_test.exs`: for example around L792/L801/L816-817 (a plain
  first-run `down` of `[TriggerSQL.drop_trigger("posts")]`) and the `:down` assertions around
  L450-630. Also update the `@generated_down_phrases`/`@rerun_doc_phrases` contract block
  (~L932-949) so it matches the new shape and the D-04 comment.

### Bench compile (SUITE-05)
- **D-13:** In `bench/mix.exs`, add `def cli, do: [preferred_envs: [compile: :test, run: :test]]`.
  Keep `env: :test` on the `threadline` path dep, because bench needs `Threadline.Test.Repo` at
  runtime. `run: :test` is required too, because `bench_helper.exs` halts outside `:test`.
- **D-14:** New alias in root `mix.exs`, backed by a function like `verify_bench/1`:
  `"verify.bench_compile": &verify_bench_compile/1`. It runs
  `bash -lc 'set -euo pipefail && cd bench && mix deps.get && mix compile --warnings-as-errors'`
  with **no `MIX_ENV`**. Add it to `ci.all` right after `"verify.compile_no_optional"`. The
  existing "ci.all excludes verify.bench" test matches the quoted `"verify.bench"` and so doesn't
  trip on `"verify.bench_compile"`; the planner should confirm this.
- **D-15:** Add the step to the existing `verify-compile-no-optional` job after its compile step,
  named `Compile bench project (bare mix compile)` and running `mix verify.bench_compile`.
  - **No cache step.** That job is pinned to zero cache steps (see
    `ci_workflow_parity_contract_test.exs` and CONTRIBUTING).
  - **Keep the job `name:` "Compile without optional deps"**, which is pinned byte-for-byte. Keep
    the job `id:`.
  - **No new job,** so the `ci-required` `needs:` list and the branch-protection roster don't
    change. Update the `verify-compile-no-optional` row in CONTRIBUTING's job table in the same
    commit.
  - Keep it off `verify-test` (the three-way matrix and the critical path).
- **D-16:** Add a small text contract test that `bench/mix.exs` declares `preferred_envs` with
  `compile: :test`, in the style of the CI-topology tests. The live CI step is the functional
  proof. The local mutation control (remove `preferred_envs`, see `mix verify.bench_compile` fail)
  goes in VERIFICATION.md.
- **D-17:** Leave the `MIX_ENV=test` prefixes in the release-lane `verify_bench/1` alone. They're
  now redundant, harmless and self-documenting, so dropping them is optional follow-up.

<code_context>
## Existing Code Insights

### Reusable Assets
- `TriggerSQL.drop_function_if_unused/2`: an idempotent, usage-checked `DO` block, never CASCADE.
  The up side (`retire_ups/1`) already trusts it unconditionally.
- `Naming.function_name/1`: a deterministic per-table name. This is the key fact behind D-01.
- `trigger_rerun_test.exs` helpers: they generate real migrations into tmp and apply the extracted
  `execute` SQL without compiling the module.
- The existing guide cleanup sweep, with its live-catalog test and doc-contract markers.

### Established Patterns
- Generated migrations are host-owned code adopters read. Every generated block carries a
  plain-language comment.
- Property tests set `max_runs` explicitly. Pure ones are `async: true`; DB-backed ones are
  `DataCase`, `async: false`, with unique names on each iteration.
- CI changes follow the same-commit roster rule. This phase adds a step, not a job.

### Integration Points
- `down_body/2` is the only generator change.
- The guide and CHANGELOG remediate chains generated by earlier releases.
- The `verify-compile-no-optional` job and `ci.all` hold the bench proof.

</code_context>

<specifics>
## Specific Ideas

- The `hair_trigger` (Rails) lesson: a trigger migration's correct `down` depends on the
  cumulative state of the chain. Threadline already handles that for triggers via `rerun?/2`.
  This phase extends it to functions, using the deterministic name instead of a scan.
- The 0.11.0 precedent: a sibling rollback hazard was fixed in docs with a pinned, live-tested
  SQL sweep. Reuse it rather than adding a second snippet.
