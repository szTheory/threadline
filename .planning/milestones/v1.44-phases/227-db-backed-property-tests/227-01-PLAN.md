Moduledoc states: plain functions only; `__using__` and `setup` are forbidden so this never becomes a second harness next to `Threadline.DataCase`; callers do `use Threadline.DataCase` + `use ExUnitProperties` + `import Threadline.Test.DbProperty`; per-iteration cleanup is required because retention's dry run/delete and export act on the whole table (D-01); transaction-plus-rollback is rejected because it hides capture. Functions (names and arities are Claude's discretion per CONTEXT, fixed here):
    1. `iteration_key/0` returns `System.unique_integer([:positive, :monotonic])`.
    2. `with_iteration(cleanup, body)`: both arity-1 funs receiving `n`. Computes `n = iteration_key()` inside the call, runs `body.(n)` in `try`, and in `after` runs `cleanup.(n)` wrapped in a private `safely/2` that rescues any exception and catches throw/exit, then calls `IO.warn` with a message naming the failed cleanup step (the warning may include the key; assertion messages never do). Returns the body's value. The body's own exception always propagates unchanged.
    3. `delete_iteration!(host_table, pk_values)` where `pk_values` is a list of strings (the text form of each `id`, so uuid and bigint keys share one code path): (a) `DELETE FROM <host_table> WHERE id::text = ANY($1)` (host rows first; this fires the trigger and captures delete changes, which step (b) then removes); (b) collect `transaction_id`s from the storage-qualified `audit_changes` where `table_name = host_table AND table_pk->>'id' = ANY($1)`, then delete those changes; (c) delete only the collected `audit_transactions` ids that now have no change left (`NOT EXISTS` against the qualified audit_changes). Every audit table name comes from `Threadline.StorageSchema.table(:audit_changes)` / `table(:audit_transactions)`. `host_table` is an internal fixture name; validate it against `~r/\A[a-z_][a-z0-9_]*\z/` and raise ArgumentError otherwise, so it is never interpolated unchecked.
    4. `delete_transactions!(ids)`: deletes the given qualified `audit_transactions` ids (the FK `ON DELETE CASCADE` removes their changes); used by the retention property.
    5. `assert_audit_tables_empty!/0`: counts rows in both qualified tables with raw SQL and calls `ExUnit.Assertions.flunk("foreign rows present; global purge oracle unsound")` (exact text, D-18 step 1) when either is non-zero; returns `:ok`.
    6. `ordered_id(rank, n)`: `Ecto.UUID.load!(<<rank::32, n::96>>)`, documented as used only by the D-17 tie example so the tie winner is decided by generated data.

The tracer test: inside `with_iteration`, insert one row with id `ordered_id(1, n)`, update it, assert two captured changes are readable through the qualified table, and pass `fn n -> delete_iteration!("dbp_harness_rows", [ordered_id(1, n)]) end` as cleanup; after `with_iteration` returns, `assert_audit_tables_empty!()` passes and the host row is gone. Further examples: (i) a body that fails an assertion still runs cleanup (assert the rows are gone after `assert_raise ExUnit.AssertionError`); (ii) a cleanup that raises produces an IO.warn (capture with `ExUnit.CaptureIO.capture_io(:stderr, ...)`) and the body's AssertionError, not the cleanup error, is what propagates; (iii) `assert_audit_tables_empty!` flunks with the exact message after one `audit_transactions` row is inserted (delete it afterwards); (iv) `SELECT $1::uuid < $2::uuid` on `ordered_id(1, n)` and `ordered_id(2, n)` is true; (v) `delete_iteration!("bad name;", [])` raises ArgumentError.
