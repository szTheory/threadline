# Requirements: Threadline v1.42 Capture Correctness for Real Table Shapes

**Defined:** 2026-09-24
**Core Value:** Every row mutation that matters is captured durably and linked to who did it and why, without the developer having to remember to opt in.
**Milestone goal:** Every audited table gets correct, collision-free capture, whatever its primary-key shape, Postgres schema, or name length. Nothing may fail silently. This is the first rung of the ladder to 1.0.0 (`.planning/MILESTONE-GUIDE.txt` §7). It ships as **0.11.0**.
**Evidence:** `.planning/research/SUMMARY.md` (reconciled decisions 1-7) plus the three scope decisions below.

## Scope decisions (maintainer-accepted 2026-09-24)

These came from parallel decision research. Record them here so later phases don't re-derive them.

1. **Release config.** Set `release-please-config.json` `bump-minor-pre-major: true` in a non-releasable `ci:`/`chore:` commit before any releasable commit. A breaking change then proposes 0.11.0, never 1.0.0. 1.0.0 is cut deliberately at v1.45.
2. **Primary-key override is config, not a CLI flag.**
   - Syntax: `config :threadline, :trigger_capture, tables: %{"posts_tags" => [primary_key: ["post_id", "tag_id"]]}`. Same place as the `mask`/`exclude` redaction settings.
   - Why config: `Threadline.Query` (RowKey) reads it at request time, so reads and writes share one declared identity. A CLI flag would freeze the override into a migration where reads can't see it, which recreates the silent-empty-history bug.
   - Allowed only on tables **without** a primary key (Phoenix join tables, legacy tables).
   - It must match a unique, non-partial, immediate index whose columns are all NOT NULL (REPLICA IDENTITY rules). This is validated at migrate time in the generated DO block.
   - Replacing an existing PK with a natural key is refused.
   - Deferred: a `--primary-key` CLI flag and honoring REPLICA IDENTITY USING INDEX.
3. **Health = structural catalog checks, no fingerprint hashes yet.**
   - Compare `tgargs` against `pg_index`, count per-table-function references by `tgfoid`, count Threadline triggers per table, and read `tgenabled`.
   - No marker is needed for overrides: an override is legal only on a table with no PK, so catalog state disambiguates.
   - Health never advises on indexes. Performance guidance lives in `guides/audit-indexing.md`.
   - Deferred: pgtrigger-style fingerprint/OUTDATED reconciliation.
4. **Row-history index ships in install**, not only in docs. This overrides SUMMARY Reconciled Decision 5.
   - Name: `audit_changes_row_history_idx` on `(table_schema, table_name, table_pk, captured_at DESC, id DESC)`.
   - Upgraders get a documented `CREATE INDEX CONCURRENTLY` migration.
   - Carbonite, PaperTrail, Audited and supa_audit all ship their row-lookup index by default. Without it, `history/3` scans every audit row for the table.

## v1.42 Requirements

### Naming and collision safety (security)

- [x] **NAME-01**: Every identifier Threadline generates (trigger, function, per-table function, migration module/file) is ≤ 63 bytes and is never silently truncated by PostgreSQL. An invalid or oversized host identifier raises an error that names the derived identifier and its byte count, not "storage schema".
- [x] **NAME-02**: Two audited tables never share a per-table capture function. This includes same-named tables in different schemas (`public.billing_invoices` vs `billing.invoices`) and long names sharing their first 36 bytes. Each table applies only its own redaction rules.
- [x] **NAME-03**: Regenerating triggers on an existing 0.10.x install never creates a second Threadline trigger on a table. Trigger names that fit stay byte-identical.
- [x] **NAME-04**: Dropping or cleaning up one table's capture objects never drops or disables another table's trigger. No `CASCADE` from an ambiguous name; a function is dropped only when no trigger references it.
- [x] **NAME-05**: Name derivation is property-tested with StreamData: ≤ 63 bytes, deterministic, injective under generators biased toward `_`-split pairs, case pairs and long shared prefixes. A golden literal-name test freezes the format.

### Capture (write side)

- [x] **CAP-01**: A table whose single-column primary key is not named `id` (integer, uuid or text) is captured with its real key in `table_pk`.
- [x] **CAP-02**: A table with a composite primary key is captured with every key column in `table_pk`, with no configuration.
- [x] **CAP-03**: Migrating triggers for a table with no primary key and no `primary_key:` override fails at migrate time, before any host write. The message names the table and the override option.
- [x] **CAP-04**: Triggers installed before 0.11.0 keep capturing exactly as before until the adopter regenerates them. A host write never fails because of a missing or changed key; the key falls back to `{}` rather than raising.
- [x] **CAP-05**: Configuring a primary-key column in `mask` or `exclude` is refused before any capture, with a message naming the column.
- [x] **CAP-06**: Per-row trigger overhead after the change is measured and stays within noise of 0.10.x on the reference benchmark. It must not reintroduce a per-row catalog lookup.

### Reads (history agrees with capture)

- [x] **READ-01**: `history/3`, `row_history_query/3` and `as_of/4` return captured rows for tables with integer primary keys (default Ecto bigserial). This fixes the existing text-vs-integer mismatch.
- [x] **READ-02**: A developer can read the history of a composite-key row by passing a keyword list or map of its key columns. A missing, extra or mismatched key set raises an `ArgumentError` that names the expected columns.
- [x] **READ-03**: Rows captured by pre-0.11.0 triggers and rows captured by regenerated triggers are both returned by a single history call for the same row.
- [x] **READ-04**: Operator-surface links for composite-key rows show no row link rather than a link to the wrong row. This is a minimal guard; UI design stays parked.

### Configuration and generators

- [x] **CONF-01**: An adopter can declare `primary_key: [...]` for a table without a primary key. It is validated for empty lists, invalid names, duplicates and overlap with redaction, and enforced at migrate time against a qualifying unique index. History reads for that table use the same declared columns.
- [x] **CONF-02**: `mix threadline.gen.triggers` writes migrations to the repo's configured migrations path, the same resolution `mix threadline.install` uses, and accepts `--migrations-path`. Rerun detection reads the same directory.

### Row-history index

- [x] **IDX-01**: New installs create `audit_changes_row_history_idx`, and existing adopters get a copy-paste `CREATE INDEX CONCURRENTLY` migration. An EXPLAIN-based test proves `history`/`as_of` use the index.

### Health checks

- [x] **HLTH-01**: `Threadline.Health.trigger_findings/1` returns structured findings (`code`, `severity`, `schema`, `table`, `message`, `details`). Every message names the table and the exact fix command. It is PgBouncer-safe and readable by a non-owner role.
- [x] **HLTH-02**: A pre-0.11 trigger on an `id`-keyed table is reported as a `:legacy_trigger_no_pk_args` **warning**.
- [x] **HLTH-03**: A trigger whose recorded key columns differ from the table's live primary key (or from a still-qualifying override index) is reported as a `:pk_drift` **error**.
- [x] **HLTH-04**: One per-table capture function referenced by more than one table's trigger is reported as a `:shared_capture_function` **error**.
- [x] **HLTH-05**: More than one Threadline trigger on a table is reported as a `:duplicate_capture_trigger` error, and a disabled Threadline trigger as a `:capture_trigger_disabled` error. Disabled triggers are no longer counted as covered.
- [x] **HLTH-06**: `mix threadline.verify_coverage` exits non-zero on any error finding for an expected table, and only prints warnings. `mix threadline.health.coverage` shows findings in text and JSON.

### Adopter twins

- [x] **TWIN-01**: The example Phoenix app and the hex evaluator include audited tables with a non-`id` PK, a composite PK, a join table using `primary_key:`, same-named tables in two schemas, and a ≥ 60-byte name. Their trigger migrations are generated by the task itself, and each shape's history round-trips.

### Release

- [x] **REL-01**: `bump-minor-pre-major` is `true` before the first releasable commit of the milestone.
- [x] **REL-02**: An upgrade guide explains:
  - regenerating triggers;
  - adding the row-history index concurrently;
  - backfill SQL for INSERT/UPDATE rows captured as `{"id": null}`;
  - which pre-0.11 rows cannot be recovered (DELETEs, redacted keys);
  - a CHANGELOG security note for installs where two tables shared a capture function.

  Doc-contract tests pin the regenerate and index steps.
- [x] **REL-03**: 0.11.0 is released through release-please from a squash-landed PR with a clean title. `main` CI is green on the released SHA, with no open PRs or stray branches left.

## Future Requirements (deferred)

- Fingerprint-based "outdated trigger" reconciliation (pgtrigger-style), and comparing function bodies against templates.
- A backfill mix task for historic `{"id": null}` rows. v1.42 documents the SQL instead.
- A `--primary-key` CLI flag (only as sugar that must equal config), and honoring `REPLICA IDENTITY USING INDEX`.
- Composite-key row routing in the operator UI.
- Capture for tables with no unique identity at all.
- Partitioned tables, RLS tenancy, multiple repos (signal-gated).
- A `--strict` health mode that fails on warnings.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Operator-UI design work | Parked until 1.0.0 (MILESTONE-GUIDE §5) |
| Natural key replacing an existing PK | Natural keys change and would split history; conflicts with RowKey |
| Runtime catalog lookup of the PK on every row | Measured 2-4.7x trigger cost; resolved at migrate time instead |
| Rewriting historic `table_pk` rows | Audit rows are evidence; the upgrade guide offers opt-in SQL only |
| Supply chain, CI economy, PII scrub | v1.43 rung |
| DB-backed property tests beyond naming | v1.44 rung |
