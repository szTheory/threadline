## Warnings

### WR-01: PR template says the PR title is always the squash subject; with `COMMIT_OR_PR_TITLE` a single-commit PR squashes under its commit subject

**File:** `.github/pull_request_template.md:19`
**Issue:** The template says "The PR title becomes the squash subject, and its type decides whether merging cuts a release." The repo setting is `squash_merge_commit_title=COMMIT_OR_PR_TITLE` (verified via `gh api repos/szTheory/threadline`), and CONTRIBUTING.md:974 correctly says a single-commit PR squashes under its commit subject. A contributor who follows the template can title a single-commit PR `ci: …` while the commit is `fix(ci): …`. The squash subject is then `fix(ci): …`, so the PR cuts a release whenever it touches any residue or shipped path. That is the F1 failure this phase exists to close. The test at `changelog_contract_test.exs:306` checks the template only for type tokens, so it cannot catch the wrong mechanism.
**Fix:**
```markdown
The squash subject decides whether merging cuts a release. It is the PR title,
or the commit subject when the PR has a single commit, so set both. Check one:
```
Optionally, pin `"single commit"` (or `"commit subject"`) as an extra template needle in the D-09 test.

### WR-02: CONTRIBUTING "Ongoing releases" contradicts itself on what Release Please parses, and misstates when the PR body matters

**File:** `CONTRIBUTING.md:974` and `CONTRIBUTING.md:978`
**Issue:**
- Line 974 (new): "Release Please also reads the squash body and the PR body, so keep both free of paragraphs that start with a commit type."
- Line 978 (pre-existing, four lines below): "Release Please only parses the squash subject".

Both cannot be true, and line 974 is the accurate one for the squash body. RESEARCH Pitfall 1 shows 17.6.0 `splitMessages` splitting the message on `\n\n(?=type(scope)?: )`. With `squash_merge_commit_message=COMMIT_MESSAGES`, a commit body paragraph such as `fix(ci): …` becomes a second conventional commit.

The "PR body" half of line 974 is wrong. Release Please reads the PR body only through `preprocessCommitMessage` for `BEGIN_COMMIT_OVERRIDE`, and the PR body is not part of the squash message under `COMMIT_MESSAGES`. A type-prefixed paragraph in the PR body does nothing.

Line 974 also omits the other body trigger: a `BREAKING CHANGE:` footer in any commit body makes even a `ci:` squash releasable, as a major bump. D-15 calls this out for PR B, but the contributor rule does not.

The D-06 test pins only the substrings `must merge under a releasable squash subject` and `` `BEGIN_COMMIT_OVERRIDE` ``. The "only parses the squash subject" clause is therefore free to change.
**Fix:**
```markdown
This repository squashes with the PR title, except that a single-commit PR squashes under its commit subject, so set both. Release Please also parses the squash body (the PR's commit messages), so keep it free of paragraphs that start with a commit type and of `BREAKING CHANGE` footers. The PR body matters only through `BEGIN_COMMIT_OVERRIDE`.
```
At line 978, replace "Release Please only parses the squash subject" with "Release Please reads the squash commit, not `CHANGELOG.md`".

### WR-03: PR template classifies docs as "Ships nothing to adopters", but docs ship in the Hex package

**File:** `.github/pull_request_template.md:21-22`
**Issue:**
- `README.md`, `CHANGELOG.md`, `CONTRIBUTING.md` and `guides/` are in `package()[:files]`, so they are in the tarball and on HexDocs.
- This phase's own CHANGELOG block (CHANGELOG.md:24-42) lists documentation changes as the content of the next release.
- A guides-only PR therefore matches both checkboxes, and they give contradictory instructions: `docs:` and no prose, versus `fix:` and prose.

CONTRIBUTING.md:971 is more careful ("CI, tests, tooling, planning … or as `docs:` for documentation only"), but the template drops the distinction. The policy D-07 intends is that documentation-only changes merge as `docs:` and roll into the next release's prose. The template should state that policy, not claim that docs ship nothing.
**Fix:**
```markdown
- [ ] Ships no code to adopters (CI, tests, tooling) or changes documentation only: the title uses `ci:`, `test:`, `chore:` or `docs:`, never `fix(ci):`.
- [ ] Changes the library code or dependency requirements: the title uses `feat:`, `fix:`, `perf:` or `deps:`, and this PR adds prose under `## Unreleased — highlights` in `CHANGELOG.md`.
```
Apply the same wording to the CONTRIBUTING.md:971-972 bullet labels.

### WR-04: The new Unreleased lead sentence becomes false when the next releasable change rolls in

**File:** `CHANGELOG.md:24-26`
**Issue:** D-13 requires this prose to roll forward into the next real release. The lead paragraph reads "Threadline's library code and dependency requirements are unchanged since 1.1.0. The changes are to the documentation … and to maintainer-only Mix aliases." This is a whole-release claim, not a line item. The next `feat:`/`fix:`/`deps:` PR will add its own section under the same heading. If it does not also rewrite this lead, the dated 1.1.1/1.2.0 entry opens with a false statement. No test catches that: the newest-entry contract checks only that some prose exists.
**Fix:** Make the lead a statement that stays true as entries are added, and keep the specific facts under `### Changed`. For example:
```markdown
## Unreleased — highlights

This section collects changes since 1.1.0. So far they touch only the
documentation that ships with the package and maintainer-only Mix aliases;
rewrite this paragraph when a library change lands.
```
Alternatively, add a line to CONTRIBUTING.md "Ongoing releases" telling the next releasable PR to rewrite the lead paragraph.

### IN-03: The "every file it touches" wording may overstate the guard for renames out of a shipped directory (unverified upstream detail)

**File:** `CONTRIBUTING.md:976`, `test/threadline/release_artifact_contract_test.exs:274-279`
**Issue:** Release Please takes a commit's files from GitHub's PR changed-file list. For a git-detected rename, that list reports only the new `path`. Moving a shipped module out of `lib/` into `test/support/` (an adopter-visible removal) would then look like a commit touching only `test/`, and the backstop would drop it even under `feat!:`. I inferred this from GitHub's `PullRequestChangedFile.path` semantics and have not reproduced it against 17.6.0. The type rule still governs such commits, but the doc's "every file it touches" is the git view, not Release Please's view.
**Fix:** Confirm against `src/github.ts` at v17.6.0 (the files query). If confirmed, add one clause to CONTRIBUTING: "a rename is seen under its new path only".

### IN-04: `tracked_files/0` crashes with a bare MatchError and discards git's stderr

**File:** `test/threadline/release_artifact_contract_test.exs:520-523`
**Issue:** `{out, 0} = System.cmd("git", ["ls-files", "-z"], cd: File.cwd!())` turns any git failure (no repository, `safe.directory` refusal in a container, git missing) into `MatchError` with no diagnosis. The rest of this module uses `flunk/1` with the command output.
**Fix:**
```elixir
case System.cmd("git", ["ls-files", "-z"], cd: File.cwd!(), stderr_to_stdout: true) do
  {out, 0} -> String.split(out, <<0>>, trim: true)
  {out, status} -> flunk("git ls-files -z failed (#{status}): #{out}")
end
```

### IN-05: The type rule is framed as squash-only, but the repository also allows merge commits and rebase merges

**File:** `CONTRIBUTING.md:969`, `.github/pull_request_template.md:19`
**Issue:** `gh api` shows `allow_merge_commit=true` and `allow_rebase_merge=true`. A rebase-merged PR lands every commit with its own subject, so one `fix(ci):` commit among several `ci:` commits cuts a release, and the "squash subject" guidance does not cover it. The setting predates this phase, and the deferred PR-title check notes the bypass, but the new rule text presents squash as the only path.
**Fix:** Either add "Merge with squash; a rebase or merge commit makes every commit subject count", or disable rebase and merge-commit merges in the repository settings (a maintainer decision).
