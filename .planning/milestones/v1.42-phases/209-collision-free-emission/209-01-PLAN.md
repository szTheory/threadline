<objective>
Make any PostgreSQL identifier-truncation NOTICE (SQLSTATE 42622) raised during the test suite fail the suite, with a positive control and a canary proving the failure path (roadmap SC4; D-09, D-10).

Purpose: truncation is how per-table capture function names collided in older releases. This guard lands first so every later plan in this phase runs under it, and so a regression that reintroduces silent truncation fails CI. It is test infrastructure only; nothing ships.
Output: `Threadline.Test.NoticeGuard`, test_helper wiring, controls, canary contract, and the one existing deliberate truncation fixed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| generated DDL -> PostgreSQL identifier limit | an identifier over 63 bytes is silently truncated by PostgreSQL (NOTICE 42622), which is how two tables' capture functions once resolved to one object |
| test suite -> CI verdict | the guard turns a silent NOTICE into a failed CI run |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-209-01 | Tampering | any future generator change that emits an overlong identifier | high | mitigate | NoticeGuard fails the suite on any 42622 through the test repo (Task 1); canary proves the non-zero exit (Task 2) |
| T-209-02 | Repudiation | guard silently detached or blind (handler raised, client_min_messages raised) | medium | mitigate | handler body rescued; verify!/1 fails when the handler is not attached; boot asserts client_min_messages = notice (Tasks 1-2) |
| T-209-03 | Tampering | a test hiding a real product truncation by draining it | low | accept | take/0 drains only the calling process's hits; tests that drain must assert the exact expected hit (documented in the moduledoc); code review covers misuse |
| T-209-04 | Information disclosure | guard coverage gaps (raw Postgrex sessions, nested mix, example app repo) | low | accept | documented in the moduledoc; the static identifier-length assertion added later in this phase covers generator output independently |
</threat_model>
