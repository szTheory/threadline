<objective>
Make regenerating triggers over a 0.10.x install unable to move a sibling table onto another table's redaction rules: add the migrate-time post-condition guard, and prove every upgrade order on real PostgreSQL (roadmap SC1 upgrade half, SC3; NAME-02, NAME-04; D-05, with D-01 and D-04 behavior under upgrade).

Purpose: in 0.10.x, public.billing_invoices and billing.invoices shared one function name. Regenerating only the table that keeps the legacy name would rewrite that shared body and silently switch the sibling's rules. The guard turns that into an atomic, explained failure; the safe orders pass.
Output: the guard builder and its emission, real-PG upgrade scenario tests. The moduledoc subsection explaining the migrate-time error and the safe orders is plan 05 (split out with the other adopter-facing docs to keep plans 03 and 04 inside the context budget).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| 0.10.x catalog state -> new migration | a new migration rewrites or re-points capture functions another table's trigger may still use |
| migrate-time guard -> adopter deploy | a raise stops `mix ecto.migrate` in the adopter's deploy |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-209-15 | Information disclosure | regenerating the legacy-keeping table rewrites the shared body, switching the sibling to weaker or different redaction rules | critical | mitigate | post-condition guard raises after all re-points; one DDL transaction rolls everything back (Task 1 real-PG test asserts body and tgfoid unchanged) |
| T-209-16 | Denial of service | guard failing a production deploy | medium | accept | maintainer-accepted (D-05): CI migrates a fresh DB first; the HINT gives the exact fix; safe orders documented in the gen.triggers moduledoc (plan 05) |
