# Phase 210 Plan 05: PK-Agnostic Capture — Benchmark, Adopter Docs, Phase Gate Summary

**An in-server A/B benchmark against a frozen 0.10.2 capture body (with a pg_index-per-row sensitivity control proving the bench can detect a regression) records the current body within 1.07x of baseline on every operation while the control comes in at 1.5-2x, adopter docs and CHANGELOG now describe primary-key discovery and the `primary_key:` override, and Phase 210 closes on a fully green `mix ci.all`.**

## Accomplishments

- `bench/pk_capture_bench.exs` installs the frozen 0.10.2 body, the current global capture body, and a sensitivity-control body (derived from the fixture by replacing its three `id`-extraction assignments with a per-row `pg_index`/`pg_attribute` lookup, asserting exactly 3 matches or raising) as three differently named functions in one database, then times `INSERT ... SELECT generate_series(1, 50000)`, `UPDATE` of every row, and `DELETE` of every row on a fresh table per variant per rep, alternating variant order across 5 reps, via a server-side `bench_elapsed_us(sql)` helper timed with `clock_timestamp()`
- Recorded result (`bench/baselines/pk_capture_bench.md`): current/baseline within 1.03-1.07x on every operation (bar: ≤1.10x); catalog/baseline at 1.54-1.95x on every operation (bar: ≥1.25x, proving the bench's sensitivity); a two-column composite-key table (current body only) at 0.96-1.08x of the current body's single-key median
- `bench/fixtures/threadline_capture_changes_v0_10_2.sql` is pinned byte-for-byte against `Threadline.Test.LegacyTriggerSQL.v0_10_2_install_function/2` by a new real-PG test in `legacy_trigger_pk_fallback_test.exs`, so the frozen baseline copy cannot silently drift from the fixture the rest of Phase 210's tests already trust
- `mix verify.bench` now runs `pk_capture_bench.exs`; it stays out of `mix ci.all`, matching D-07's "not a CI gate" decision
- `mix threadline.gen.triggers`'s moduledoc gained a "Primary keys" section (discovery, supported types, the `primary_key:` override with a `posts_tags` example naming `config/config.exs`, the has-a-primary-key and mask/exclude refusals, and the `{}`-on-unresolved behavior); the configuration guide's `trigger_capture` row and the CHANGELOG's Unreleased Breaking changes/Required action/Added sections now describe the same surface, including that the `{"id": null}` → `{}` change affects only rows that never had a usable identity and that a refused key type keeps its existing trigger until regenerated
- Phase-gate `mix ci.all` surfaced one Dialyzer `unmatched_return` (a validated-identifier return discarded inside a `try` in `trigger_capture_config.ex`, from Plan 04) and two Credo `--strict` findings (an unaliased nested module and an over-quoted string literal, both in Plan 03/04 test files) — all three are inside files Phase 210 already owns, fixed in place, and the full gate is now green: credo clean, dialyzer clean, xref no cycles, `verify.test` 2063 tests/0 failures/1 excluded, `verify.threadline` 1/1 covered, `verify.example` 117 tests/0 failures, `verify.example_browser` 318 passed/26 skipped (the pre-existing, healthy baseline)

## Decisions Made

- The sensitivity-control body is generated by regex-patching the frozen fixture text rather than hand-written, and the patch asserts exactly 3 replacements or raises — this is the concrete mechanism behind T-210-16's mitigation (a benchmark that silently stopped seeing the injected slowdown would otherwise report a false PASS)
- Variant order alternates per rep (forward on odd reps, reversed on even) so within-run machine drift does not systematically favor one variant over another
- Per the plan's explicit instruction ("rerun once to rule out machine noise... do not loosen the bar"), the bar failed once at full rows/reps (delete ratio 1.125 vs 1.10) before the recorded, passing rerun; the bar and sensitivity threshold were never changed
