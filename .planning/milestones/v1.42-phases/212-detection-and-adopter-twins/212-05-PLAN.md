Give the example Phoenix app every TWIN-01 table shape:

Placement decision (Claude's discretion, recorded here):
- The fixtures live in `priv/shape_fixtures/migrations`, which test/test_helper.exs migrates up for the ExUnit suite and down in `ExUnit.after_suite`.
- The e2e runner (`e2e/run-e2e.sh`) runs `mix ecto.migrate` against the same `threadline_phoenix_test` database. A default-path migration would put the fixture tables on `/audit/coverage`, the redaction screen and the seeded coverage evidence.

Config decision:
- The `primary_key:` override (D-19) and the two `mask:` entries live in `config/test.exs`, not `config/config.exs`. They are omitted when `THREADLINE_E2E=1`.
- Reason: Elixir `Config` deep-merges keyword lists but replaces maps, and test.exs (and dev.exs) already set `:trigger_capture` `tables:` maps, so an entry in config.exs would be dead in the test env.
- The browser lane (which exports `THREADLINE_E2E=1`) must see no fixture config on its redaction screen (D-22).
- The override is still declared as app config, which is D-19's substance.

Output: the fixture DDL migration, the generated trigger migration, config, test_helper wiring, schema modules, round-trip and contract tests.
</objective>

<interfaces>
- `mix threadline.gen.triggers --tables a,b --migrations-path DIR` writes one `<version>_<name>.exs`. The name is hashed when the table list is long. Rerun detection and ordinal naming (`TriggerMigration.scan/1`, `resolve_name/2`) read only DIR.
- `Threadline.history(schema_module, id, repo: Repo)` accepts a bare scalar, or a keyword list or map naming every key field. For a `primary_key:` override table, the override's declared columns are the accepted keys. `table_schema` comes from the schema's `@schema_prefix` (default "public").
- The example app's storage schema is `"threadline"` (config/config.exs). History reads use it automatically.
- ExUnit here uses the Ecto SQL sandbox (`ThreadlinePhoenix.DataCase`). Capture triggers fire inside the sandbox transaction, so a test's audit rows and its history read share one transaction.
- `Ecto.Adapters.SQL.Sandbox` `:auto` mode, used by test_helper before `mode(:manual)`, runs migrations outside any sandbox transaction.
- The browser lane runs `e2e/run-e2e.sh`, which exports `MIX_ENV=test` and `THREADLINE_E2E=1` and runs `mix ecto.migrate` (default path only), then `mix demo.reset` and `mix demo.seed`.
</interfaces>
