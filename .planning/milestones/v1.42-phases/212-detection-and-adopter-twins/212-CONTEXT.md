# Phase 212: Detection and Adopter Twins - Context

**Gathered:** 2026-09-26
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase has two parts:
- A `mix` command tells adopters, with the exact fix, when a table's capture is stale, drifted, shared, duplicated or disabled.
- The adopter twins (the example Phoenix app and the hex evaluator) prove that every table shape works end to end.

It delivers:
- `Threadline.Health.trigger_findings/1`, a catalog-only check that is PgBouncer-safe and works for a non-owner role;
- five finding codes;
- findings wired into `mix threadline.verify_coverage` (gate) and `mix threadline.health.coverage` (viewer, text and JSON);
- the new table shapes in both twins, with trigger migrations generated by `mix threadline.gen.triggers` and a history round-trip for each shape.

Requirements: HLTH-01..06 and TWIN-01.

Out of scope:
- a `--strict` warnings-fail mode (already its own ROADMAP backlog item)
- operator-UI work (parked until 1.0.0)
- the 0.11.0 upgrade-guide prose (Phase 213). This phase records the facts Phase 213 must say.
- widening the PK type allowlist

</domain>

<decisions>
## Implementation Decisions

### Carried forward (locked; do not reopen)
- **Unresolved keys (210 D-04):** both `{}` and `{"id":null}` mean "unresolved".
- **Legacy no-arg trigger on a table whose PK is not exactly `(id)` (210 D-04):** this is an **error-level** finding, detected from the catalog (`tgargs`, `pg_index`), never by scanning `audit_changes`.
- **Set equality for every key comparison (210 D-16):** order carries no meaning.
- **Override qualification (210 D-17):** the override must match a unique index that is valid, ready, immediate, non-partial and non-expression, whose key columns equal the declared set exactly and are all NOT NULL.
- **Override config (210 D-14/D-18):** read through `Threadline.Capture.TriggerCaptureConfig.load/0`, the same loader capture uses.
- **Shared function fix (209-CONTEXT):** the fix for a shared per-table function is to regenerate **all** colliding tables in one `mix threadline.gen.triggers --tables a,b` run, never one at a time.
- **Global function (0.10.2 and later):** the default-mode global function `threadline_capture_changes` is shared **by design**.

### Findings API (public, additive)
- **D-01:** `trigger_findings/1` returns `[%Threadline.Health.Finding{}]`.
  - The struct has `@enforce_keys` on `code`, `severity`, `schema`, `table`, `message` and `details` (a map), plus `@type t`.
  - This follows the repo's precedent for public read models such as `ActorRef`, `AuditContext` and `LinkedChange`.
  - **Reversibility:** costly. Field names become public; adding fields later is additive.
- **D-02:** Options:
  - `:repo` (required).
  - `:schema`, which takes a string or a list of strings.
  - **With `:schema` omitted, the check covers every non-system schema.** It excludes `pg_catalog`, `information_schema`, `pg_toast*` and `pg_temp*`, and it also excludes the configured Threadline storage schema's own audit tables.
  - This deliberately differs from `trigger_coverage/1`'s `"public"` default, because the twins' same-named-tables-in-two-schemas shape and cross-schema function sharing cannot be seen one schema at a time. Document the difference in the moduledoc.
  - The shared-function check always runs over the whole catalog. `:schema` only filters which findings are **returned**, by the finding's table schema.
  - **Reversibility:** costly. Narrowing the default later would silently drop findings.
- **D-03:** A trigger is "Threadline's" when either of these holds:
  - its name starts with `threadline_audit_`;
  - its function (`pg_trigger.tgfoid` → `pg_proc.proname`) is exactly `threadline_capture_changes`, or starts with `threadline_capture_changes_`.

  Taking the union catches a copied or renamed trigger that still calls a Threadline function.
  - `trigger_coverage/1` keeps its name-prefix identification and gains only D-05's enabled filter. Changing coverage identification further is not needed for any requirement.
  - Use a literal `LIKE` with an `ESCAPE` for the underscore, pinned by a test against the `Naming` module's prefixes.
- **D-04:**
  - **Order:** findings are sorted deterministically by `{schema, table, code}`, and the moduledoc documents this.
  - **Multiplicity:** one table may produce several findings; there is no short-circuit.
  - **Severity:** exactly `:error` or `:warning`, with no `:info`.
- **D-05:** (behaviour change, CHANGELOG) `trigger_coverage/1` no longer counts a Threadline trigger as covered when `tgenabled` is `'D'` (disabled) or `'R'` (replica-only). HLTH-05 requires this.
  - The change goes under "Breaking changes" in the CHANGELOG, because a `verify_coverage` CI gate can turn red on upgrade. Phase 213's upgrade guide must repeat it.
  - **Reversibility:** one-way in practice. Reverting would flip adopters' CI a second time.
- **D-06:** Emit telemetry event `[:threadline, :health, :findings_checked]` with measurements `%{errors: n, warnings: n}`.
  - It is a separate event, so existing `[:threadline, :health, :checked]` subscribers are unaffected. It goes through `Threadline.Telemetry`, like `emit_health_checked`.
  - **Reversibility:** costly. The event name and its keys become public.
- **D-07:** A malformed `:trigger_capture` config makes `trigger_findings/1` raise, the same `ArgumentError` that `TriggerCaptureConfig.load/0` raises.
  - That is consistent with how gen.triggers and reads treat the same config, and it adds no new finding code.
  - The Mix tasks surface it through `Mix.raise`, as they already do for setup errors.

### Detection semantics per code (catalog only)
- **D-08:** reading trigger arguments. Read `pg_trigger.tgargs` as bytea and split it in Elixir on NUL. PostgreSQL documents it as NUL-terminated strings, so drop the trailing empty element.
  - Do not parse `pg_get_triggerdef` text.
  - `tgnargs` gives the count.
- **D-09:** `:legacy_trigger_no_pk_args` (warning, HLTH-02). A Threadline trigger with `tgnargs = 0`, on a table whose expected key set (D-10) is exactly `{"id"}`.
  - Fix: `mix threadline.gen.triggers --tables <schema.table>`, then `mix ecto.migrate`.
- **D-10:** `:pk_drift` (error, HLTH-03) means the recorded key set is not equal to the expected key set.
  - **Recorded key set:** the `tgargs` columns. For `tgnargs = 0` it is `{"id"}`, the legacy implicit key from 210 D-01, but only when the live key is not exactly `(id)`. So a legacy no-arg trigger on a non-`(id)` table is `:pk_drift` at error level, which fulfils 210 D-04's hand-off with no extra code.
  - **Expected key set** is the set `mix threadline.gen.triggers` would record if run now:
    1. the configured `primary_key:` override, if a D-17-qualifying index exists;
    2. otherwise the live primary key, from `pg_index` with `indisprimary`, first `indnkeyatts` entries, attnames;
    3. otherwise none.
  - **Special cases, each reported as `:pk_drift` with a `details.reason`:**
    - the key would be refused at regeneration: no PK and no override, an override with no qualifying index, or an override on a table that has a PK;
    - a recorded column no longer exists or was renamed.
  - The message states the recorded set, the expected set and the reason, plus the fix: the `config/config.exs` override snippet or the index requirement where relevant, then `mix threadline.gen.triggers --tables <schema.table>`.
- **D-11:** `:shared_capture_function` (error, HLTH-04). A per-table function (`proname LIKE 'threadline\_capture\_changes\_%'`, never the bare global `threadline_capture_changes`) referenced by Threadline triggers on more than one table, counted as `count(DISTINCT tgrelid) > 1`.
  - One finding is emitted per affected table.
  - The message names every table that shares the function, and the one fix command that regenerates them all: `mix threadline.gen.triggers --tables a,b`.
- **D-12:** `:duplicate_capture_trigger` (error, HLTH-05). More than one Threadline trigger (by D-03) on one table.
  - The message names each extra trigger, and the fix is `DROP TRIGGER "<extra>" ON "<schema>"."<table>";`, then `mix threadline.gen.triggers --tables <schema.table>` to confirm the canonical trigger.
  - The canonical trigger is the one named `Naming.trigger_name/1`.
- **D-13:** `:capture_trigger_disabled` (error, HLTH-05). `tgenabled` is `'D'` or `'R'`. `'O'` and `'A'` are healthy.
  - The message says which state was found. The fix is `ALTER TABLE "<schema>"."<table>" ENABLE TRIGGER "<name>";` for `'D'`, or `ENABLE ALWAYS TRIGGER` for `'R'`.
  - `'R'` fires only under `session_replication_role = replica`, so ordinary application writes are not captured.
- **D-14:** message format. Every message names the qualified table (`schema.table`) and the exact fix command, as HLTH-01 requires. Use the qualified form everywhere, including `public`, so the command pastes correctly.

### PgBouncer and non-owner safety (SC1)
- **D-15:** queries. Use independent, parameterized `SQL.query!/3` catalog reads, following today's `health.ex` pattern:
  - no `SET`, temp tables, advisory locks or named prepared statements;
  - only world-readable catalogs: `pg_trigger`, `pg_class`, `pg_namespace`, `pg_index`, `pg_attribute` and `pg_proc`.

  A research probe on 2026-09-26 confirmed that a zero-grant role can read these.
- **D-16:** tests.
  - The non-owner test is new, because no `CREATE ROLE` precedent exists in `test/`. The test module creates a uniquely named `NOLOGIN` role with no grants, runs the check under `SET LOCAL ROLE` inside a transaction, and drops the role in `on_exit`.
  - The PgBouncer case goes into the existing `pgbouncer_topology` lane: a tagged test calling `trigger_findings/1` through the pooler.
  - Any role DDL the lane needs goes in `priv/ci/topology_bootstrap.exs`, which runs over a direct connection.

### Mix tasks (HLTH-06)
- **D-17:** `verify_coverage`
  - It exits non-zero, via the existing `exit({:shutdown, 1})` path, on any `:error` finding for a table in its expected-table positive list.
  - It prints warnings but never fails on them.
  - Error findings on tables outside the list are printed under a "not gated" heading and never fail the task, so an integrity problem on an unlisted table is visible without breaking the positive-list contract.
  - `Mix.raise` stays reserved for setup and config failures.
  - It keeps the existing `--schema=NAME` flag and its default, and passes the schema through to `trigger_findings/1`.
- **D-18:** `health.coverage`
  - It is still a viewer and always exits 0.
  - Text output gains a separate FINDINGS section after the existing table, with columns SEVERITY, CODE, TABLE and MESSAGE.
  - `--json` gains an **additive** `findings` key: a list of objects with string `code` and `severity`, plus `schema`, `table`, `message` and `details`. Existing keys and their shape are unchanged.
  - It keeps `--schema=NAME`.
  - **Reversibility:** costly. The JSON key becomes public, but it is additive.

### Adopter twins (TWIN-01)
- **D-19:** shape fixtures. The shapes are a clearly labelled fixture set, not new help-desk domain tables. A 60-byte name and same-named tables in two schemas have no honest help-desk story.
  - **Example app:**
    - a migration creating `shape_*` tables, commented as TWIN-01 contract fixtures;
    - a non-`id` PK (text or uuid code PK);
    - a composite PK;
    - a join table with no PK and a unique index, configured with `primary_key:` in the example app's `config/config.exs`;
    - a same-named table in `public` and in a host-owned schema created by `CREATE SCHEMA IF NOT EXISTS` (e.g. `shapes`, never the Threadline storage schema);
    - a table name of at least 60 bytes.
  - **Hex evaluator:** its own minimal fixture tables with the same shapes, local to `priv/ci/hex_evaluator`. It must not share migrations with the example app, because the evaluator is a separate project that resolves `:threadline` from the rehearsal registry.
- **D-20:** generated migrations.
  - Trigger migrations for the fixtures are produced by running `mix threadline.gen.triggers` in each twin, then committed.
  - A contract test pins them: it regenerates to a temp directory and asserts the migration body matches the committed file. File timestamps and names are normalized. On failure, the message prints the exact regenerate command.
- **D-21:** round-trip assertions.
  - **Example app (primary):** ExUnit tests insert, update and delete each shape and assert that `Threadline.history/3` returns the rows. Composite rows use a keyword list or map id, the override table uses its declared columns, and the two-schema table checks that each schema's history stays separate.
  - **Hex evaluator:** a thin mirror of the same round trips.
  - Both twins also assert that `trigger_findings/1` returns no error findings for their fixtures, which exercises health against real generated migrations.
- **D-22:** browser lane. The fixture tables stay out of seeds and out of every operator-surface query path.
  - The screenshot baselines are frozen and never regenerated.
  - The phase gate must show both results unchanged:
    - `ci.all`'s browser line at 318 passed / 26 skipped / 0 failed;
    - a local `mix verify.example_browser` run with the same 8 known screenshot failures and no ninth.
  - If a fixture table changes any rendered page, that is a regression to fix, never a baseline to regenerate.

<specifics>
## Specific Ideas

- SC2 needs one real-PG fixture per code, each with a clean negative control. For example:
  - a legacy trigger on an `id` table gives only the warning, while a regenerated trigger gives nothing;
  - a disabled trigger gives the finding, and re-enabling it gives nothing.
- A `'R'` (replica-only) trigger gets its own test case, because it is the silent-loss mode.
- `:shared_capture_function` can be seeded by pointing a second table's trigger at the first table's per-table function.

</specifics>

## Deferred Ideas

- A `--strict` mode where warnings fail the gate (existing ROADMAP backlog item).

- An `:invalid_config` finding code, so health degrades instead of raising on malformed `:trigger_capture` config.
- Showing findings in the operator UI (parked until 1.0.0).
