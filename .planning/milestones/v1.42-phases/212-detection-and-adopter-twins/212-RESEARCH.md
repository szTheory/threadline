## Summary

This phase has no external-package risk: every finding is a catalog query against `pg_trigger`/`pg_class`/`pg_namespace`/`pg_index`/`pg_attribute`/`pg_proc`, built with the exact SQL fragments `Threadline.Capture.PrimaryKeySQL` and `Threadline.Capture.TriggerSQL` already use to *install* triggers. The correct posture for `Threadline.Health.trigger_findings/1` is: **reuse, don't reinvent** — the override-qualification predicate, the PK-resolution `pg_index` join, and the "who else uses this function" query in `TriggerSQL.function_owner_guard/2` are all copy-adaptable into read-only `SELECT`s. I verified all five catalog mechanics locally against the project's own `threadline_test` database (session transcripts below): `tgargs` bytea decoding, `tgenabled` state transitions, and non-owner-role catalog readability. All three behaved exactly as CONTEXT.md's D-08/D-09/D-13/D-15 assume.

The riskiest part of this phase is not the catalog SQL — it's structural: (1) `CoveragePolicy` and the two Mix tasks currently know nothing about severities and must be extended without breaking `trigger_coverage/1`'s existing three-bucket contract; (2) the adopter twins' trigger migrations must, for the first time in this repo's hex_evaluator, be produced by running `mix threadline.gen.triggers` rather than hand-written literal SQL — the hex_evaluator's existing migrations (`posts`, governance schema) are **hand-authored strings that predate the generator**, so D-20's regenerate-and-pin-to-committed-file pattern has no existing analogue in `priv/ci/hex_evaluator/` (it does exist in `examples/threadline_phoenix/`, whose `20260527154557_...` migration was clearly `gen.triggers`-authored — same naming and body pattern as `Naming.migration_name/2` produces).

**Primary recommendation:** Build `trigger_findings/1` as a new module (`Threadline.Health.Findings` or similar) that borrows SQL fragments from `PrimaryKeySQL`/`TriggerSQL` by literal reuse (copy the predicate strings, cite the source lines, keep them lexically identical via a shared private helper if practical) rather than re-deriving equivalent-looking SQL. Wire it into the existing `verify_coverage`/`health.coverage` tasks additively. For the twins, follow the `examples/threadline_phoenix` precedent exactly: write fixture tables + config, run `mix threadline.gen.triggers --tables ...` for real, commit the output, and use `Threadline.Test.MigrationHarness` for the regenerate-diff contract test.

### Options (D-02) — schema defaulting differs from `trigger_coverage/1`

`Threadline.Health.trigger_coverage/1` defaults `:schema` to `"public"` — confirmed at `lib/threadline/health.ex:58` (`schema = Keyword.get(opts, :schema, "public")`). D-02 requires `trigger_findings/1` to default to **all non-system schemas** when `:schema` is omitted. This means `trigger_findings/1` cannot reuse `trigger_coverage/1`'s per-schema query shape unchanged — it needs a catalog query that either omits the schema predicate entirely (scanning all schemas) or unions across `CoverageSchemas.available/1`-style discovery, then filters the *returned* findings by schema afterward per the D-02 note ("`:schema` only filters which findings are returned"). `CoverageSchemas.available/1` (`lib/threadline/health/coverage_schemas.ex:39-51`) already has the system-schema exclusion pattern to imitate:

```sql
-- lib/threadline/health/coverage_schemas.ex:41-47 (VERIFIED, read this session)
SELECT DISTINCT schemaname
FROM pg_tables
WHERE schemaname <> 'information_schema'
  AND schemaname NOT LIKE 'pg\_%' ESCAPE '\'
ORDER BY schemaname
```

This excludes `information_schema` and `pg_*`, but D-02 additionally requires excluding `pg_catalog`, `pg_toast*`, `pg_temp*` (covered by the `pg\_%` pattern already, since `pg_catalog`/`pg_toast`/`pg_temp` all start with `pg_`) and the storage schema's own audit tables (excluded by table name, not schema name — the storage schema itself, e.g. `"threadline"`, is a normal user schema that may also contain host tables, so only its `audit_*`/`threadline_*` tables are excluded, via `StorageSchema.threadline_table?/1`, `lib/threadline/storage_schema.ex:158-161`, which checks table name against the `@threadline_tables` list, not schema).

## Detection Semantics — Exact SQL to Reuse (D-08..D-14)

All five catalog mechanics below were verified live against `threadline_test` on `localhost:5432` this session (see Verification Log at the end). None required a new extension or superuser.

### D-08: `tgargs` decoding

`pg_trigger.tgargs` is `bytea`, NUL-separated per argument, **with a trailing NUL after the last argument** (verified: a 2-arg trigger `research_probe_fn('a','b')` produced raw bytes `61 00 62 00` = `"a\0b\0"`). `convert_from(tgargs, 'UTF8')` **fails** in SQL for this exact reason — I reproduced `ERROR: invalid byte sequence for encoding "UTF8": 0x00` when attempting it, confirming D-08's explicit instruction to decode in Elixir, not via `pg_get_triggerdef` or `convert_from`. The correct Elixir-side approach:

```elixir
# Query tgargs as bytea (Postgrex returns bytea columns as raw Elixir binaries)
tgargs
|> :binary.split(<<0>>, [:global])
|> Enum.reject(&(&1 == ""))  # drops the trailing empty element from the final NUL
```

`tgnargs` (integer column) gives the count directly — no need to trust the split length; use it as a cross-check.

### D-09/D-10: PK drift and legacy no-arg trigger

The "expected key set" computation must mirror `PrimaryKeySQL.create_trigger_block/3`'s two branches (`lib/threadline/capture/primary_key_sql.ex:120-200` detected path, `:202-299` override path — both `[VERIFIED]`, read this session). The exact PK-resolution query to reuse read-only, verified against a composite-key table (`research_probe_t (a,b)` with `PRIMARY KEY (a,b)`):

```sql
-- Adapted read-only from lib/threadline/capture/primary_key_sql.ex:144-149 (VERIFIED)
SELECT array_agg(a.attname::text ORDER BY k.ord)
  FROM pg_index i
  CROSS JOIN LATERAL unnest(i.indkey::int2[]) WITH ORDINALITY AS k(attnum, ord)
  JOIN pg_attribute a ON a.attrelid = i.indrelid AND a.attnum = k.attnum
 WHERE i.indrelid = $1::regclass AND i.indisprimary AND k.ord <= i.indnkeyatts
```

Verified live: this returned `a` then `b` in declared order for the composite-PK probe table. `indnkeyatts` correctly excludes `INCLUDE` columns (per `PrimaryKeySQL`'s comment at line 65-66, `[CITED: lib/threadline/capture/primary_key_sql.ex:65-66]` — not independently re-verified with an `INCLUDE` column this session, but this is standard, well-documented PostgreSQL `pg_index` semantics `[ASSUMED: standard PG behavior, low risk]`).

The **override qualification predicate** (D-17 carryover from 210) to reuse verbatim is `PrimaryKeySQL.qualifying_index_predicate/0` (`lib/threadline/capture/primary_key_sql.ex:437-438`, `[VERIFIED]`):

```elixir
"i.indisunique AND i.indisvalid AND i.indisready AND i.indimmediate AND i.indpred IS NULL AND i.indexprs IS NULL"
```

This function is already `@doc false` public (not private) — "Shared text so a future `primary_key:` config override match reuses the identical predicate" (its own docstring, line 436). **`trigger_findings/1` should call `Threadline.Capture.PrimaryKeySQL.qualifying_index_predicate/0` directly**, not copy the string, so a future change to qualification rules cannot silently diverge between install-time enforcement and health detection.

The override *key-set equality* fragment to reuse is `PrimaryKeySQL.override_index_key_set_sql/0` (private, lines 305-312) — this is `defp`, not `@doc false` public, so either (a) it needs to become `@doc false` public like `qualifying_index_predicate/0`, or (b) `trigger_findings/1`'s catalog module re-derives the identical SQL text and a test pins the two against each other. Recommend (a): promote it alongside `qualifying_index_predicate/0` for the same reuse reason, since D-10's "expected key set" computation is precisely this fragment's job.

### D-11: shared capture function

Mirrors `TriggerSQL.function_owner_guard/2`'s query (`lib/threadline/capture/trigger_sql.ex:168-195`, `[VERIFIED]`) which already does:

```sql
-- lib/threadline/capture/trigger_sql.ex:182-188 (VERIFIED)
SELECT string_agg(format('%I.%I', n.nspname, c.relname), ', ' ORDER BY n.nspname, c.relname), ...
  FROM pg_trigger t JOIN pg_class c ON c.oid = t.tgrelid
  JOIN pg_namespace n ON n.oid = c.relnamespace
 WHERE t.tgfoid = fn AND t.tgparentid = 0 AND t.tgrelid <> owner
```

For `trigger_findings/1`, drop the "exclude this table's own oid" clause and instead `GROUP BY t.tgfoid HAVING count(DISTINCT t.tgrelid) > 1`, restricted to `proname LIKE 'threadline\_capture\_changes\_%' ESCAPE '\'` (per-table functions only — the D-11 exclusion of the bare global `threadline_capture_changes` function, which is shared by design per the carried-forward decision). `tgparentid = 0` is a real and necessary filter — it excludes the trigger PostgreSQL auto-clones onto each partition of a partitioned table, matching `TriggerSQL`'s own comment (line 116-119, `[CITED: lib/threadline/capture/trigger_sql.ex:116-119]`, not independently verified with a partitioned table this session, but load-bearing documented Postgres behavior — `[ASSUMED: standard PG partitioned-trigger cloning behavior]`).

Function identity resolution: `tgfoid` is `regproc`/oid; join to `pg_proc` for `proname`, and to `pg_namespace` via `pronamespace` for the function's schema. For the **default global function**, it lives in the configured storage schema (`StorageSchema.function/2`, `lib/threadline/storage_schema.ex:135-137`, qualifies with `StorageSchema.get/1`). For **per-table functions**, `TriggerSQL.per_table_function_name/2` (line 246-251) also qualifies via `StorageSchema.function/2` — so both live in the storage schema, never in the host table's own schema. This matters for D-11's message: name every affected table (which can be in any schema) plus the *one* shared function (which is always in the storage schema).

### D-12: duplicate trigger

`COUNT(*) FROM pg_trigger WHERE tgrelid = <table> AND tgparentid = 0` grouped/filtered to Threadline triggers by D-03's union predicate, `HAVING count(*) > 1`. The canonical trigger is `Naming.trigger_name/1` (`lib/threadline/capture/naming.ex:112-114`, `[VERIFIED]`) — every other Threadline-identified trigger on the table is "extra."

### D-13: disabled/replica trigger

`tgenabled` verified live via `ALTER TABLE ... DISABLE TRIGGER` → `'D'`, then `ENABLE REPLICA TRIGGER` → `'R'`, then `ENABLE ALWAYS TRIGGER` → `'A'`. Default (never touched) is `'O'`. All four single-character values match D-13's text exactly. `'D'` and `'R'` are unhealthy; `'O'` and `'A'` are healthy.

## Common Pitfalls

### Pitfall 1: Re-deriving SQL instead of reusing it
**What goes wrong:** A health-check query that "looks equivalent" to the install-time DO-block SQL but differs in an edge case (e.g., forgetting `tgparentid = 0`, or a different unique-index qualification rule) silently disagrees with what `gen.triggers` actually enforces, producing false positives/negatives on partitioned tables or edge-case overrides.
**Why it happens:** The DO-block SQL lives inline in PL/pgSQL string templates (`TriggerSQL`/`PrimaryKeySQL`), which is awkward to literally `import`/call from a read-only Elixir-side query — it's tempting to just write a "similar" query by hand.
**How to avoid:** Where a helper is already `@doc false` public (like `PrimaryKeySQL.qualifying_index_predicate/0`), call it directly. Where the needed fragment is currently `defp` (like `override_index_key_set_sql/0`), promote it to `@doc false` public rather than copy-pasting the SQL text, and add a test that would fail if the two diverge.
**Warning signs:** A `:pk_drift` false-positive against a table using a legitimate `primary_key:` override that `gen.triggers` itself would accept.

### Pitfall 2: `CoveragePolicy`/task changes breaking the existing three-bucket contract
**What goes wrong:** Extending `verify_coverage`/`health.coverage` for findings could accidentally change the meaning of `{:covered, name}` for tables with a disabled trigger (D-05's behavior change) in a way that also breaks the *existing* `trigger_coverage/1` test suite (`test/threadline/health_test.exs` has extensive coverage of the three-bucket policy, `[VERIFIED]` read this session).
**Why it happens:** D-05 is explicitly a breaking change to `trigger_coverage/1`'s covered/uncovered semantics (disabled/replica no longer counts as covered) layered on top of an already-tested, already-stable function.
**How to avoid:** Add the `tgenabled NOT IN ('D','R')` filter to `fetch_threadline_covered_tables/2` (`lib/threadline/health.ex:97-109`) as a surgical, isolated change, and update/extend `health_test.exs`'s existing describe blocks rather than writing all-new tests that might miss an existing assertion the old behavior satisfied.
**Warning signs:** `mix ci.all` going red on the existing `trigger_coverage/1` test suite for reasons unrelated to the new `:capture_trigger_disabled` finding itself.

### Pitfall 3: hex_evaluator fixture accidentally introducing `storage_schema` config
**What goes wrong:** Adding a same-named-tables-in-two-schemas fixture to the hex_evaluator, or any config needed for a `primary_key:` override, could tempt someone to add `config :threadline, storage_schema: ...` for consistency with the example app — this silently breaks `legacy_public_schema_test.exs`'s entire premise (see above).
**Why it happens:** The example app already sets a dedicated schema, so it's the "normal" pattern to reach for.
**How to avoid:** Explicitly note in the plan that hex_evaluator's `config/config.exs` must stay free of `:storage_schema`; any needed config addition is only `:trigger_capture` (for the `primary_key:` override) or `:ecto_repos`.
**Warning signs:** `legacy_public_schema_test.exs`'s first test (`"this fixture is still legacy-shaped..."`) starts failing.

### Pitfall 4: Assuming `ci.all` covers the hex evaluator and pgbouncer lanes
**What goes wrong:** SC1 (PgBouncer + non-owner) and SC4 (hex evaluator) verification is assumed satisfied because `mix ci.all` passed, when neither `verify.hex_evaluator` nor `verify.topology`/pgbouncer_topology is part of the `ci.all` alias.
**Why it happens:** `ci.all` is the "run everything" mental model, but this repo deliberately keeps release-lane and topology-lane checks separate (documented at `mix.exs` lines 138-143, 156-161, `[VERIFIED]`).
**How to avoid:** The phase's Validation Architecture section (below) lists these as explicit separate commands the planner must schedule, not subsumed under `ci.all`.
**Warning signs:** A plan's verification checklist only says "run `mix ci.all`" for SC1/SC4.

### Pitfall 5: D-20's regenerate-diff contract test picking a different migration ordinal
**What goes wrong:** `TriggerMigration.resolve_name/2` (`lib/threadline/mix/trigger_migration.ex:47-60`, `[VERIFIED]`) numbers a migration `_2`, `_3`, etc. when a name/module collision exists in the target directory's *existing* migrations. A D-20 contract test that regenerates into an empty tmp dir will get the un-numbered name even though the committed migration might be numbered (if other trigger migrations for overlapping tables existed at generation time), or vice versa — causing a spurious diff failure unrelated to the actual trigger SQL.
**Why it happens:** Naming is directory-state-dependent by design (this is *load-bearing* correct behavior for real rerun detection, not a bug).
**How to avoid:** The contract test should regenerate into a tmp dir seeded with copies of every *other* trigger migration that existed in the real directory at the time the fixture migration was committed (or, simpler: only compare the migration's *body content*, ignoring the module name / file name entirely, and separately assert the fixture's own committed file still applies cleanly).
**Warning signs:** A contract test that is flaky or fails immediately after unrelated fixture tables are added elsewhere in the same migrations directory.
