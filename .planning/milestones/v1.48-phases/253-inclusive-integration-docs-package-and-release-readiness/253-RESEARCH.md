## Common Pitfalls

1. **Starting Retention too early:** an application-tree child may execute during migration/reset before schema readiness. Change the existing managed server spawn only after migration/reset; wait for the actual host Repo/schema before adding the real Pruner.
2. **Calling worker availability a destructive proof:** blank-submit/cancel is non-mutating; typed-submit is a separate fixture. Bind and compare operation/audit/seed rows before and after startup; keep the typed mutation isolated.
3. **Changing ordinary seeded operation rows:** default Export startup cleanup can mark the fixed-epoch seeded running job stale. Use the accepted private 12000-hour cutoff, record the override and make no default-cleanup claim. Preserve the actual Retention rows.
4. **Keeping stale direct-entry selectors:** migrate all old Retention modal openers, including screenshot and phase UAT probes, while keeping Prune now only inside the final confirmation dialog.
5. **Overclaiming inclusive or visual proof:** use the actual focused element and actual tab zoom; measure the intended host container. Do not infer container behavior from a shrink-wrapped child, zoom from a screenshot viewport, or route/DB behavior from Storybook.
6. **Refreshing evidence in the wrong order:** final copy/style edits invalidate affected width/behavior/capture proof. Run cheap affected checks and captures before review; avoid format-only repeated review rounds.
7. **Confusing a local gate with exact-candidate CI:** focused checks, a local archive and an old CI receipt are not current required CI. Keep stable job IDs and two-project browser evidence; no local full-root repeat or workflow dispatch.
8. **Making an accidental release claim:** archive/evaluator success is package readiness evidence, not a version bump, publication, merge or REL-01 completion.
