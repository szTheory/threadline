<objective>
Close born-red cause BR-4: `mix docs --warnings-as-errors` emits 60 warning lines (29 distinct)
and fails, blocking `mix verify.release` before it reaches anything else.

Purpose: this is a cross-phase interaction our own phase created. Phase 200 set `@moduledoc
false` on 26 modules. Plan 202-03 then wrote the 0.10.0 changelog entry that documents exactly
that change — and to document it, it names those modules in backticks. ExDoc autolinks
backticked module names and warns when the target is hidden. Both halves are correct: the
modules should be private, and the changelog should say so. The defect is that ExDoc is being
asked to link to them.

Output: a green documentation build with the changelog entry intact and the privacy decision
untouched.
</objective>

  <action>
    Present the maintainer with the measured situation and two options. Do not pick one
    autonomously — this establishes the house style for every future release note that
    documents a module going private.

    State plainly what was measured: 26 distinct modules referenced from the 0.10.0 entry, each
    warning twice (html + epub), plus `c:put/2` warning 6 times from two pre-existing older
    entries at lines 56 and 123. Total 60 warning lines. Note explicitly that the `c:put/2`
    warnings are NOT from Plan 202-03's entry — they are pre-existing and would have failed this
    gate whenever it was first run with `--warnings-as-errors`.

    Option A — `skip_code_autolink_to` in mix.exs: add the module names (and the `c:put/2`
    reference form) to ExDoc's `skip_code_autolink_to` list. The changelog prose is untouched,
    names still render in monospace, and nothing links. Cost: a list in mix.exs that must be
    maintained as more modules go private, and which silences the warning class for those names
    everywhere in the docs, not only in the changelog.

    Option B — de-linkify at the reference site: change how the names are written in CHANGELOG.md
    so ExDoc does not treat them as code references to resolve. The prose stays accurate and the
    exemption is local to the entry that needs it, with no growing allowlist. Cost: the names no
    longer render as code, and the convention must be remembered by whoever writes the next such
    entry.

    Recommend Option A for the `c:put/2` references specifically — they are genuine references to
    a real public callback that simply need qualification or exemption, and de-linkifying them
    would make the upgrade note less useful. State a recommendation for the module inventory too,
    with the reason, and let the maintainer decide.

    Record the decision and its rationale in the SUMMARY before starting Task 2.
  </action>
