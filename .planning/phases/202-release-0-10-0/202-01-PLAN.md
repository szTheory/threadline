<objective>
Make 0.10.0 non-breaking for the entire pre-0.10 adopter population, and prove it
with an end-to-end install that actually exercises this tree.

Purpose: `Threadline.StorageSchema` is new in 0.10.0 and cannot detect the schema an
adopter installed into. Shipping it with the `"threadline"` default would prefix every
read path onto tables a 0.9.x adopter does not have, while their already-deployed
unqualified triggers keep writing to `public` — capture continues, exploration goes
blank, and no existing gate catches it. D-01 flips the default to `"public"`; D-03
demands the flip be proven by an install that looks like a 0.9.x adopter's, which is
only possible once D-07/D-08 make the hex evaluator resolve THIS tree instead of the
previously published one.

Output: flipped default with docs and installer steering to match; a rehearsal
registry harness; a version-literal-free hex evaluator; and a legacy-`public` end-to-end
test that fails loudly if the split brain ever comes back.
</objective>

<assumption_delta_decision>
**Signal:** `derived→chosen`. D-01 turns the storage schema from a constant Threadline
picks (`"threadline"`, isolation by default) into a decision the host must make
explicitly to get isolation (`config :threadline, storage_schema: "threadline"`).

**Noun now primary:** *the host's existing schema*. Before D-01 the primary noun was
*Threadline's own schema*; after it, Threadline's dedicated schema is one variant of
"wherever the host put the tables", and `public` — the schema every pre-0.10 install
actually uses — is the represented-by-default case.

**Decision:** `promote`. `public` becomes primary (the default), the dedicated
`threadline` schema is demoted to an explicit opt-in documented as the recommended
choice for a *new* install (D-02). We are NOT adding a second default alongside the old
one, and NOT adding runtime detection — detection is what the module cannot do, which is
the whole reason the default matters.

**Rationale:** the library cannot observe which schema an adopter installed into, so the
default must be the one that is true for the population that already exists. Isolation
becomes a steering problem (installer + guide) rather than a silent assumption.

**Second signal (`singular→plural`), D-07:** the evaluator's single dep-resolution
source becomes two (rehearsal registry / hexpm). Decision: `add-alongside`, deliberately
— the two modes answer different questions ("does the tree under test install?" vs
"did the thing we just published install?") and collapsing them would reintroduce the
exact pre-publish-gated-on-post-publish-fact shape this phase exists to remove. What
would force a promote: if rehearsal mode ever became capable of proving the published
artifact (it cannot — it never touches hex.pm).
</assumption_delta_decision>
