<objective>
Shift the born-red release defect class left: catch it on the pull request that introduces it
instead of at the publish gate.

Purpose: Phase 202 found three independent causes that would each have made the 0.10.0 release
pull request red — a Dialyzer `unknown_function`, 60 ExDoc warnings, and a hardcoded install pin
in a contract test. All three were invisible to `ci.all` at the current version and surfaced
only when Plan 202-05 Task 1 simulated a version bump, after four plans of work had been
committed on the assumption the release was green by construction.

The common property is that each becomes observable only under a bump. Nothing in CI simulates
a bump, so nothing catches them until a human is standing at the publish gate. This plan makes
the simulation a routine check.

Output: a fail-closed rehearsal script and a CI job that runs it, so the next occurrence of this
defect class is a red PR check with a named cause.
</objective>

    Write `bin/verify-bump-rehearsal` automating the manual rehearsal recorded in the 202-05
    SUMMARY: derive the next minor from `mix.exs` `@version`, apply it to `mix.exs` and the
    release manifest, run `mix release.pins`, then run the release verification entrypoint and
    the contract test files against that bumped state.

    FIRST, solve the extra-files trap recorded in `known_trap` above, because everything else
    depends on it. A bump that only edits `mix.exs` is not a faithful simulation: release-please
    also rewrites every `x-release-please-version` marked line in the same commit, and omitting
    that makes the rehearsal fail Family B of the version-truth contract for a reason that has
    nothing to do with any real defect. Read `release-please-config.json`'s `extra-files` list and
    apply the same rewrite the updater would, to exactly the lines it marks. If you conclude a
    faithful simulation is not achievable, say so plainly and propose what the gate CAN honestly
    assert instead — do not ship a rehearsal that is red for a reason nobody can fix, and do not
    paper over it by excluding the contract from the run.

    The trace-free requirement is the hard part and must be solved structurally, not by
    discipline. Do NOT implement it as "edit the tree, then put it back" — that is the pattern
    that has already gone wrong twice in this phase. Prefer a mechanism where the real tree is
    never mutated at all: a throwaway clone or `git worktree` in a temp dir, torn down by a
    `trap`, is the shape `bin/with-rehearsal-registry` already established in this repo for the
    same class of problem. Read that script and follow its precedent.

    Capture the working tree's state before and after and compare them — `git status --porcelain`
    plus a checksum over the files the rehearsal could touch. A difference is a FAIL, even if the
    rehearsal itself passed. Report what differed.

    Fail closed everywhere: if the bump cannot be applied, if `release.pins` cannot run, if the
    temp tree cannot be created, the script exits non-zero with a named FAIL block. There is no
    path where an unrunnable rehearsal prints OK.

    Add a `verify.bump_rehearsal` alias in `mix.exs` so the check has a named entrypoint, per the
    repo's standing convention that contributors and CI cite `mix verify.*` verbatim rather than
    ad-hoc commands.

    Before finishing, prove the script has teeth. Temporarily reintroduce ONE of the three fixed
    born-red causes in the temp tree only — the hardcoded pin is the cheapest — confirm the
    rehearsal goes red and names it, then confirm the real tree is still untouched. Quote the
    failure output in the SUMMARY.
