## Phase Scope

Phase 189 does not implement UI, redesign the operator surface, add screenshots, add a public component API, create compliance features, or run a synthetic external pilot. The UI contract for this phase governs how `189-QUALITY-AUDIT.md` talks about UI-adjacent authority surfaces and validates evidence boundaries.

The final audit artifact must help maintainers decide what is true, what matters, and what happens next. It must not turn v1.39 into a new UI/product/compliance milestone.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Review Quality Audit |
| Empty state heading | No evidence found |
| Empty state body | This surface has no current repo proof. Mark confidence Low and route it to `Prove before claim` or the owning phase. |
| Error state | Could not verify this surface. Re-run the named command or cite the current file evidence before closing the row. |
| Destructive confirmation | none - Phase 189 has no destructive UI or data action |

Copy rules:

- Say what failed, why it matters, and the next action.
- Name the affected user: adopter, operator, maintainer, release owner, or host integrator.
- Use direct consequence language: "Evaluators see mixed version truth" instead of "documentation risk".
- Avoid vague severity theater and marketing terms such as "enterprise-grade", "robust", "seamless", "powerful", and "next-generation".
- Keep actions and changes distinct, requests and transactions distinct, and audit history distinct from database activity auditing.

## Audit Artifact Contract

The executor-facing artifact is `.planning/phases/189-quality-baseline-and-authority-surface-audit/189-QUALITY-AUDIT.md`.

Required structure:

1. YAML frontmatter with phase, artifact type, audited date, requirements, status, and source precedence.
2. Short executive summary: no more than six bullets, weakest risks first.
3. Ranked Evidence Ledger: one table sorted weakest/highest-risk first.
4. QUAL-03 Residuals: one table covering every required residual.
5. Good Enough / N/A Appendix: visible, not hidden or implied.
6. v1.39 Narrowing: which findings route to Phase 190, 191, 192, 193, future, external, or none.

Every ranked row must include:

| Field | Contract |
|-------|----------|
| Rank | Integer order, weakest/highest-risk first |
| Quality dimension | Specific surface, not a vague category |
| Score | `0`, `1`, `2`, `3`, or `4` only |
| Confidence | `High`, `Medium`, or `Low`, separate from score |
| Evidence refs | File paths, command names, CI job ids, or package truth refs |
| Practical consequence | Plain-language impact on adopter, operator, maintainer, release owner, or host integrator |
| Highest-leverage fix | One concrete next action |
| Priority | One locked taxonomy label |
| Route bucket | `Must-fix now`, `Phase-owned`, `Future seed`, `Good enough`, `N/A`, `External-owned`, `Maintenance note`, or `Backlog cleanup` |
| Owner phase | `190`, `191`, `192`, `193`, `future`, `external`, or `none` |

Allowed score meanings:

| Score | Meaning |
|-------|---------|
| 0 | unknown, unproven, or broken trust boundary |
| 1 | must-fix adoption, operations, release, or maintainer risk |
| 2 | workable with material residual |
| 3 | good enough for current claims |
| 4 | strong/proven |

Do not invent a second severity scale.

## Interaction Contract

The audit document must behave like a decision surface for maintainers under time pressure.

- Put the highest-risk row first; do not group by what is easiest to write.
- Make every row answer: what failed or is unproven, why it matters, what evidence supports that claim, and what the next action is.
- Keep route buckets stable and exact; do not use synonyms like "critical-ish", "yellow", "watch", or "nice to have".
- Use one next action per row. If there are two real actions, split the row.
- Keep "good enough" and "N/A" visible so the audit does not imply unbounded work.
- Route findings only when repo evidence affects a current adoption, production, support, release, or maintainer authority surface promised by v1.39.
- Prefer named proof bundles such as `mix verify.*`, `mix ci.*`, `VERIFICATION.md`, `VALIDATION.md`, current source/tests, CI job ids, and doc-contract tests over prose.

## Visual Hierarchy For `189-QUALITY-AUDIT.md`

- First screen: title, scope sentence, and weakest-three summary. No hero, marketing copy, or decorative visuals.
- Ledger: single dense table with exact columns from this spec. Use Markdown links/paths, not paragraphs of narrative.
- Residuals: separate table so seeds and proof limits do not pollute the ranked ledger.
- Appendix: good-enough and N/A rows must be scan-friendly and short.
- Diagrams: optional only if they clarify authority precedence or phase routing. Use domain nouns on rails; do not add decorative diagrams.
- Screenshots: not part of Phase 189 output. If future proof is routed, record it as `Future seed` or the owner phase, not as work done now.
