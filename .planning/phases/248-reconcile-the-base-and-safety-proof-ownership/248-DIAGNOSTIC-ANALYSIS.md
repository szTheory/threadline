## What the observation establishes

The timeout stack is concrete: `gen_server.call` / `file.call` under `filelib.do_double_star`, reached from `Path.wildcard` in `owned_files/1`, called by `replace_owner_files/2` for the mutated root owner. In the 60.75-second event window the observer collected 184 samples. The sampled file-server reductions advanced by 429,209 with 184 distinct values; its queue was 17 at p50, 30 at p95, and 34 at maximum. The same VM's scheduler run queue peaked at 126. The sampled call sites changed among directory listing, metadata reads, file reads, directory/file removal and creation, CWD reads, and file-I/O server startup. This pattern is consistent with a progressing file server serving many requests under a busy VM while the wildcard caller waits in the queue.

That is evidence for contention and request amplification, not proof of root cause. A sampled function histogram is not an operation count or attribution to test callers. The stack records where this test was waiting at timeout; it does not show which other tests or processes supplied the queue. The observer interval reached 5.781 seconds and a sample cost reached 4.686 seconds, so sampling was irregular and could perturb a loaded VM or miss shorter stalls. Progressing reductions do not rule out a slow individual wildcard or intermittent long requests. The event's `duration_us: 0` conflicts with the explicit 60-second ExUnit timeout and 60.75-second event window; use the ExUnit log and elapsed window, not that zero field.

The observer covered 2,690 samples overall and saw a file-server queue peak of 41. It did not capture per-request latency, caller identity, OS-wide competing process activity, or complete stacks over the interval. The parent reports PostgreSQL was stopped after the suite and there were no other DB clients; that post-run fact does not measure DB activity during the timed window. The captured stack points at filesystem service, not a database call.

The run records one seed (`584294`) but no repeat index or before/after inventory of temp paths, Git worktrees, database state, file descriptors, or other persistent state. `source_unchanged: true` establishes that source did not drift; it does not establish that runtime state was clean across iterations. The inspected temp-heavy contracts use per-test `:tmp_dir`, unique names, or cleanup callbacks, but this sample does not prove that every test cleans up after every failure. No repeat-state leak is demonstrated here, and this run cannot rule one out.

Keep the exact uncovered assertion as the negative control. The planned private mutants should verify that removing/misdirecting the overlap literal makes the overlap assertion fail and restoring the bench input makes the uncovered assertion fail; this is validation of the existing controls, not a reason to add another permanent assertion that repeats their implementation.
