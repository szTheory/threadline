Move the serialization from `WalkthroughCase` into `ThreadlinePhoenix.Demo.Reset.run/0` and
`ThreadlinePhoenix.Demo.Seed.run/0`, so that every entry point is covered — all five `async: false`
seeding modules **and** the `mix demo.reset` / `mix demo.seed` tasks, which the current wrapper cannot
reach (WR-02 problem 1). The unguarded callers are precisely the ones that would collide with a
guarded one, so a partial guard is worse than none.

The lock must not survive an abnormal process exit (WR-01). Use `pg_advisory_xact_lock($1, $2)` inside
the function's own transaction where one already exists — a transaction-scoped lock is released on
commit, rollback, **and** disconnect, so an ExUnit timeout kill cannot strand it. Where `Reset.run/0`
or `Seed.run/0` cannot legitimately be wrapped in a single outer transaction (a TRUNCATE sequence
that must not be one unit of work is a real reason; verify before assuming), use
`pg_try_advisory_lock($1, $2)` in a bounded retry loop with an unconditional `pg_advisory_unlock($1, $2)`
in an `after`, and set `lock_timeout` to `'45s'` so a stranded peer surfaces as a named lock-timeout
error rather than an unbounded hang. Never use bare `pg_advisory_lock/1`, and never leave the wait
unbounded.

Namespace the key (IN-02): define a module attribute `@advisory_lock_classid` holding a fixed integer
constant specific to Threadline demo seeding, and use the two-argument advisory-lock form with that
classid plus a stable objid. Delete `@demo_seed_lock_key`'s unnamespaced `:erlang.phash2/1` value —
Postgres advisory locks share one global keyspace per database and an unnamespaced 27-bit hash can
silently serialize against an unrelated tool.

Delete the lock wrapper from `walkthrough_case.ex` and correct its remaining comment. The current
comment asserts a mechanism the test topology forbids: all five seeding modules are `async: false`
and ExUnit never runs two `async: false` modules concurrently, so "two concurrent unboxed seed/reset
cycles" cannot occur within one `mix test` (WR-02 problem 2). Replace it with the surviving
mechanism — cross-OS-process contention: a parallel CI lane, a developer running `mix demo.seed`, or
a second `mix test` against the same database — and cite where the lock now lives.

Do not weaken or remove any assertion in `walkthrough_case.ex` or in any of the five seeding modules.
