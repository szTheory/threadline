<objective>
Close Gap 4: CI run 33183920952's `Example app browser E2E (Playwright)` reports 5 failures, 9
passed, and 348 tests that did not run. The two named failing specs are
`tests/operator-accessibility.spec.ts:397` ("keeps Coverage readiness, schema recovery, and theme
picker controls keyboard reachable") and `tests/operator-coverage-readiness.spec.ts:119` ("keeps
the selected-schema verdict, picker, row actions, and table readable"), the latter across all four
viewports — phone-320, phone-375, tablet, and desktop-1024.

Purpose: 198-10 added a schema-resolution step to this job's database preparation. It was
necessary and it was not sufficient. Both failing tests visit `/audit/coverage` and depend on the
schema picker offering `public`, on the "Selected schema readiness" region rendering a verdict, and
on the coverage table containing both covered and uncovered rows — all of which are functions of
what the example app's database and demo seed actually contain when the browser arrives.

Note the shape of the numbers before chasing them: `4 viewports x 1 coverage-readiness test + 1
accessibility test = 5`, and the browser lane runs with a CI failure ceiling (D-18) that aborts the
run once that ceiling is hit. The "348 did not run" figure is most likely that ceiling working as
designed, not a separate early-abort defect. **Verify that before spending effort on it** — but do
not assume it either.

Output: a written diagnosis attributing each failure to a cause, then a fix at the cause.

**Do not reach green by weakening the specs.** No deleted assertion, no loosened selector, no
added retry, no conditional guard, no quarantine. If the true cause is the deferred
`examples/threadline_phoenix` `DemoContractTest` demo-seed drift, say so explicitly and treat it as
a blocking dependency — that item is carried in `deferred-items.md` and `.planning/WINDOWS.md`
across Phases 177/179/180/182 and must not be silently absorbed here.
