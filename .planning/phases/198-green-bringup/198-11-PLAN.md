<objective>
Close GREEN-11. The flake classifier is present, well-reasoned, and completely unreachable on
the only path it exists for.

Purpose: `.github/workflows/flake-detection.yml:87` uses `set -uo pipefail`, which does not
clear the `-e` GitHub injects via `shell: /usr/bin/bash -e {0}`. When `mix verify.flake` fails,
the line-88 pipeline aborts the step before line 89 writes `exit_code`. `Classify broken vs
flaky` (`:101`) carries no `if:`, so it defaults to `success()` and is SKIPPED; the issue step
(`:145`, gated on `steps.classify.outputs.classification`) is skipped transitively. The step's
own comment at `:82-83` asserts the opposite — "Captures the exit code instead of failing here,
so the classification and issue steps below still run." Verification rated this a Blocker: the
artifact and the claim genuinely diverge.

Output: a wired, and — critically — a PROVABLE classifier.

**Why this is not a two-line YAML edit.** The minimal fix is `set +e` plus `if: always()`, and
that is exactly the shape that regressed once already: untested workflow shell whose only
execution path is a nightly 120-minute job nobody watches. This plan instead extracts the
classification into `bin/classify-flake-run` — a committed script, the pattern the repo already
uses for `bin/verify-release-shape` (`ci.yml:573`) and `bin/verify-branch-protection` (D-12) —
so the logic becomes directly executable and unit-testable in `mix test`. D-12 states the
principle verbatim: a runbook is an assertion, a script is proof.

**Preserve the reasoning that is already correct.** The existing classifier anchors on a
MEASURED stable marker (`Running ExUnit with seed:`, one header per iteration, with the
observed exit/header pairs recorded in the workflow comment) rather than an assumed one, and
deliberately routes an absent header to `unknown` rather than `flaky`. That reasoning survives
intact; only its reachability and its empty-value handling change.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI job outcome -> maintainer notification | A `schedule` run notifies nobody; the deduplicated issue is the only channel, so a skipped issue step is a silent failure |
| workflow YAML -> shell semantics | GitHub injects `-e` into every `run:` body; a step that assumes otherwise aborts silently mid-body |
| script -> workflow | Logic tested in one place and invoked from another can drift apart without either noticing |
