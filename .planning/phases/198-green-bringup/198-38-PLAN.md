<objective>
Close **CR-01** — the round-5 code review's unresolved Critical — at its cause, with a regression
test that can actually observe the failure mode, and give **CR-01, WR-01 and IN-01** each a terminal,
recorded disposition.

**The defect.** `ThreadlinePhoenix.Demo.Reset.with_demo_lock/1` and `ThreadlinePhoenix.Demo.Seed`'s
private twin each issue independent, non-transactional `Repo.query!/2` calls for `SET lock_timeout`,
`pg_try_advisory_lock` and `pg_advisory_unlock`, with no `Repo.checkout/2`, no `Repo.transaction/2`
and no Sandbox pinning. `Demo.Reset.run/1` calls `Demo.Seed.run()` from **inside** its own guarded
body, so the same lock pair is acquired twice, nested. Postgres advisory-lock session reentrancy —
which the `Demo.Seed.run/0` docstring explicitly relies on — requires both acquires to land on the
**same physical connection**. Under `DBConnection.ConnectionPool` with `pool_size: 10`
(`config/dev.exs:18`, `config/runtime.exs:36-37`) that is not guaranteed. Failure modes: a
false-positive 45-second lock-timeout crash, or a leaked advisory lock stranded on an idle pooled
connection that reproduces on the next `mix demo.reset`. WR-01 is the same root cause seen from the
`SET lock_timeout` side.

**Why the existing suite cannot catch it, and what that forces.** Every test that exercises this path
(`demo_reset_test.exs`, `demo_contract_test.exs`, `walkthrough_case.ex`) wraps the call in
`Ecto.Adapters.SQL.Sandbox.unboxed_run/2`, which pins one connection and therefore *structurally*
masks the exact race. A new test that also runs under `unboxed_run/2` would prove nothing. The
regression test in Task 2 therefore asserts on **connection identity** — that the guarded region runs
inside a single checked-out connection and that the same backend PID serves the outer and the nested
acquire — and it runs under `Ecto.Adapters.SQL.Sandbox.mode(Repo, :auto)`, where the pool behaves
like the real `mix demo.reset` pool rather than like a pinned sandbox owner.

**Which remedy, and why.** `198-REVIEW.md` offers two: pin the connection with `Repo.checkout/2`
around the whole guarded region, or switch to `pg_advisory_xact_lock` inside `Repo.transaction/2`.
The transaction-scoped variant is attractive because it deletes the manual unlock path and therefore
the leak mode outright — but it is **not admissible here**, and the reason is in the code, not in
preference. `Demo.Reset.with_demo_lock/1`'s own docstring records that the demo pipeline issues many
independent `Repo.transaction/1` calls **by design**, each producing its own distinct audit
transaction for the seeded fiction; the guarded body also runs `Demo.Tables.truncate_sql()`. Wrapping
the pipeline in one outer transaction would collapse every seeded audit transaction into one Postgres
transaction and change the shape of the seeded audit trail that the walkthrough and demo-contract
tests assert against. So: **`Repo.checkout/2`**. It pins the connection — which is the whole of what
CR-01 and WR-01 require — while leaving each inner `Repo.transaction/1` its own commit boundary and
its own audit transaction.

**Tracer.** Task 1 is the end-to-end slice: one connection-pinned guard, the nested acquire path
wired through it, verified by a real run of the demo reset pipeline. Tasks 2 and 3 expand outward
into falsification and disposition. Nothing here touches CI configuration, capture evidence, or any
requirement's status — plan 198-40 owns the measured verdict (D-01).

**Edge lift, spec-less probe fallback §A.** The deterministic edge probe surfaced 26 applicable
