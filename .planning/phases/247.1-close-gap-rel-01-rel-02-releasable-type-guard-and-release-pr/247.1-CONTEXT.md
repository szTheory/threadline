## Implementation Decisions

### A. Releasable-type guard (SC1)
- **D-01:** Add `"exclude-paths"` to the `"."` package in `release-please-config.json`, listing the maximal directories that contain no shipped file. Researched list (planner/executor must re-derive it from the contract test, not copy it blindly): `.github`, `.impeccable`, `.planning`, `bench`, `bin`, `brandbook/examples`, `brandbook/tools`, `config`, `examples`, `lib/threadline/operator_surface/live/stress_live`, `priv/ci`, `priv/repo`, `prompts`, `scripts`, `test`. — **Reversibility:** reversible — one config key.
- **D-02:** Semantics are fixed by release-please **17.6.0** (bundled by `release-please-action` v5.0.0 pin `45996ed1`): `src/util/commit-exclude.ts` matches **directory prefixes only** (`file.indexOf(path + "/") === 0`; no globs, exact file paths never match, `"."` excludes everything), and a commit is excluded only when **every** file it touches is excluded (mixed commits still count; a commit without file data fails open). Docs and tests must state exactly this and nothing stronger.
- **D-03:** Accepted residue: unshipped **top-level files** (`AGENTS.md`, `CLAUDE.md`, `SECURITY.md`, `mix.lock`, dotfiles, `release-please-config.json`, manifest, `CHANGELOG-GENERATED.md`, `docker-compose*.yml`, …) and the single-file `exclude_patterns` modules (`release.pins.ex`, `stress_live.ex`, `stress_fixtures.ex`, `stress_router.ex`) cannot be excluded by release-please. The commit-type rule (D-07) covers them. SC1 is satisfied for every unshipped path release-please can express; the residue is pinned in the test (D-04.4) so it is a conscious, visible list, not a silent gap.
- **D-04:** Contract test in `test/threadline/release_artifact_contract_test.exs`, reusing its existing `mix hex.build --unpack` helper: the unpacked tarball (built from `mix.exs` `package()`) is ground truth, matching the mix.exs comment "a gate that asserts its own inputs proves nothing". `shipped` = tracked files (`git ls-files`) present in the tarball; `expected` = every directory D with no shipped file under it whose parent is root or contains a shipped file. Assertions:
  1. `exclude-paths` == `expected` (sorted set equality, both directions — catches a new unshipped top-level dir and stale entries);
  2. soundness: no entry is a prefix of any shipped file (a real `lib/` fix must never be swallowed);
  3. shape: no `"."`, no glob chars `*?[{`, no leading/trailing `/`, each entry is a directory holding tracked files;
  4. the uncoverable residue (unshipped tracked files not under any entry) equals a list pinned in the test;
  5. mutation controls in the repo's existing style: adding `"lib"` fails (2), dropping `"bin"` fails (1), adding `"bin/ci-test-partitions"` fails (3).
- **D-05:** Rehearsal: the documented CLI dry-run reads config from `main`, so pre-landing proof uses a programmatic dry-run against `release-please@17.6.0` (`Manifest.fromManifest` → override `repositoryConfig['.'].excludePaths` → read-only `buildPullRequests()`), run with `npm_config_ignore_scripts=true` and the token read inline from `gh auth token`. Researcher result: baseline → "Would open … release 1.1.1"; with D-01 list → "No user facing commits found … skipping", 0 candidates; controls `["bin/ci-test-partitions"]` → 1.1.1, `["bin"]` → 0. Record the script (no token) and output in the phase dir. Post-landing, the documented CLI dry-run on `main` must print no release PR.
- **D-06:** Add a line to CONTRIBUTING "Upgrading the Release Please action": on any library bump, re-verify `commit-exclude.ts` semantics (directory prefix, all-files-excluded) before trusting `exclude-paths`.

### C. Type/prose coupling docs (SC2) + cheap debt
- **D-07:** CONTRIBUTING "Ongoing releases": insert a rule block before the existing CONTRIBUTING.md:969 paragraph (keep that sentence verbatim — `changelog_contract_test.exs:293-297` pins it). Content: the squash subject's type decides releases (`feat`/`fix`/`perf`/`deps` or `!`; scope does not matter, `fix(ci):` is a fix); both directions — (a) changes that ship nothing (CI, tests, tooling, planning) merge as `ci:`/`test:`/`chore:` (`docs:` for docs only), never `fix(ci):`; (b) a releasable subject needs release prose under `## Unreleased — highlights` in the same PR or the Release PR cannot be dated and stays red. ### B. #101 recovery and live proofs (SC3, SC4) — ordering is load-bearing
- **D-12:** Order: **PR A (prose) → observe REL-02 → PR B (guard+docs) → close #101 unmerged.** Landing the guard first would make release-please 17.6.0 see zero user-facing commits since v1.1.0, return early from `createPullRequests()` (manifest.ts:922-926), never refresh or close #101, and destroy the REL-02 observation. — **Reversibility:** one-way — once PR B lands, #101 can no longer be refreshed by automation, so REL-02 must be observed first.
- **D-13:** PR A: typed `docs(changelog):`, touches `CHANGELOG.md` only, adds **true** prose under `## Unreleased — highlights` that rolls forward to the next real release (Breaking changes: None; Required action: None; plus a factual line about what changed in the shipped tarball since 1.1.0). The executor derives that line from an unpacked-tarball diff of v1.1.0 vs main (`mix hex.build --unpack` at both) — never invent content; if the shipped delta is docs-only, say exactly that. Merge under the standing grant on green CI.
- **D-14:** REL-02 observation: after PR A merges, run `244-REL02-EVIDENCE.md` §3 commands a–e verbatim (read-only, no retry/wait loops beyond waiting for runs to finish) and check §4 pass conditions (release run has no "remained the same"; `Sync install pins on Release PR` = success; #101 `headRefOid` changed; a `pull_request` ci.yml run on the new head is green; no manual dispatch/push). A cancelled run on an intermediate head is not a failure (§5). Rewrite `Status:` to `observed — release run <id>, CI run <id>, head <sha>`, note assumption A1 confirmed live (§6 fallback not needed). This also turns Release@main green (closes F2's symptom).
- **D-15:** PR B: typed `ci(release):` (not releasable; precedent in CONTRIBUTING step 4). Carries D-01..D-11. CONTRIBUTING.md is shipped, so exclude-paths does not apply to PR B — its type is the only guard: the PR title AND (if single-commit) the commit subject must be `ci(release): …`, and no body may contain `BREAKING CHANGE`. Its release run is a free live SC1 check: log shows "No user facing commits found", sync job skipped, run green; afterwards the documented CLI dry-run on main prints no PR.
- **D-16:** Close #101 **unmerged** after PR B lands, with a comment (no adopter-facing change since 1.1.0; superseded by the guard), remove the `autorelease: pending` label, do not delete the branch. release-please only considers OPEN and MERGED PRs (and `autorelease: snooze` closed ones), so the next real releasable commit opens a fresh PR on the same branch. **Hard rule for every executor/lander: never merge #101** — it will be green between D-14 and D-16 and the "merge my own green PRs" grant does not cover it (merging tags v1.1.1 and creates a GitHub Release before the Hex approval gate; not cleanly undoable). Shipping 1.1.1 is rejected: a no-op Hex release.
- **D-17:** Honest recording: SC4/REL-02 → satisfied (observed). SC3/REL-01 → mechanism observed live (dating + green CI on the refreshed #101), but the clause "the next release PR's first CI run is green with no separate CHANGELOG-dating PR" cannot be met in this phase (PR A is itself a prose PR, and no releasable package change is pending). Bind it to the next natural release cycle in `247.1-REL01-EVIDENCE.md` mirroring the REL-02 file (trigger: first feat/fix/perf/deps commit touching shipped files landing with its prose; pass: sync job success, first `pull_request` CI on the release PR's final head green, no `docs(changelog)` PR in between). Verification records REL-01 as `deferred-with-trigger`, REQUIREMENTS REL-01 stays Pending with that note. After any `phase.complete`, hand-diff REQUIREMENTS.md (it marks deferred reqs Complete — known gsd-tools bug).
