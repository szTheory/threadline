3. **No other test pins the key set of `release-please-config.json`.** Adding `exclude-paths` breaks nothing. Every consumer reads named keys only.

This session also turned up three new pitfalls the planner must design around:

- The repo squashes with `squash_merge_commit_message=COMMIT_MESSAGES`.
- release-please 17.6.0 `splitMessages` treats any paragraph in the squash body that starts with `fix:`/`feat(...):`/… as an extra conventional commit.
- `preprocessCommitMessage` replaces the whole message with the PR body's `BEGIN_COMMIT_OVERRIDE` block whenever that literal string appears.

So PR A and PR B should be merged with an explicit `--subject` and `--body`, their PR bodies must not contain the override token, and the new PR-template section must not contain it either.

The 1.1.0 → main shipped delta is documentation-only plus maintainer-only `mix.exs` aliases, with no `lib/` file change. I confirmed this by diffing the published 1.1.0 tarball (`mix hex.package fetch threadline 1.1.0 --unpack`) against the current build. That is the true fact PR A's prose must state (D-13).

**Primary recommendation:** Land PR A first: `docs(changelog):`, CHANGELOG.md only, prose shaped to pass the newest-entry contract after dating. Then observe REL-02 with the §3 commands. Then land PR B, `ci(release):` on a fresh `land/v1.47-247.1` branch cut from `origin/main` after PR A merges. It carries `exclude-paths`, the pure-function contract test, the docs and the F4 relax. Then close #101 unmerged. Merge every PR with `gh pr merge --squash --subject … --body …` so no stray commit-message paragraph can make release-please treat it as releasable.

### Pattern 1: Pure checker plus live assertion plus mutation controls (for D-04)
**What:** One pure function `exclude_paths_errors(entries, tracked, shipped, pinned_residue)` returns a list of `rule=<id>: …` strings. The live test feeds it the real config, `git ls-files -z` and `built_archive().entries`, and asserts `== []`. Each mutation control feeds a modified `entries` list and asserts its own rule id fires. The controls need **no** extra `hex.build`.
**When:** This is how the repo already writes contract rules: `regenerate_errors/2` (release_control_plane_contract_test.exs:574-612), `build_cache_errors/2` (ci_workflow_parity), `dependabot_errors/2` (dependabot_config_contract_test.exs moduledoc :15-35).
**Why it matters here:** `built_archive/0` runs a real `mix hex.build --unpack`. It is already called 6 times textually, and about 10 times at runtime because of the `for {tag, paths} <- @source_owners` loop. The file's weight is 18 816 ms (`test/partition_weights.txt:224`). Add **one** `built_archive()` call and make everything else pure.

**Rule ids to use (suggested):** `rule=set-equal` (D-04.1, report missing and stale separately), `rule=sound` (D-04.2), `rule=shape` (D-04.3), `rule=residue` (D-04.4). Mutation controls (D-04.5): `entries ++ ["lib"]` → `rule=sound` (and set-equal); `entries -- ["bin"]` → `rule=set-equal`; `entries ++ ["bin/ci-test-partitions"]` → `rule=shape` (not a maximal directory, and nested under `bin`).

### Pattern 2: Section slice plus needle list (for D-09)
Slice CONTRIBUTING the same way `build_cache_section/1` does it: split on lines, drop until the heading, take until the next `^### ` / `^## `. The heading is `### Ongoing releases (0.6.1+)` (CONTRIBUTING.md:961), so match with `String.starts_with?(line, "### Ongoing releases")`. Derive the releasable types the way `dependabot_config_contract_test.exs:68-70` does: `for %{"type" => type} = section <- sections, section["hidden"] != true, uniq: true`. On the current config that gives `feat`, `fix`, `perf`, `deps`.

**Anchoring caveat:** `@unreleased_heading_regex` is `~r/^## Unreleased — highlights$/m` (changelog_contract_test.exs:56). It is **line-anchored**. In CONTRIBUTING and the PR template the heading appears inline, inside backticks (CONTRIBUTING.md:964). The anchored regex will never match there. D-09's "unanchored" means: add a sibling attribute (for example `@unreleased_heading_text "## Unreleased — highlights"`) and assert with `String.contains?/2`. Do not edit the anchored regex, because the 0.11.0 block locator depends on it (:89-103).

### Anti-Patterns to Avoid
- **Using `git ls-files` without `-z`.** Two tracked filenames under `prompts/prior-art/from-sigra/` contain an em dash and are emitted C-quoted (`"prompts/prior-art/from-sigra/Auth Domain Language \342\200\224 …"`). That yields a bogus top-level dir `"prompts`. Every existing whole-repo caller uses `["ls-files", "-z"]` (`removed_artifact_contract_test.exs:182`, `planning_dependency_contract_test.exs:16`).
- **Walking the filesystem instead of `git ls-files`.** `hex.build --unpack` stages a `tmp_<hash>` directory in the checkout root (`test/partition_colocate.txt` header), and local `deps/`/`_build/` exist. Only tracked files define the repo's paths.
- **Writing `exclude-paths` with globs or file paths.** 17.6.0 `isRelevant` is `path === ROOT_PROJECT_PATH || file.indexOf(\`${path}/\`) === 0`, and `normalizePaths` only strips leading and trailing `/`. A file path or glob silently matches nothing.
- **Adding a new `built_archive()` per mutation control.** Each one adds about 2 s to a colocated heavy file on all three lanes (CI-03 balance).

## Common Pitfalls

### Pitfall 1: A squash body paragraph or PR-body token makes PR B releasable
**What goes wrong:** PR B touches CONTRIBUTING.md, which is shipped, so `exclude-paths` cannot ignore it. If release-please finds any user-facing conventional commit in its message, it refreshes #101 instead of returning early. That breaks D-16.
**Why:** The repo setting is `squash_merge_commit_message: "COMMIT_MESSAGES"` [VERIFIED: `gh api repos/szTheory/threadline` this session; also `squash_merge_commit_title: "COMMIT_OR_PR_TITLE"`]. release-please 17.6.0 `splitMessages` splits the message on `/\r?\n\r?\n(?=(?:feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(?:\(.*?\))?: )/`, and `preprocessCommitMessage` replaces the message with the PR body's text after `BEGIN_COMMIT_OVERRIDE` [VERIFIED: release-please v17.6.0 `src/commit.ts:388-403, 456-466`, fetched this session]. GitHub's bullet form (`* fix(247): …`) does not match the split regex because of the leading `* `, but a commit *body* paragraph that starts with `fix(ci): …` would match.
**How to avoid:** Merge PR A and PR B with `gh pr merge <n> --squash --subject "<type(scope)>: … (#<n>)" --body "<plain prose, no type-prefixed paragraph, no BREAKING CHANGE>"`. PR bodies (`gh pr create --body`) must not contain the literal `BEGIN_COMMIT_OVERRIDE`.
**Warning signs:** PR B's release run shows `prs_created=true` or the sync job runs. A dry-run after merge shows `Would open 1`.

### Pitfall 2: The PR template carrying `BEGIN_COMMIT_OVERRIDE`
**What goes wrong:** If the new `## Release impact` text names the escape hatch literally, every PR opened from the web UI inherits it. Then `preprocessCommitMessage` takes the rest of the body as the override message. It is unparseable, so the real commit is dropped, which can strand a real `fix:` unreleased.
**How to avoid:** Keep `BEGIN_COMMIT_OVERRIDE` only in CONTRIBUTING (where :969 already has it). Optionally add `refute String.contains?(pr_template, "BEGIN_COMMIT_OVERRIDE")` to the D-09 test. This is a cheap, honest addition and does not contradict D-09.

### Pitfall 3: PR A prose that dates but leaves #101 red
**What goes wrong:** After dating, `[1.1.1]` becomes the newest dated entry. `changelog_contract_test.exs` then requires all of the following on #101's head [VERIFIED: changelog_contract_test.exs:159-209 read this session]:
- prose lines between the heading and the first `###` ("the newest release entry opens with human-written highlights");
- a `### Breaking changes` or `### Required action` heading;
- a feature-tour heading matching `^### (?:Added|Changed|Fixed|Deprecated|Removed|Features|Bug Fixes)\b`;
- breaking/required placed **before** the feature tour;
- no generated `([abc1234](…/commit/` bullets.

`bin/date-release-changelog` strips `_Nothing yet for the next release._` and needs other non-blank content [VERIFIED: bin/date-release-changelog:106-117].
**How to avoid:** Use the 1.1.0 entry as the shape model (CHANGELOG.md:24-60): a one-sentence summary paragraph, then `### Breaking changes` / None, then `### Required action` / None, then `### Changed` with the factual docs-only bullet(s). Replace the placeholder line. CHANGELOG.md ships, so the planning-vocabulary scan applies (`release_artifact_contract_test.exs:7-14`). That means no `Phase N`, no `phase_…`, no `D-NN`, no `ADOPT|COMP|CRITIC|DATA|GREEN|GROUP|MECH|NAV|PROOF|SURFACE|WR-NN`, and no `v1.34`–`v1.41`.
**Local proof before PR A:** the script has no version flag. It reads `@version` from `mix.exs` (`Usage: bin/date-release-changelog [--root DIR] [--date YYYY-MM-DD] [--check]`, bin/date-release-changelog:20-23). So in a scratch `git clone --no-local` of the prose commit, set `@version "1.1.1"` in the clone's `mix.exs`, run `bin/date-release-changelog --root <clone>`, and then run `mix test test/threadline/changelog_contract_test.exs` inside the clone (ephemeral PG16 env exported). Delete the clone afterwards. `bin/verify-bump-rehearsal` also exercises this path in CI (`verify-bump-rehearsal` job, ci.yml:455). When Unreleased already has prose, it skips the stand-in seed (bin/verify-bump-rehearsal:405-406).

### Pitfall 4: The shipped delta wording (D-13)
**Fact found this session:** I diffed the published 1.1.0 tarball against the current `hex.build --unpack` (identical code to `origin/main`; the only non-`.planning` difference on milestone/v1.47 is `prompts/discuss-fanout-method.md`). The files that differ are `CHANGELOG.md`, `CONTRIBUTING.md`, `guides/adoption-pilot-backlog.md`, `guides/configuration-and-commands.md`, `mix.exs` and `hex_metadata.config`. Beyond that, 1.1.0 carried two **empty directories**, `lib/threadline/critic_trust/` and `lib/threadline/operator_surface/mechanical_checker/`. No `lib/` file changed. No `{:dep, …}` requirement line changed in `mix.exs` (the diff touches maintainer aliases only).
**How to avoid:** State the change as docs-only: contributor and command-reference documentation, no library code, no dependency change. The executor must re-run the diff at execution time, because main may move. Avoid naming retired commands. It is not required, but it keeps the prose adopter-facing.

### Pitfall 5: Cherry-pick/landing double-apply
**What goes wrong:** PR A's CHANGELOG commit lives on the milestone branch and is already on main. Cherry-picking `<last-landed>..milestone` for PR B re-applies it, which gives an empty pick or a conflict. A CHANGELOG hunk can also apply silently into the wrong section (memory: landing-branch trap).
**How to avoid:** Cut `land/v1.47-247.1` from `origin/main` **after** PR A merges. Cherry-pick only PR B's code commits by explicit SHA list, never PR A's. Add one `docs(planning):` sync commit with `git checkout <milestone-sha> -- .planning/phases/247.1-… .planning/phases/244-release-flow/244-REL02-EVIDENCE.md .planning/REQUIREMENTS.md .planning/ROADMAP.md .planning/STATE.md` (explicit tracked paths). Before pushing, run `git diff --stat land/v1.47-247.1 milestone/v1.47 -- . ':(exclude).planning'`. Expect only `prompts/discuss-fanout-method.md` and nothing release-related. Then run `bin/verify-repo-hygiene`.

### Pitfall 6: Assumption A1 false on the live refresh
**What goes wrong:** The PR A release run updates #101 but reports `prs_created=false`, so the sync job is skipped. The new head is undated, CI on #101 goes red, and REL-02 §4 fails.
**How to avoid:** Treat this as a **stop point** in the live-ops plan. Record the observation honestly and do **not** land PR B. Once PR B lands, #101 can never be refreshed again (D-12). Per §6 of the evidence file, the fix is a separate follow-up (key the sync job on an open-release-PR check) and is not patched inside the observation. Escalate to the maintainer as a scope decision.

### Pitfall 7: Merging #101 by grant reflex
**What goes wrong:** #101 goes green between D-14 and D-16. The standing "merge my own green PRs" grant does not cover it. Merging it tags v1.1.1 and creates a GitHub Release.
**How to avoid:** Every live-ops task names `never merge #101` as a halt clause (memory: executors route around preconditions). Use `--match-head-commit` on PR A and PR B merges so a mistyped number cannot merge the wrong PR.

### Pitfall 8: Residue drift friction
Any new top-level tracked file, or a new file directly under `brandbook/`, changes the pinned residue and fails D-04.4. That is intended, because it makes the decision conscious. The failure message must say what to do: either move the file under an excluded directory or add it to the pinned residue with a reason. Note that the residue is **not only top-level files**. Twelve `brandbook/*` files are residue too, because `brandbook/` holds three shipped SVGs.

## Code Examples

### Derivation (verified: run through `MIX_ENV=dev mix run --no-start` this session against a fresh `hex.build --unpack`)
```elixir
# Output on the current tree:
# [".github", ".impeccable", ".planning", "bench", "bin", "brandbook/examples",
#  "brandbook/tools", "config", "examples",
#  "lib/threadline/operator_surface/live/stress_live", "priv/ci", "priv/repo",
#  "prompts", "scripts", "test"]   residue count: 34
defp tracked_files do
  {out, 0} = System.cmd("git", ["ls-files", "-z"], cd: File.cwd!())
  String.split(out, <<0>>, trim: true)
end

defp dirs_of(files) do
  for f <- files,
      parts = f |> Path.split() |> Enum.drop(-1),
      n <- 1..length(parts)//1,
      into: MapSet.new(),
      do: parts |> Enum.take(n) |> Path.join()
end

defp under?(file, dir), do: String.starts_with?(file, dir <> "/")

defp expected_exclude_paths(tracked, shipped) do
  has_shipped? = fn d -> Enum.any?(shipped, &under?(&1, d)) end

  for d <- dirs_of(tracked),
      not has_shipped?.(d),
      parent = Path.dirname(d),
      parent == "." or has_shipped?.(parent),
      do: d
end
# shipped = Enum.filter(tracked, &(&1 in built_archive().entries))  — use a MapSet
# The tarball also holds the untracked hex_metadata.config; intersecting with tracked drops it.
```
