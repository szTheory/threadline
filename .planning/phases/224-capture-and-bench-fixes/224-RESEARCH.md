## Summary

Phase 224 is two small, well-isolated fixes plus a measurement duty, all confined to code already read in full this session. The capture fix (CAPT-01/CAPT-02) is a one-line-conceptual change to `down_body/2` in `lib/mix/tasks/threadline.gen.triggers.ex`: stop filtering `function_downs` by `needs_per_table` so every first-run table's `down` unconditionally emits a `drop_function_if_unused` call. This is safe because `Naming.function_name/1` is a pure function of schema+table (verified by reading `lib/threadline/capture/naming.ex`), so the first-run migration can always predict the one possible per-table name before any rerun exists. `TriggerSQL.drop_function_if_unused/2` (`lib/threadline/capture/trigger_sql.ex:124-149`) is reused completely unchanged — it is already idempotent (no-op if the function doesn't exist) and already usage-checked (skips the drop and prints a WARNING if a live trigger still points at it), so wiring it in for every first-run table cannot regress the already-passing "keeps the function and warns" test (`trigger_rerun_test.exs:94-107`).

The test work (CAPT-02) has two parts. The deterministic regression test can and should reuse `test/support/migration_harness.ex`'s `generate!/2` + `Ecto.Migrator.up/down` pattern exactly as `test/threadline/upgrade_rollback_test.exs` already does — this is not a new isolation mechanism, it is the established one: migrations are applied against the suite's real `Repo` (writing real `schema_migrations` rows keyed by the file's numeric version) and the harness's `cleanup!/1` deletes those rows afterward. This directly answers the CONTEXT D-08 open question in the CONTEXT file: no new "isolated migrations source" is needed. The orphan check (D-09) can be copied near-verbatim from the SQL pattern already pinned and tested in `guides/upgrading-to-0.11.md`'s "Rolling back" section (lines 255-274) and proven live in `test/threadline/upgrade_rollback_test.exs`.

The bench fix (SUITE-05) is confirmed reproducible: running `cd bench && mix deps.get && mix compile` bare in this session failed with `module ExUnitProperties is not loaded and could not be found` while compiling `threadline`'s own `test/support/naming_generators.ex` — because bench's `mix compile` defaults to `MIX_ENV=dev`, but `bench/mix.exs` declares `{:threadline, path: "..", env: :test}`, which forces the `:threadline` path dependency itself into its `:test` env (compiling `test/support`, which `use`s `ExUnitProperties`/`stream_data`) while bench's own `deps.get` ran in `:dev` and never fetched `stream_data`. Adding `preferred_envs: [compile: :test, run: :test]` to `bench/mix.exs`'s `def cli` makes `mix compile` (and `mix deps.get`, which Mix keys off the *resolved* env for a bare invocation) run in `:test` throughout, matching root `mix.exs`'s own `def cli` pattern (`mix.exs:7-32`) almost exactly.

**Primary recommendation:** Implement D-01 exactly as specified (delete the `needs_per_table` filter on `function_downs` in `down_body/2`; leave `retire_ups/1` and the rerun-side down untouched), add the D-04 comment via a small helper mirroring `rerun_rollback_comment/2`, update every pinned test assertion listed below in one commit, then add the CAPT-02 tests (reusing `MigrationHarness` and the guide's D-09 SQL), then do the independent bench/CI fix, then the D-06 guide/CHANGELOG edit, then measure (D-18).

### Pattern 1: Deterministic-name drop instead of forward scan

**What:** `down_body/2` currently computes `function_downs` by filtering `first_run_specs` on `needs_per_table` (the CURRENT run's own opts), then emits `drop_function_if_unused(Naming.function_name(t))` only for those. D-01 removes that filter so it runs for **every** first-run table regardless of this run's `needs_per_table`.
**When to use:** Exactly here — this is the only place per-table function drop safety needs wiring, because `Naming.function_name/1` is deterministic and requires no knowledge of migrations that don't exist yet.
**Example (current code, to be changed):**
```elixir
# Source: lib/mix/tasks/threadline.gen.triggers.ex:596-606 (read this session)
function_downs =
  first_run_specs
  |> Enum.filter(fn {_t, %{needs_per_table: n?}} -> n? end)
  |> Enum.map_join("\n\n", fn {t, _} ->
    execute_line(TriggerSQL.drop_function_if_unused(Naming.function_name(t)))
  end)

[rerun_rollback_comment(table_specs, rerun_tables), trigger_downs, function_downs]
|> Enum.reject(&(&1 == ""))
|> Enum.join("\n\n")
```
The D-01 shape drops the `Enum.filter` entirely — `function_downs` becomes a map over ALL `first_run_specs`, plus a new per-table D-04 comment line prepended to each drop (see Pattern 2).

### Pattern 2: D-04 comment, in the style of `rerun_rollback_comment/2`

**What:** `rerun_rollback_comment/2` (`lib/mix/tasks/threadline.gen.triggers.ex:614-629`) already shows the established idiom: build a list of plain-English lines, `Enum.map_join("\n", &("    # " <> &1))`. The new first-run comment should follow the same idiom — one or two short lines before the function drop, not a full paragraph like the rerun comment (D-04 explicitly asks for "a short `#` comment").
**When to use:** Immediately above each unconditional function-drop `execute_line` in `function_downs`, once per table (or once for the block if all first-run tables share the wording — CONTEXT's suggested wording is per-table: "This also removes the per-table capture function of `<table>` ...").
**Example (existing idiom to mirror):**
```elixir
# Source: lib/mix/tasks/threadline.gen.triggers.ex:616-629 (read this session)
defp rerun_rollback_comment(table_specs, rerun_tables) do
```

### Pattern 3: Reuse `MigrationHarness` for the CAPT-02 regression test (answers D-08)

**What:** `test/support/migration_harness.ex` (read in full this session) already runs a generated migration file exactly the way `mix ecto.migrate`/`mix ecto.rollback` do: `generate!/2` calls the real `Mix.Tasks.Threadline.Gen.Triggers.run/1` into a tmp dir; `migrate_up/1` and `migrate_down/1` compile the migration file and call `Ecto.Migrator.up/4` / `.down/4` against the suite's real `Threadline.Test.Repo` (no isolated migrations table, no separate prefix); `cleanup!/1` deletes the `schema_migrations` row and purges the compiled module afterward. This exact harness is already used by `test/threadline/upgrade_rollback_test.exs` to prove a similar "no orphan after full rollback" property against real Postgres.
**When to use:** For the new `describe` block in `trigger_rerun_test.exs` (D-08). This satisfies CONTEXT's SC1 fidelity concern ("wired through `mix ecto.rollback --all` … or is text-extracted `execute` application enough") — `Ecto.Migrator.up/down` (not text-extracted `execute`) is already the established, cheap pattern for exactly this kind of test, and it does NOT need a separate migrations source: `MigrationHarness.cleanup!/1`'s explicit `DELETE FROM schema_migrations WHERE version = $1` is how the suite avoids polluting shared state. `trigger_rerun_test.exs`'s OWN existing helpers (`generate!/2`, `apply_up!/1`) are a *simpler*, older pattern that only extracts and replays `up`'s `execute` calls as raw SQL, bypassing `Ecto.Migrator` and `down` entirely — that pattern cannot exercise `down` at all, so it is insufficient for CAPT-02's partial/full rollback assertions and `MigrationHarness` (or a new `apply_down!/1` built the same way `MigrationHarness.migrate_down/1` already is) must be used or mirrored instead.
**Example:**
```elixir
# Source: test/support/migration_harness.ex (read in full this session)
def generate!(tmp, args) do ... end          # writes ONE migration file
def migrate_up(file), do: migrate(file, :up)     # Ecto.Migrator.up/4 against Repo
def migrate_down(file), do: migrate(file, :down) # Ecto.Migrator.down/4 against Repo
def cleanup!(files) do
  for file <- files do
    Repo.query!("DELETE FROM schema_migrations WHERE version = $1", [version(file)])
    ...
  end
end
```
Two migrations for the CAPT-02 regression = two `generate!/2` calls into the same tmp dir (second call is a rerun because `TriggerMigration.rerun?/2` scans `scan.sources`, which `write_migration!/3` reads from disk before writing the new file — `lib/mix/tasks/threadline.gen.triggers.ex:352,360-364`), then `migrate_up/1` both, then `migrate_down/1` in reverse order for partial vs. full-chain assertions.

### Pattern 4: The D-09 orphan check — copy the existing pinned SQL shape

**What:** `guides/upgrading-to-0.11.md` lines 255-274 (read this session) already contains the exact SQL shape D-09 asks for: `pg_proc` joined to `pg_namespace`, filtered on the configured storage schema, matching `threadline\_capture\_changes\_%` (escaped underscores — the global `threadline_capture_changes` function has no trailing `_%` so it never matches), and checked against `pg_trigger` with `t.tgparentid = 0` (excludes partition-clone triggers, per `TriggerSQL.drop_function_if_unused/2`'s own `DO` block, `lib/threadline/capture/trigger_sql.ex:138-141`, which uses the identical join). This SQL is already proven live by `test/threadline/upgrade_rollback_test.exs`.
**When to use:** Build the D-09 Elixir helper (likely in `MigrationHarness` or a new test-support function) as a direct SQL port of this guide block, parameterized on `StorageSchema.get()` (`lib/threadline/storage_schema.ex:43-47`) rather than hardcoding `'public'` — the guide's `<storage_schema>` placeholder must become a real bound parameter so the check never depends on `search_path` (per D-09's explicit warning about a stale local `public.threadline_capture_changes()`).
**Example (from the guide, to adapt into a query, not raw text):**
```sql
-- Source: guides/upgrading-to-0.11.md:257-273 (read this session)
SELECT p.oid, format('%I.%I', n.nspname, p.proname) AS qualified
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = '<storage_schema>'
  AND p.proname LIKE 'threadline\_capture\_changes\_%'
  AND NOT EXISTS (
    SELECT 1 FROM pg_trigger t WHERE t.tgfoid = p.oid AND t.tgparentid = 0
  )
```

### Anti-Patterns to Avoid
- **Forward-scanning later migrations to decide the first-run `down`:** impossible and explicitly rejected by D-01/CONTEXT — `TriggerMigration.covered_pairs/1` only sees migrations that exist at generation time, and a rerun by definition does not exist yet when the first-run migration is written.
- **Adding a `quiet:` option or any new parameter to `drop_function_if_unused/2`:** explicitly forbidden by D-02. The function is `@moduledoc false` (`lib/threadline/capture/trigger_sql.ex:2`) and unchanged.
- **A second cleanup-SQL snippet/marker pair in the upgrade guide:** explicitly forbidden by D-06 — extend prose under the existing `<!-- threadline:rollback-cleanup-sql:start/end -->` markers, do not add a new pair.
- **Adding a cache step to `verify-compile-no-optional`:** the job is pinned cache-free by a live contract test (`no_optional_cache_errors/1`, `test/threadline/ci_workflow_parity_contract_test.exs:4032-4045`), which scans the WHOLE job block for any `- uses: actions/cache` line, not just existing steps — a new step must not introduce one.

## Common Pitfalls

### Pitfall 1: Forgetting the rerun-side `down` must stay untouched
**What goes wrong:** Someone "fixes" the rerun's `down` to also emit a function drop, reasoning symmetry.
**Why it happens:** It looks inconsistent that only the first-run `down` drops the function.
**How to avoid:** D-01 explicitly explains why: `ecto.rollback` runs downs newest-first, so a rerun's `down` runs BEFORE the first-run's trigger drop — the trigger the rerun would check is always still live, so the guarded drop would never fire and would print a false "WARNING … kept" on every ordinary single-step rollback. Leave `retire_ups/1` and the rerun `down` path fully alone.
**Warning signs:** A new WARNING appears in `mix ecto.rollback` output on an ordinary rerun-only rollback that never touched a per-table function.

### Pitfall 2: Missing one of the five pinned test-assertion blocks
**What goes wrong:** `down_body/2`'s new shape breaks tests that were never updated, and CI goes red in a way unrelated to the intended fix.
**Why it happens:** The exact-output assertions are spread across multiple `describe` blocks in one large test file.
**How to avoid:** Update, in the same commit as the generator change, every one of:
  1. `test/mix/tasks/threadline/gen_triggers_test.exs:791-793` — "a first-run table keeps today's rollback" (plain `posts` table: today asserts `executes(file, :down) == [TriggerSQL.drop_trigger("posts")]`; after D-01 this must include the function drop + D-04 comment even though `posts` was never per-table).
  2. Lines 795-807 — the `per_table` sub-case in the same test (test_redaction_users): already includes the drop, but now needs the comment too.
  3. Lines 809-829 — "a rerun table's rollback leaves capture on" (`rerun` file's down: must STILL be `[]`/no trigger-down+function-down — unaffected by D-01, verifies the guard).
  4. Lines 831-843, 845-862, 864-883, 885-894 — the mixed-table-set, "names the function it retired" and "retires nothing" down-comment tests; the "does not restore the earlier capture policy" phrase set is on the RERUN side (unaffected), but any test asserting the FIRST-RUN file's down text (e.g., `refute File.read!(first) =~ "does not recreate"`, lines 852/874) must keep passing since D-04's new comment uses different wording than the rerun's `retired_lines`.
  5. Lines 27-31 (`@generated_down_phrases`) and 21-26 (`@rerun_doc_phrases`) — these constants gate the "rerun documentation" describe block (lines 907-953) and must stay in sync with whatever D-04/D-05 wording is chosen; they currently only cover the RERUN comment, so D-04's new FIRST-RUN comment wording does not need to be added to these two constants unless the planner also chooses to doc-contract-pin it.
**Warning signs:** `mix test test/mix/tasks/threadline/gen_triggers_test.exs` red on assertions unrelated to the property/regression tests being added.

### Pitfall 3: The bench fix alone doesn't restore a broken bench state
**What goes wrong:** After adding `preferred_envs`, `bench && mix compile` still fails because `bench/deps` was already fetched under `:dev` in a previous run (stale `mix.lock`/`_build` state) with `stream_data` missing.
**Why it happens:** `preferred_envs` only affects env RESOLUTION for a bare invocation going forward; a dirty `_build`/deps cache from a prior `:dev` run can mask the fix locally.
**How to avoid:** The CI job runs on a fresh checkout every time, so this only matters for local verification — `rm -rf bench/_build bench/deps` (or `mix deps.get` after the fix) before confirming green locally, and note this in VERIFICATION.md's repro steps.
**Warning signs:** `mix compile` in bench still errors after the `preferred_envs` edit is applied, but a fresh clone or `_build` wipe succeeds.

### Pitfall 4: `verify.bench_compile` colliding with `ci.all`'s cache-free-verify-compile-no-optional exclusion text
**What goes wrong:** The `@build_cache_exclusions` map (`test/threadline/ci_workflow_parity_contract_test.exs:2402-2403`) and `no_optional_cache_errors/1` (line 4032) key on the literal job id `"verify-compile-no-optional"` and scan its ENTIRE block, not per-step. Since D-15 adds the bench-compile step INSIDE that same job (not a new job), any cache step added anywhere in that job — including one accidentally added for the new bench-compile step — trips this existing contract test.
**How to avoid:** Do not add a `uses: actions/cache@...` step for the new "Compile bench project (bare mix compile)" step. `mix deps.get` for bench will re-fetch on every run of this job (acceptable per D-15: "No cache step. That job is pinned to zero cache steps").
**Warning signs:** `mix test test/threadline/ci_workflow_parity_contract_test.exs` fails with `rule=no-optional-cache`.
