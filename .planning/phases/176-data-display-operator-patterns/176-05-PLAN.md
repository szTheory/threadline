<objective>
Replace the client-only `data-confirm` retention prune with a T3 type-to-confirm flow that is enforced ENTIRELY server-side, wire per-row kebab actions, fix the policy/redaction diff-table collapse, and gate the (backend-less) redact action behind a blocking human checkpoint. This is the security core of Phase 176: the current prune is a confirmed open hole (client-only `data-confirm`, no `secure_compare`, no authz re-check, no audit-the-action).

Purpose: a client `data-confirm` provides zero server enforcement — an attacker bypasses it trivially, and a forged `phx-value-id` can target another scope's data. DATA-04's load-bearing fix is server enforcement: re-fetch the canonical token from the DB at action time, `Plug.Crypto.secure_compare` it against the operator-typed value, re-check authorization (the client id is an untrusted claim, not a grant), scope-filter the query so a forged id fails closed, audit the destructive action itself as an `AuditAction`, and default to refusal on every mismatch. This is a BLOCKING high-severity threat — a plan that leaves it client-only fails the security gate. The redact action has NO runtime backend (redaction is codegen-time only), so it is gated behind a human checkpoint rather than implemented against a non-existent handler.
Output: `retention_history_live.ex` rebuilt prune handler with full D-21 enforcement + `data_table` stream adoption + kebab; `policy_redaction_live.ex` diff-collapse fix; the Plan-01 T3 security RED test GREEN; the redact backend question resolved at a checkpoint.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator browser → prune_now handle_event | `phx-value-id` + typed confirmation are untrusted client claims; the server is the only authority (the security core of this phase) |
| canonical token (DB) → comparison | the token must be re-fetched server-side and compared constant-time; never shipped to the client |
| destructive action → audit trail | every irreversible action must be recorded as an AuditAction (audit the auditor) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan | Severity |
|-----------|----------|-----------|-------------|-----------------|----------|
| T-176-10 | Tampering / EoP | client-only `data-confirm` prune | mitigate | DELETE the client confirm; move ALL enforcement to `handle_event` (Task 2). Client confirm is never the gate. | **high (BLOCKING)** |
| T-176-11 | Elevation of Privilege | forged `phx-value-id` targeting another scope | mitigate | Re-check authz in the event + scope-filter the query; forged id fails closed (Task 2). Test asserts refusal. | high |
| T-176-12 | Spoofing | replaying/forging the typed confirmation token | mitigate | Re-fetch canonical token from DB at action time; `Plug.Crypto.secure_compare`; never ship token to client (Task 2). | high |
| T-176-13 | Information disclosure | timing attack on token compare | mitigate | `Plug.Crypto.secure_compare/2` (constant-time) — never hand-rolled `==` (Task 2). | medium |
| T-176-14 | Repudiation | unaudited destructive prune | mitigate | Record the prune as an `AuditAction` (Task 2). Test asserts the record on success. | medium |
| T-176-15 | Tampering | redact handler against a non-existent backend | mitigate | Blocking `checkpoint:human-verify` (Task 1) resolves scope before any handler is written; default defers redact. | medium |
| T-176-SC | Tampering | npm/pip/cargo installs | accept | No installs (zero new runtime deps invariant); `Plug.Crypto` already a direct dep. Not applicable per RESEARCH.md. | low |
</threat_model>
